## 一、先明确课程目标

本课程的首要目标是帮助计算机应用技术专业学生形成就业能力，主要面向：

- 云计算运维；
- Linux 运维；
- 网络工程师；
- 初级系统与网络管理员。

“网络系统管理”竞赛是课程设计的重要参考，但不是课程本身的目标。课程不能为了覆盖竞赛项目而不断扩充内容，更不能改造成竞赛集训。内容取舍的优先级为：

1. 岗位实际使用频率与必要性；
2. 学生能否在当前基础和学时内真正掌握；
3. 与前后课程是否连贯；
4. 是否能形成可操作、可验证、可排障的任务；
5. 竞赛标准是否提供了有价值的能力参照。

竞赛参考依据：

- 人社部门组织的网络系统管理选拔赛通常包含理论、服务器和网络三个模块；
- WorldSkills Network Systems Administration 标准强调数据传输网络、网络与系统运维、基础设施自动化和故障排查；
- 本模块只承担其中与 Linux 服务器网络实施、远程管理、主机防护和故障排查有关的部分。

官方参考：

- [中华人民共和国第三届职业技能大赛比赛项目名单](https://www.mohrss.gov.cn/xxgk2020/fdzdgknr/qt/gztz/202503/W020250307314017631874.pdf)
- [北京市人社局网络系统管理项目选拔赛说明](https://rsj.beijing.gov.cn/ywsite/zyjd/jnjs/jsxx/202507/t20250716_4150436.html)

## 二、专业课程之间的边界

学生不是只学习本课程，因此不要在模块二重复建设完整的网络、自动化、安全或云计算课程。

### 2.1 已有或同期课程

- 已学：C 语言程序设计、Web 前端、计算机组成原理、Python 程序设计、计算机网络技术、MySQL。
- 同期：交换路由技术、Python 自动化运维。
- Python 自动化运维会学习 Ansible、Paramiko 和 Fabric。

### 2.2 下一学期课程

- 网络安全基础；
- 云计算应用；
- 企业级综合实训项目。

企业级综合实训计划从 eNSP 网络拓扑开始，继续配置 Linux 服务器和业务，最终完成网络通信、服务运行与综合验收。Kubernetes 在“云计算应用”中重点学习；“虚拟化容器技术”只安排基础使用和操作体验。

### 2.3 本模块与其他课程的分工

| 内容 | 主要承担课程 | 模块二如何处理 |
|---|---|---|
| VLAN、Trunk、STP、链路聚合、静态路由、OSPF | 交换路由技术 | 不重复配置，只在排障场景中理解网关和路径 |
| Linux 地址、网卡、路由、DNS、Socket、服务访问 | Linux 模块二 | 核心内容 |
| SSH、文件传输、远程同步 | Linux 模块二 | 核心内容 |
| firewalld、SELinux 基础诊断与回滚 | Linux 模块二 | 核心内容 |
| Bash 自动化 | Linux 课程 | 只做少量、可逐行理解的辅助操作 |
| Ansible、Paramiko、Fabric | Python 自动化运维 | 不在模块二展开 |
| 深度攻防、安全审计 | 网络安全基础 | 模块二只做主机基础防护 |
| Docker 网络与容器服务 | 虚拟化容器技术 | 后续从本模块的网络和端口知识继续 |
| Kubernetes 网络与编排 | 云计算应用 | 本模块不提前展开 |

课程之间应当使用同一套思路逐步升级，而不是互相重复：

```text
交换路由技术完成网络拓扑和路由交换
        ↓
Linux 模块二完成服务器接入、远程管理、服务验证和基础防护
        ↓
Python 自动化运维完成批量管理和自动化执行
        ↓
虚拟化容器技术完成业务容器化
        ↓
下学期完成网络安全、云平台和企业综合联调
```

## 三、模块二的准确定位

模块二不是缩小版的交换路由课程，也不是网络系统管理竞赛集训。其定位是：

> 从 Linux 服务器视角学习网络接入、远程管理、服务验证、基础防护和故障排查，为云计算运维、Linux 运维、网络工程和后续综合实训建立共同基础。

学生完成模块二后，应能处理以下真实任务：

- 为三台 Linux 虚拟机规划并配置固定地址、网关和 DNS；
- 判断地址、子网、网关、路由和名称解析是否正确；
- 判断服务是否监听、端口是否可达、应用是否响应；
- 从 Ubuntu 运维端通过 SSH 管理两台 Rocky Linux 服务器；
- 使用密钥认证、客户端别名、SCP、SFTP 和 rsync；
- 配置 firewalld 的最小开放、来源限制并完成安全回滚；
- 判断 SELinux 是否阻止服务访问资源；
- 使用网络状态、服务状态、日志和少量数据包证据定位故障；
- 编写“现象—证据—判断—根因—修复—验证—回退”的故障报告。

## 六、经过审查后确定的优化方向

### 6.1 章节 2.1 与实验 8

当前教材已经包含 `ip route get` 和 `ip neigh`，实验 8 也已经使用 `ip route get`。不要重复编写已有内容。

需要补齐或加强的是：

- 用很短的篇幅说明 TCP/IP 分层与 Linux 排障对象的对应关系，不要求背诵完整 OSI 七层；
- 解释 CIDR 前缀、子网掩码、网络地址、广播地址、可用地址和默认网关；
- 用课程真实 VMnet8 参数做一到两个判断题，不安排大量子网计算；
- 把 `ip neigh` 加入实验 8 的观察和证据记录；
- 如果加入 `tracepath`，必须先检查 Rocky 和 Ubuntu 是否已经安装对应软件包，并提供无法安装时的替代方案；它不是必须新增的核心命令；
- 保持 Ubuntu 22.04 Desktop 使用 NetworkManager 图形界面与状态命令，不要直接套用 Ubuntu Server Netplan 模板。

实验 8 的核心仍然是三机静态网络、重启持久化、互通矩阵和一次可恢复故障，不得被理论计算挤占。

### 6.2 章节 2.2 与实验 9

当前端口、监听地址、`ss` 和 `nc` 的方向正确。需要加入最低限度的 `tcpdump`，原因是云计算运维和网络故障排查需要判断“数据包是否到达”。

只要求掌握少量、可解释的过滤方式，例如：

```bash
sudo tcpdump -i any -nn icmp
sudo tcpdump -i any -nn port 53
sudo tcpdump -i any -nn tcp port 80
sudo tcpdump -i any -nn tcp port 22
```

限制：

- 不讲复杂 BPF 表达式；
- 不要求使用 Wireshark；
- 不把抓包变成独立大型实验；
- 使用前确认软件包来源和安装方法可在机房环境完成；
- 每次抓包都必须配合另一终端发起明确请求，并说明如何使用 `Ctrl+C` 停止；
- 输出较长时只保存必要证据，不要求学生逐包分析全部字段。

实验 9 只有 2 学时，必须通过删减换取时间。

### 6.3 章节 2.4 与实验 9

保留：

- HTTP 请求与响应；
- 常见状态码；
- `curl -I`、`curl -v`、状态码与耗时；
- HTTPS 和证书的基本作用；
- 客户端验证失败时的基本现象。

压缩：

- 手工生成自签名证书；
- 完整 HTTPS 服务配置；
- 复杂证书字段分析。

实验 9 中，HTTPS 证书制作应明确标注为拓展或教师演示，不能一边写“拓展”，一边又在必交成果中要求全部学生提交。核心验收应集中在端口、DNS、HTTP 和基础抓包证据。

### 6.4 章节 2.5～2.7 与实验 10

当前三章和实验 10 的方向正确，原则上不扩充功能。

必须保持：

- Ubuntu 运维端分别管理 `rocky-server` 和 `rocky-web`；
- 主机指纹、密码登录、Ed25519 密钥、`ssh-copy-id`；
- `~/.ssh/config` 客户端别名；
- SCP、SFTP、远程命令；
- 至少一次认证或配置故障的“观察—修复—复测”；
- 涉及 SSH 服务端安全变更时使用双会话和明确回退，不能把学生锁在服务器外。

不要加入 Ansible；本实验只为后续 Python 自动化运维准备稳定的 SSH、密钥和 sudo 基础。

### 6.5 章节 2.8 与实验 11

`rsync` 具有岗位价值，应保留；但现有核心偏向本地备份，远程同步的重要性不足。

优化后应突出：

- 复用实验 10 的 SSH 密钥和客户端别名；
- Ubuntu 与 Rocky 之间通过 SSH 完成 rsync；
- 第一次同步、文件变化后的增量同步和 `--dry-run`；
- 源目录末尾 `/` 的语义；
- 谨慎使用 `--delete`；
- 从备份完成一次隔离恢复和内容验证。

`cron` 保留基础使用，但降低脚本复杂度：

- 命令先逐行执行并确认结果；
- 最后才允许组合成短脚本；
- 不编写长篇“万能备份脚本”；
- 异常通知、复杂轮转和批量主机管理留给后续课程。

实验 11 只有 2 学时，远程 rsync、恢复验证是核心；完整定时脚本可降为拓展。

### 6.6 章节 2.9～2.11 与实验 12

当前 firewalld、来源限制、运行时/永久规则、回滚、SELinux 上下文和 AVC 日志方向正确，应保留。

边界：

- 不深入编写自定义 SELinux 策略模块；
- 不扩展为网络攻防实验；
- 不用“关闭 firewalld”或“关闭 SELinux”作为最终修复；
- 每次规则变更都必须有验证、持久化判断和回退；
- 必须保留 SSH 管理入口。

### 6.7 章节 2.12 与实验 13

当前“客户端—地址与路由—名称解析—端口—服务—防火墙—SELinux—应用与日志”的分层排障主线很好，是模块二最接近岗位任务和竞赛能力标准的部分。

只做有限增强：

- 至少一张故障卡允许或要求使用 `tcpdump` 判断数据包是否到达；
- 在故障报告中记录使用该命令的理由和观察结果，而不是只贴截图；
- 保持至少三个不同层次的故障；
- 每次只修改一个因素，修复后必须从原客户端按原路径复测；
- 不增加故障总数，以免超过 4 学时。

## 七、Shell 脚本使用原则

教师已经明确：可以适当使用 Shell 脚本，但不能让脚本代替学生完成任务。

所有教材和实验应遵守：

1. 新知识首次出现时，一条命令一条命令执行；
2. 每条命令解释输入、作用、输出和验证方法；
3. 先手工完成并理解完整任务，再考虑封装；
4. 只把已经执行成功的少量命令组合成短脚本；
5. 避免开场给出数十行脚本让学生整体复制；
6. 不用脚本一次性创建大量后续才会解释的文件、用户、目录和服务；
7. 脚本失败时，学生必须能定位具体失败步骤。

## 八、三机环境和连续状态

所有修改必须服从当前三机环境，不得改回双机：

| 主机 | 主要角色 |
|---|---|
| `ubuntu-client` | 学生运维端、客户端、远程验证端 |
| `rocky-server` | 数据、管理和基础服务服务器 |
| `rocky-web` | Web 与后续业务服务器 |

重要状态：

- 模块二从 `Linux-L1` 基线开始；
- 实验 8 生成三机固定地址、`/etc/hosts` 和每台主机自己的 `~/m1-project/course-env.sh`；
- 实验 10 生成 SSH 密钥和客户端配置；
- 实验 12 保持正确的 firewalld 与 SELinux 基线；
- 实验 13 结束形成 `Linux-L2`；
- `Linux-L2` 继续供模块三和虚拟化容器技术使用。

机房存在还原环境，教材不能假设前一节课状态天然存在。每个实验开头必须写清：

- 知识前置；
- 状态依赖；
- 建议起点或快照；
- 恢复后的预检命令；
- 缺失对象应如何创建或恢复。

## 十、内容可执行性检查

每个章节和实验修改后必须逐项检查：

1. 命令使用的目录是否已经创建；
2. 文件是否在前文创建，或者明确由教师素材提供；
3. 用户、用户组、服务、端口和主机名是否已经存在；
4. 命令在哪台虚拟机、哪个用户、哪个终端执行；
5. 是否需要 `sudo`；
6. 软件包是否已安装，离线或国内软件源是否可用；
7. 多行命令是否可以拆成初学者能理解的单步操作；
8. 修改配置前是否备份；
9. 网络、SSH、防火墙和 SELinux 变更是否有回退入口；
10. 故障修复后是否从原客户端按原路径复测；
