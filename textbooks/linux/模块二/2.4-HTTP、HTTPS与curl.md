# 2.4 HTTP、HTTPS与curl

> 所属课程：《Linux操作系统》

> 学习前置：2.2端口与监听、2.3名称解析

## 学习目标

完成本章后，应能够：

1. 说明一次HTTP访问经过名称解析、TCP连接和HTTP请求响应的过程。
2. 识别URL、请求方法、状态码、响应头和响应体。
3. 使用`curl`分别查看内容、响应头、详细连接过程、状态码和耗时。
4. 区分“TCP连接失败”“HTTP返回错误状态”和“TLS证书验证失败”。
5. 说明HTTPS提供的保护，以及证书名称、有效期和信任链的作用。

## 2.4.1 HTTP位于哪一层

HTTP是应用层协议。它规定客户端怎样描述请求、服务器怎样返回结果。一次访问通常经历：

```text
解析URL
→ 把主机名解析为IP
→ 根据路由到达目标
→ 与目标端口建立TCP连接
→ HTTPS场景进行TLS握手
→ 发送HTTP请求
→ 接收HTTP响应
```

任何一层失败，都可能表现为“网页打不开”。排障时不能只看浏览器最后的提示。

常见端口：

| 协议 | 常见默认端口 | 实验端口 |
|---|---:|---:|
| HTTP | 80 | 8080 |
| HTTPS | 443 | 8443 |

80和443是约定的默认值，不是强制要求。URL使用其他端口时必须明确写出，例如`http://rocky-server:8080/`。

## 2.4.2 URL的组成

观察：

```text
https://rocky-server.test:8443/docs/index.html?unit=2
```

| 部分 | 示例 | 作用 |
|---|---|---|
| Scheme | `https` | 指定协议 |
| Host | `rocky-server.test` | 指定目标名称 |
| Port | `8443` | 指定目标端口 |
| Path | `/docs/index.html` | 指定服务器上的资源路径 |
| Query | `unit=2` | 向应用传递查询参数 |

URL中的路径不是客户端本地文件路径。服务器怎样把URL映射到文件或程序，由Web服务配置决定。

## 2.4.3 HTTP请求与响应

一个简化的HTTP请求：

```http
GET /index.html HTTP/1.1
Host: rocky-server.test:8080
User-Agent: curl
Accept: */*
```

- 请求行包含方法、路径和HTTP版本。
- `Host`用于说明客户端希望访问哪个站点。
- 其他Header描述客户端能力或请求条件。
- POST、PUT等请求还可能带有Body。

一个简化的响应：

```http
HTTP/1.0 200 OK
Content-Type: text/html
Content-Length: 24

<h1>HTTP practice</h1>
```

- 状态行包含HTTP版本、状态码和说明。
- Header描述内容类型、长度、缓存等信息。
- 空行之后是响应Body。

常见方法：

| 方法 | 一般用途 |
|---|---|
| `GET` | 获取资源 |
| `HEAD` | 只获取响应头 |
| `POST` | 提交数据或触发处理 |
| `PUT` | 创建或整体替换资源 |
| `DELETE` | 删除资源 |

具体接口是否允许某种方法，应以应用文档和权限控制为准。

## 2.4.4 状态码

| 分类 | 含义 | 常见示例 |
|---|---|---|
| 1xx | 临时信息 | 100 Continue |
| 2xx | 请求成功 | 200、201、204 |
| 3xx | 重定向或缓存 | 301、302、304 |
| 4xx | 请求、认证或权限相关问题 | 400、401、403、404 |
| 5xx | 服务端或上游处理失败 | 500、502、503、504 |

几个常见区别：

- `200 OK`：请求成功并返回内容。
- `301/302`：资源要求客户端访问另一个位置。
- `403 Forbidden`：服务器理解请求，但拒绝提供资源。
- `404 Not Found`：服务器收到请求，但目标资源不存在。
- `502 Bad Gateway`：代理没有从上游获得有效响应。
- `503 Service Unavailable`：服务当前不可用。

状态码只能描述HTTP层结果，不能单独给出唯一根因。例如403可能与应用权限、文件权限或SELinux有关。

## 2.4.5 使用curl查看HTTP

本节在`rocky-server`使用两个终端。

### 第一步：准备站点

在终端A创建目录：

```bash
mkdir -p ~/course-practice/m2/ch24
```

打开首页：

```bash
vim ~/course-practice/m2/ch24/index.html
```

写入：

```html
<h1>HTTP practice</h1>
```

保存并退出。

### 第二步：启动临时HTTP服务

在终端A运行：

```bash
python3 -m http.server 18080 --bind 0.0.0.0 --directory ~/course-practice/m2/ch24
```

保持终端A运行。后续命令在终端B执行。

### 第三步：获取响应体

```bash
curl http://127.0.0.1:18080/
```

预期看到首页中的HTML。

### 第四步：只看响应头

```bash
curl -I http://127.0.0.1:18080/
```

`-I`发出HEAD请求，用于快速查看状态行和响应头。

### 第五步：查看连接与报文细节

```bash
curl -v http://127.0.0.1:18080/
```

在详细输出中：

- 以`>`开头的是curl发送的请求内容。
- 以`<`开头的是服务器返回的响应内容。
- `Connected to`附近显示连接目标和端口。

### 第六步：只输出状态码与耗时

```bash
curl -sS -o /dev/null -w 'code=%{http_code} total=%{time_total}\n' http://127.0.0.1:18080/
```

常用选项：

| 选项 | 作用 |
|---|---|
| `-sS` | 隐藏进度条，但保留错误 |
| `-o FILE` | 把响应体写入指定文件 |
| `-o /dev/null` | 丢弃响应体 |
| `-w FORMAT` | 按格式输出状态码、耗时等信息 |
| `-L` | 跟随重定向 |
| `--connect-timeout` | 限制建立连接的等待时间 |
| `--max-time` | 限制整个请求的总时间 |

### 第七步：观察404

```bash
curl -sS -o /dev/null -w 'code=%{http_code}\n' http://127.0.0.1:18080/not-found
```

预期HTTP状态码为404。此时TCP连接和HTTP通信都已经成功，只是请求的资源不存在。

## 2.4.6 HTTP错误与curl退出状态

默认情况下，curl收到404后仍可能退出0，因为它成功完成了HTTP事务。

要求4xx和5xx作为命令失败：

```bash
curl --fail-with-body http://127.0.0.1:18080/not-found
```

紧接着查看上一条命令的退出状态：

```bash
echo $?
```

这两条命令必须在同一个终端连续执行。`$?`只保存上一条命令的退出状态。

三类问题应分开判断：

| 问题层次 | 典型现象 | 主要证据 |
|---|---|---|
| TCP连接失败 | refused、timeout | `ss`、`nc`、`curl -v` |
| HTTP错误 | 收到403、404、502等 | 状态码、响应头、服务日志 |
| 内容不符合预期 | 状态码可能为200 | 响应体、应用日志、业务数据 |

## 2.4.7 HTTPS与TLS

HTTPS是在TLS保护的连接中传输HTTP。

TLS主要提供：

1. 机密性：传输内容经过加密。
2. 完整性：传输内容被篡改时能够被发现。
3. 身份验证：客户端根据证书判断服务端身份。

HTTPS不表示网站内容本身一定安全，也不替代账号权限、漏洞修复和业务安全。

简化握手过程：

```text
客户端发送支持的TLS版本、算法和访问名称
→ 服务端返回选择结果和证书
→ 客户端验证证书
→ 双方协商会话密钥
→ 使用加密通道传输HTTP
```

交互观察：[Socket、TCP、HTTP与TLS端到端访问动画](../../../animations/06-socket-tcp-http-tls/index.html)。重点观察`SNI`、证书`SAN`和客户端信任库的关系。

## 2.4.8 客户端怎样验证证书

客户端通常检查：

- 证书是否由受信任的CA签发。
- 当前时间是否处于证书有效期内。
- URL中的主机名是否包含在证书SAN中。
- 证书签名和证书链是否有效。

常见失败：

| 现象 | 含义 |
|---|---|
| 自签名证书不受信任 | 客户端信任库中没有对应签发者 |
| 证书过期或尚未生效 | 当前时间不在有效期内 |
| 主机名不匹配 | URL名称不在证书SAN中 |
| 证书链不完整 | 服务端没有提供必要的中间证书 |

使用curl查看HTTPS握手细节：

```text
curl -v https://<实际测试站点>/
```

`-k`或`--insecure`会跳过证书验证：

```text
curl -vk https://<实际测试站点>/
```

它只能用于受控实验中的对照诊断，不能作为生产环境证书错误的长期解决办法。

如果已经取得可信的实验CA或公开证书文件，可以显式指定：

```text
curl --cacert <CA证书文件> https://<与证书SAN一致的名称>/
```

客户端仍会检查证书有效期和名称。

## 本章练习：HTTP证据表

保持`rocky-server`终端A中的18080服务运行，在终端B逐条完成。

| 目标 | 命令 | 需要记录的证据 |
|---|---|---|
| 证明端口监听 | `ss -lnt` | 监听地址和端口 |
| 获取首页 | `curl http://127.0.0.1:18080/` | 响应体 |
| 查看响应头 | `curl -I http://127.0.0.1:18080/` | 状态行和Content-Type |
| 查看完整过程 | `curl -v http://127.0.0.1:18080/` | 连接目标、请求行、响应状态 |
| 只看状态码 | `curl -sS -o /dev/null -w 'code=%{http_code}\n' http://127.0.0.1:18080/` | 200 |
| 请求不存在资源 | `curl -sS -o /dev/null -w 'code=%{http_code}\n' http://127.0.0.1:18080/not-found` | 404 |

回答：

1. 404是否表示TCP连接失败？为什么？
2. `curl -I`与普通`curl`显示内容有什么差异？
3. `curl -v`中`>`和`<`分别表示什么？
4. 为什么生产环境不能长期使用`curl -k`？

完成后回到终端A按`Ctrl+C`，再检查端口：

```bash
ss -lnt
```

确认18080已经不再监听。
