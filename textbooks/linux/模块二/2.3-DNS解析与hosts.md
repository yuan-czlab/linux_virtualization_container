## 2.3.1 名称解析解决什么问题

人更容易记住`rocky-server`或`www.example.com`，网络通信最终仍需要IP地址。名称解析负责把名称转换为一个或多个地址。

名称解析成功不等于目标服务可用。完整访问还要经过：

```text
名称解析 → 路由选择 → 到达目标主机 → 目标端口监听 → 应用处理
```

因此“域名能解析”只能证明解析阶段获得了地址。

## 2.3.2 Linux系统解析链

Linux应用通常不会直接读取某一个DNS文件，而是调用系统名称服务接口。系统再按照`/etc/nsswitch.conf`决定查询来源和顺序。

```text
curl、ssh等应用
→ 系统名称服务接口
→ /etc/nsswitch.conf中的hosts规则
→ /etc/hosts、DNS或其他来源
→ 返回地址
```

查看当前`hosts`规则：

```bash
grep '^hosts:' /etc/nsswitch.conf
```

Rocky与Ubuntu的内容可能不同。常见关键字包括：

| 关键字 | 含义 |
|---|---|
| `files` | 查询`/etc/hosts` |
| `dns` | 查询DNS服务器 |
| `resolve` | 通过systemd-resolved查询 |
| `myhostname` | 解析本机名称 |

顺序会影响结果。若`files`位于`dns`之前，`/etc/hosts`中的同名记录通常会先被系统应用使用。

查看本地静态映射：

```bash
cat /etc/hosts
```

实验8已经加入三台课程虚拟机的映射。每一行的基本格式为：

```text
IP地址  规范主机名  可选别名
```

例如：

```text
192.168.200.10  rocky-server rocky-server.test
```

实际地址必须以实验8参数表为准。

## 2.3.3 DNS客户端配置

查看兼容的解析器配置入口：

```bash
cat /etc/resolv.conf
```

常见字段：

| 字段 | 作用 |
|---|---|
| `nameserver` | 指定DNS服务器 |
| `search` | 为短名称尝试追加搜索域 |
| `options` | 设置超时、重试等解析行为 |

`/etc/resolv.conf`可能是普通文件，也可能由NetworkManager或systemd-resolved生成。

查看它是否为符号链接：

```bash
ls -l /etc/resolv.conf
```

在Rocky中查看NetworkManager当前获得的DNS：

```bash
nmcli -f IP4.DNS device show
```

在Ubuntu中还可以查看systemd-resolved状态：

```bash
resolvectl status
```

持久DNS应通过负责管理网络的工具配置。直接修改自动生成的`/etc/resolv.conf`，内容可能在重新连接或重启后被覆盖。

## 2.3.4 DNS查询的基本过程

客户端通常把请求交给递归解析器。递归解析器可能直接返回缓存，也可能继续询问根DNS、顶级域DNS和权威DNS。

```text
客户端
→ 递归解析器
→ 缓存命中：直接返回
→ 缓存未命中：根 → 顶级域 → 权威DNS
→ 把结果返回客户端并缓存
```

本课程重点是DNS客户端使用和故障排查，不在本模块搭建企业DNS服务器。

常见记录类型：

| 类型 | 常见用途 |
|---|---|
| `A` | 名称对应IPv4地址 |
| `AAAA` | 名称对应IPv6地址 |
| `CNAME` | 一个名称作为另一个名称的别名 |
| `MX` | 指定邮件交换服务器 |
| `NS` | 指定某个域的权威DNS服务器 |
| `PTR` | 把IP地址反向解析为名称 |
| `TXT` | 保存文本、所有权验证或邮件安全策略等信息 |

## 2.3.5 getent、dig与nslookup

Rocky Linux 9安装DNS查询工具：

```bash
sudo dnf install -y bind-utils
```

Ubuntu 22.04先刷新软件包索引：

```bash
sudo apt update
```

安装查询工具：

```bash
sudo apt install -y dnsutils
```

### getent：模拟普通应用的系统解析

查询课程主机：

```bash
getent hosts rocky-server
```

查询公共名称：

```bash
getent hosts mirrors.aliyun.com
```

`getent`遵循系统NSS规则，更接近`curl`和`ssh`等应用的解析行为。

### dig：直接观察DNS查询

查询A记录：

```bash
dig mirrors.aliyun.com A
```

只显示简短答案：

```bash
dig +short mirrors.aliyun.com A
```

查询AAAA记录：

```bash
dig mirrors.aliyun.com AAAA
```

完整输出中应重点观察：

- `status`：查询状态，例如`NOERROR`或`NXDOMAIN`。
- `ANSWER SECTION`：DNS返回的记录。
- `SERVER`：本次实际使用的DNS服务器。
- `Query time`：查询耗时。

### nslookup：快速交互查询

```bash
nslookup mirrors.aliyun.com
```

`nslookup`便于快速查询，但结构化排障通常优先使用`dig`。

## 2.3.6 证明hosts与DNS不是同一条路径

查询`localhost`的系统解析结果：

```bash
getent hosts localhost
```

再直接询问DNS：

```bash
dig +short localhost
```

很多系统中，第一条命令可以从本地来源得到结果，而第二条命令没有相同答案。这说明：

- `getent`按NSS规则查询，可能读取`/etc/hosts`。
- `dig`直接向DNS服务器发起查询，不读取`/etc/hosts`。

再对课程主机进行对照：

```bash
getent hosts rocky-server
```

```bash
dig +short rocky-server
```

如果实验8只在`/etc/hosts`配置了`rocky-server`，`getent`应成功，而`dig`通常不会得到相同记录。

## 2.3.7 DNS故障排查顺序

名称解析失败时按下列顺序检查：

```text
1. 已知IP或网关是否可达
2. 当前网络连接是否取得DNS服务器
3. /etc/resolv.conf实际指向哪里
4. getent是否能够通过系统解析链得到地址
5. dig向默认DNS查询是否成功
6. dig向指定DNS查询是否成功
7. /etc/hosts或nsswitch是否覆盖了预期结果
8. UDP/TCP 53是否被网络策略阻断
```

检查默认路由：

```bash
ip route
```

使用参数表中的实际网关测试：

```text
ping -c 2 <实际网关>
```

检查有效DNS：

```bash
nmcli -f IP4.DNS device show
```

通过系统解析链查询：

```bash
getent hosts mirrors.aliyun.com
```

直接查询默认DNS：

```bash
dig mirrors.aliyun.com
```

如果机房允许访问指定公共DNS，还可以进行对照：

```bash
dig @223.5.5.5 mirrors.aliyun.com
```

指定DNS查询失败不一定是DNS软件问题，也可能是机房禁止客户端绕过统一DNS。

## 2.3.8 安全地模拟一次DNS查询失败

本练习不修改系统DNS配置，只让一次`dig`请求发送到文档示例地址`192.0.2.53`：

```bash
dig +time=2 +tries=1 @192.0.2.53 example.com
```

观察退出状态：

```bash
echo $?
```

这两条命令必须在同一个终端中按顺序执行，因为`$?`只表示上一条命令的退出状态。

该方法的优点是不会破坏软件源、SSH和后续实验使用的DNS。实验9会在有明确恢复值的前提下，完成一次真正的DNS配置故障与恢复。
