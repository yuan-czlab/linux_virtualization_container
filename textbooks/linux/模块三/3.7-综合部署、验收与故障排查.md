# 3.7 综合部署、验收与故障排查

> 所属课程：《Linux操作系统》
> 所属模块：模块三 企业服务器部署与综合运维
> 对应整册教材：第31章
> 对应实验：实验20 Linux企业服务器综合项目
> 学习路径：读取需求 → 设计架构 → 核对基线 → 分层整合 → 验证安全与恢复 → 故障排查 → 文档交付

本章把前面分散学习的Linux基础、网络、SSH、Nginx、MySQL、MongoDB、Redis、Git和Shell巡检整合为一个三机项目。重点不再是“会不会输入某条命令”，而是能否说明系统为什么这样设计、如何证明它可用、出现故障如何定位，以及机房还原后如何继续课程。

## 3.7.1 项目情境与学习目标

TechCorp需要交付一套小型业务环境：

- `ubuntu-client`作为用户和管理员客户端；
- `rocky-web`作为统一Web入口；
- `rocky-server`运行后端服务和三类数据服务；
- 两台Rocky都保持firewalld运行和SELinux Enforcing；
- Git保存脱敏运维资料；
- Shell脚本检查服务器状态；
- 备份必须能够通过恢复验证。

完成本章后，应能够：

1. 从业务需求推导主机角色、访问方向和端口边界；
2. 解释Nginx、后端服务和数据服务之间的依赖；
3. 使用“可运行、可访问、可使用、可保护、可恢复、可交付”六个维度验收系统；
4. 按照网络、进程、监听、安全控制、协议和数据逐层排障；
5. 为故障建立现象、假设、证据、修复和回归验证记录；
6. 形成能够由另一名学习者复核，并能由后续容器课程继承的`Linux-L4`成果。

## 3.7.2 最终三机架构

```text
ubuntu-client
  │
  ├── SSH/22 ───────────────► rocky-web
  ├── SSH/22 ───────────────► rocky-server
  │
  └── HTTP/80 ──────────────► rocky-web
                                │
                                ├── /            静态站点
                                ├── /health      Nginx健康页
                                │
                                └── /api/ ──────► rocky-server:5000
                                                   techcorp-api
                                                       │
                                                       ├── MySQL 127.0.0.1:3306
                                                       ├── MongoDB 127.0.0.1:27017
                                                       └── Redis 127.0.0.1:6379
```

这一结构体现了两层访问边界：

1. `ubuntu-client`只能直接访问Web入口和SSH，不能直接访问后端5000和数据库端口；
2. `rocky-web`可以访问`rocky-server:5000`，但MySQL、MongoDB和Redis仍只供`rocky-server`本机使用。

后端采用Python内置HTTP服务器仅用于课程中演示systemd和跨机反向代理，不属于生产级应用服务器。

## 3.7.3 系统成功不是组件状态相加

每个服务单独显示`active`，不代表整个系统已经成功：

```text
Nginx active
  + 80端口监听
  + 客户端能够到达
  + server_name匹配
  + 文件权限与SELinux正确
  + upstream可以访问
  = Web入口才可能真正可用
```

类似地：

- Nginx配置语法正确，但后端停止，`/api/`仍可能返回502；
- MySQL监听3306，但业务账号没有表权限，业务查询仍会失败；
- MongoDB认证成功，但用户角色不包含业务库，操作仍会被拒绝；
- Redis返回`PONG`，但业务键或持久化可能仍不正确；
- Git工作区干净，但并不能证明数据库备份可以恢复。

综合项目要验证完整路径，而不是收集互不关联的“成功截图”。

## 3.7.4 从需求推导端口边界

先回答“谁必须访问谁”，再决定监听和防火墙：

| 目标主机 | 端口 | 使用者 | 期望边界 |
|---|---:|---|---|
| `rocky-web` | 22 | 课程管理客户端 | 课程网络可达 |
| `rocky-web` | 80 | `ubuntu-client` | 课程网络可达 |
| `rocky-server` | 22 | 课程管理客户端 | 课程网络可达 |
| `rocky-server` | 5000 | 仅`rocky-web` | 监听业务地址，防火墙限制来源 |
| `rocky-server` | 3306 | 本机应用与管理员 | 仅回环监听，不开放防火墙 |
| `rocky-server` | 27017 | 本机应用与管理员 | 仅回环监听，不开放防火墙 |
| `rocky-server` | 6379 | 本机应用 | 仅回环监听，不开放防火墙 |

监听与防火墙解决不同问题：

- 监听决定进程接受哪些本地地址上的连接；
- firewalld决定通过网络进入主机的流量是否允许；
- 应用认证决定连接到达服务后能否使用功能；
- 应用授权决定认证身份可以操作什么数据。

只设置其中一层不能代替其他层。

## 3.7.5 六维验收模型

| 维度 | 核心问题 | 典型证据 |
|---|---|---|
| 可运行 | 进程能否稳定启动并由系统管理 | `systemctl`、`journalctl` |
| 可访问 | 正确来源能否到达目标地址和端口 | `ip`、`getent`、`ss`、`firewall-cmd`、`nc` |
| 可使用 | 客户端能否完成协议和业务操作 | `curl`、SQL查询、文档查询、Redis键读取 |
| 可保护 | 非授权来源和身份是否被拒绝 | 监听范围、rich rule、认证失败、最小权限 |
| 可恢复 | 配置、文件和数据能否从备份恢复 | `diff`、测试数据库、校验值、重启读取 |
| 可交付 | 他人能否依据资料复核和接管 | Git历史、部署记录、故障记录、检查点 |

“失败符合预期”也是有效验收。例如`ubuntu-client`直接访问`rocky-server:5000`应失败，因为安全策略只允许`rocky-web`来源。

## 3.7.6 基线检查与停止点

综合项目开始前，应确认前19个实验留下的状态真实存在。

在每台主机先确认身份：

```bash
printf 'host=%s user=%s\n' "$(hostnamectl --static)" "$(whoami)"
```

查看网络：

```bash
ip -brief address
```

查看路由：

```bash
ip route
```

确认名称解析：

```bash
getent hosts rocky-server rocky-web ubuntu-client
```

确认安全控制：

```bash
getenforce
```

```bash
sudo firewall-cmd --state
```

出现以下情况时应停止集成，先回到对应实验恢复：

- 主机名或固定IP与课程规划不一致；
- 三机名称解析错误；
- SSH密钥登录不可用；
- 根分区空间不足；
- SELinux不是Enforcing；
- firewalld没有运行；
- Nginx或任一数据服务缺失；
- 实验18的Git仓库或实验19脚本不存在。

在错误基线上继续叠加配置，会让后续现象同时包含多个根因。

## 3.7.7 依赖关系与整合顺序

推荐按依赖从内到外整合：

```text
三机身份、地址、路由、解析和SSH
        ↓
rocky-server后端文件、低权限账户和systemd服务
        ↓
rocky-server:5000监听与来源限制
        ↓
rocky-web到后端的直接访问
        ↓
Nginx反向代理与SELinux布尔值
        ↓
ubuntu-client访问统一Web入口
        ↓
MySQL、MongoDB、Redis本机认证与数据
        ↓
备份恢复、Git、巡检、故障和交付
```

如果先配置Nginx、后检查后端，遇到502时会同时面对解析、网络、防火墙、进程和SELinux多个未知项。逐层验证可以把故障范围压缩到刚刚增加的层。

## 3.7.8 自建服务的systemd闭环

将一个后端程序交给systemd，至少需要考虑：

| 配置 | 作用 |
|---|---|
| `User`、`Group` | 避免使用root运行普通业务程序 |
| `WorkingDirectory` | 指定程序工作目录 |
| `ExecStart` | 给出绝对可执行文件和参数 |
| `Restart=on-failure` | 进程异常退出时重新启动 |
| `NoNewPrivileges=true` | 阻止进程获得新的额外权限 |
| `PrivateTmp=true` | 提供独立临时目录视图 |
| `WantedBy=multi-user.target` | 允许设置常规多用户启动目标启用 |

单元文件修改闭环：

```text
备份旧单元
→ 使用vim修改
→ systemd-analyze verify
→ systemctl daemon-reload
→ systemctl restart/enable
→ systemctl is-active
→ journalctl
→ ss检查端口
→ curl检查协议内容
```

`systemctl daemon-reload`只让systemd重新读取单元定义，不会自动重启服务；`enable`设置开机启动，也不等于当前已经运行。

## 3.7.9 Nginx跨主机反向代理

实验14中，Nginx代理的是`rocky-web`本机`127.0.0.1:5000`。综合项目将后端迁移到`rocky-server:5000`，增加了真实的跨主机链路。

请求过程：

```text
ubuntu-client请求 /api/health.json
→ rocky-web:80接收请求
→ Nginx匹配location /api/
→ 去掉匹配前缀并转发到rocky-server:5000
→ techcorp-api读取health.json
→ 响应沿原路径返回
```

Nginx配置中的：

```nginx
location /api/ {
    proxy_pass http://rocky-server:5000/;
}
```

两个URI都以`/`结尾时，请求`/api/health.json`会把匹配的`/api/`替换为`/`，后端收到`/health.json`。

跨主机代理还需要满足：

- `rocky-web`能正确解析`rocky-server`；
- `rocky-server`的后端监听业务地址；
- `rocky-server`防火墙允许`rocky-web`来源；
- `rocky-web`的SELinux允许Nginx建立网络连接；
- 后端文件可由低权限服务用户读取。

## 3.7.10 SELinux与Unix权限共同生效

站点文件访问同时受到Unix权限和SELinux控制：

```bash
namei -l /srv/techcorp/www/index.html
```

```bash
ls -lZ /srv/techcorp/www/index.html
```

`namei -l`检查路径每一级目录是否允许遍历，`ls -lZ`检查文件权限与SELinux类型。正确做法是为非默认站点目录设置持久文件上下文并执行`restorecon`，而不是使用`chmod 777`或关闭SELinux。

Nginx连接远程后端还可能需要：

```bash
getsebool httpd_can_network_connect
```

配置错误时，应从Nginx错误日志和AVC记录寻找证据：

```bash
sudo ausearch -m AVC -ts recent
```

## 3.7.12 备份与恢复矩阵

| 对象 | 备份方法 | 恢复位置 | 最小验证 |
|---|---|---|---|
| 静态站点 | `rsync`或归档 | 独立测试目录 | `diff -ru`无差异 |
| Nginx配置 | 原文件副本 | 临时检查或明确回退 | `nginx -t`与三个URL |
| MySQL | `mysqldump` | `company_final_restore` | 表存在、行数和内容正确 |
| MongoDB | `mongodump` | `company_final_restore`命名空间 | 集合存在、文档数正确 |
| Redis | `BGSAVE`与RDB副本 | 课程只做重启读取 | 键仍存在、RDB文件非空 |
| Shell脚本 | Git提交 | 工作区或指定版本 | `bash -n`、正常/异常测试 |

“文件存在”不是恢复验证。空文件、错误数据库、缺失权限或不兼容版本都可能使备份无法使用。应优先恢复到隔离目标，验证成功后再决定是否影响正式数据。

## 3.7.13 配置变更闭环

每次变更都应完成：

```text
确认目标与影响范围
→ 记录当前基线
→ 建立不会被覆盖的备份
→ 一次只修改一个目标
→ 检查语法或配置结构
→ 应用变更
→ 检查进程与日志
→ 检查监听与安全策略
→ 从真实客户端验证业务
→ 检查相邻功能没有回归
→ 提交脱敏资料
```

修改失败时，不应继续叠加第二项修改。先依据日志定位，或用明确备份恢复到最近通过状态。

## 3.7.14 分层排障方法

收到故障描述后，先把模糊表述改写为可验证问题：

```text
谁：ubuntu-client
在什么时间：完成Nginx上游修改后
访问什么：http://techcorp.test/api/health.json
得到什么：HTTP 502
哪些仍正常：首页与/health正常
```

由此可知：客户端到Nginx入口大概率正常，问题更接近Nginx上游或后端链路。

推荐顺序：

1. 客户端目标：URL、地址、端口、协议是否正确；
2. 名称与网络：解析、地址、路由、连通性；
3. 服务状态：systemd是否active，journal有何错误；
4. 监听：进程是否监听预期地址和端口；
5. 网络控制：活动zone、规则和来源是否匹配；
6. SELinux与权限：是否有AVC、路径是否可遍历；
7. 应用协议：HTTP状态、数据库认证、授权和数据；
8. 回归：修复后从原客户端重走完整路径，并检查相邻功能。

## 3.7.15 常见现象与优先证据

| 现象 | 优先证据 | 常见方向 |
|---|---|---|
| 客户端无法解析域名 | `getent hosts` | hosts或DNS |
| 连接超时 | `ip route`、firewalld、监听范围 | 网络路径或丢弃规则 |
| Connection refused | `systemctl`、`ss` | 服务未运行或未监听目标地址 |
| Nginx 403 | `namei -l`、`ls -lZ`、error log、AVC | Unix权限或SELinux标签 |
| Nginx 404 | `nginx -T`、URI映射、文件路径 | server/location或资源不存在 |
| Nginx 502 | 后端`curl`、systemd、5000监听、error log、AVC | 上游不可达或协议失败 |
| MySQL Access denied | 用户、来源、密码、`SHOW GRANTS` | 认证或授权 |
| MongoDB Authentication failed | 用户所在认证库和密码 | 身份验证 |
| MongoDB Unauthorized | `connectionStatus`和角色 | 已认证但权限不足 |
| Redis NOAUTH | `AUTH`与配置 | 已连接但未认证 |
| 服务重启失败 | `systemctl status`、`journalctl` | 语法、路径、权限、端口冲突 |

## 3.7.16 故障记录与假设验证

合格故障记录至少包含：

```text
故障编号：
现象与时间：
影响范围：
第一条证据：
初步假设：
用于证伪或证实的下一条命令：
根因：
修改前备份：
修复操作：
原路径复测：
相邻功能回归：
预防方法：
```

不要把“重启以后好了”直接写成根因。重启只是操作，根因可能是配置错误、依赖未启动、端口冲突或临时资源问题。

一个假设必须能够被证据证实或证伪。例如：

```text
假设：rocky-server上的techcorp-api没有监听5000。
验证：在rocky-server执行ss与systemctl。
若5000存在且服务active：否定该假设，继续检查firewalld与SELinux。
若服务failed且journal显示目录不存在：根因接近WorkingDirectory配置。
```

## 3.7.17 回归验证

修复后至少进行两类验证：

1. 原故障路径：最初失败的用户、地址和操作现在是否成功；
2. 相邻功能：修复是否破坏其他原本正常的功能。

例如修复502后，不仅要验证`/api/health.json`，还要验证首页、`/health`、5000来源限制、SELinux状态和后端巡检。为了“让API成功”而对整个网段开放5000，不是正确修复。

## 3.7.18 证据的质量

有效证据应包含：

- 命令或操作对象；
- 主机身份；
- 时间；
- 关键结果；
- 对结果的判断。

截图只是一种载体。只有一张`active`截图不能证明完整业务链路。命令输出也不应无限堆积，应围绕问题选择能够区分假设的证据。

证据中必须避免：

- 明文密码或认证令牌；
- SSH私钥内容；
- 无关人员信息；
- 为了好看而伪造或修改命令输出；
- 只有结果、没有主机与检查对象。

## 3.7.19 Git交付与秘密边界

Git仓库适合保存：

- 脱敏Nginx模板；
- `server-health.sh`；
- 服务关系和端口说明；
- 部署步骤与故障记录模板；
- 变更原因和已验证标签。

Git仓库不保存：

- `/etc`中含真实密码的完整配置副本；
- MySQL或MongoDB备份；
- Redis RDB/AOF；
- SSH私钥；
- 运行日志和大体积证据。

提交前依次执行`status`、工作区差异、精确`add`和暂存区差异。`.gitignore`是防误操作的一层，不是秘密管理系统。

## 3.7.20 交付文档

另一名管理员应能够从交付材料获得：

1. 三机主机名、固定IP、角色和访问方向；
2. 服务、端口、监听范围与防火墙策略；
3. 关键配置路径、语法检查和启停方法；
4. 首页、健康页、后端和数据服务的验证方法；
5. 备份位置、创建时间、恢复目标和验证结果；
6. Git仓库、脚本用法和退出码；
7. 已知限制和未完成事项；
8. 至少三项故障的完整证据链。

文档应写出“如何验证”和“如何回退”，而不只写“已经配置完成”。

## 3.7.21 从Linux-L4过渡到虚拟化与容器

| Linux课程资产 | 后续容器课程中的对应能力 |
|---|---|
| 进程与systemd | 容器主进程、生命周期和重启策略 |

## 3.7.23 模块总结

1. 综合运维从需求和访问方向出发，不从随意开放端口出发。
2. 系统要从可运行、可访问、可使用、可保护、可恢复和可交付六个维度验收。
3. 组件应按依赖从内到外整合，每增加一层就立即验证。
4. 故障排查要明确现象和影响范围，用证据逐个验证假设。
5. 修复后必须重走原故障路径，并检查相邻功能没有回归。
6. 备份必须在隔离目标恢复，Git不能替代数据库和文件备份。
7. `Linux-L4`是后续虚拟化容器课程的正式起点，课程资产必须保留。
