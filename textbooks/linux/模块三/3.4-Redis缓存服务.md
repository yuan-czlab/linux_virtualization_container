# 3.4 Redis缓存服务

> 所属课程：《Linux操作系统》
> 所属模块：模块三 企业服务器部署与综合运维
> 对应整册教材：第28章
> 对应实验：实验17 Redis缓存服务部署与运行维护
> 学习路径：理解缓存场景 → 认识键与数据类型 → 配置本机服务 → 完成认证 → 验证持久化 → 排查故障

本章在`rocky-server`上部署Redis。Redis只监听本机回环地址，不向`ubuntu-client`开放6379端口。这样的设计符合当前项目的实际需求：同一台服务器上的应用可以访问Redis，而校园网中的其他主机不能直接访问Redis。

## 3.4.1 项目情境与学习目标

TechCorp的巡检平台需要保存以下运行数据：

- 网站累计访问次数；
- 最近一次巡检结果；
- 只保留几分钟的临时验证码；
- 需要去重的在线节点名称。

这些数据读写频繁，其中一部分具有明确的过期时间。直接为每一次读取都查询磁盘数据库会增加响应时间，因此项目决定在`rocky-server`上部署一个只供本机应用使用的Redis服务。

完成本章后，应能够：

1. 说明Redis与MySQL、MongoDB在数据组织和使用场景上的区别；
2. 使用string、hash、list、set和过期时间完成基础数据操作；
3. 解释`bind`、`protected-mode`、认证和防火墙之间的关系；
4. 区分RDB快照与AOF追加日志；
5. 根据服务、端口、认证、日志和数据状态定位常见故障；
6. 判断一个Redis实例是否满足“可运行、可使用、可保护、可恢复”的基本要求。

## 3.4.2 Redis解决什么问题

Redis是一个以内存读写为主的键值数据服务。客户端通过键找到值，常用于缓存、计数器、会话、排行榜、临时状态和轻量队列。

```text
应用程序
   │ Redis命令
   ▼
127.0.0.1:6379
   │ 认证与权限检查
   ▼
Redis内存数据集
   │ 根据持久化策略
   ├──────────► RDB时间点快照
   └──────────► AOF写命令日志
```

“以内存为主”不等于“数据一定不会保存到磁盘”，也不等于“可以替代所有数据库”。Redis是否适合作为唯一数据源，取决于业务能否接受数据丢失、持久化方式、备份策略和高可用设计。

| 对比项 | MySQL | MongoDB | Redis |
|---|---|---|---|
| 主要数据组织 | 表、行、列 | 数据库、集合、文档 | 键和值 |
| 典型查询 | SQL与关系查询 | 文档查询 | 按键读写和数据结构操作 |
| 主要存储介质 | 磁盘为主，利用缓存 | 磁盘为主，利用缓存 | 内存为主，可持久化到磁盘 |
| 本课程典型用途 | 业务记录 | 灵活的巡检文档 | 计数、临时状态和缓存 |

## 3.4.3 服务端、客户端与端口

Redis环境中需要区分服务端和客户端：

| 名称 | 作用 |
|---|---|
| `redis-server` | 运行Redis服务端进程 |
| `redis-cli` | 向Redis发送命令的命令行客户端 |
| `redis` | Rocky Linux中常见的systemd服务单元名 |
| `/etc/redis/redis.conf` | 官方RPM常用的主配置文件 |
| 6379/TCP | Redis默认TCP端口 |

查看软件版本：

```bash
redis-server --version
```

观察结果中的`v=`字段，它表示服务端版本。再查看客户端版本：

```bash
redis-cli --version
```

查看服务是否运行：

```bash
systemctl is-active redis
```

返回`active`只说明systemd认为服务正在运行，并不能证明认证、业务键和持久化都正常。

查看6379端口：

```bash
sudo ss -lntp | grep ':6379'
```

重点观察本地地址：

- `127.0.0.1:6379`表示仅接受本机IPv4连接；
- `[::1]:6379`表示仅接受本机IPv6连接；
- `0.0.0.0:6379`表示监听所有IPv4接口，风险明显增大；
- 没有结果通常表示服务未启动、使用了其他端口，或启动失败。

## 3.4.4 进入与退出redis-cli

连接本机默认端口：

```bash
redis-cli
```

进入后，提示符类似：

```text
127.0.0.1:6379>
```

此时输入的是Redis命令，不是Linux命令。先检查服务响应：

```text
PING
```

正常返回：

```text
PONG
```

退出客户端：

```text
EXIT
```

如果执行`PING`得到`NOAUTH Authentication required`，说明TCP连接已经到达Redis，但当前会话尚未通过认证。这与“连接被拒绝”不是同一种故障。

## 3.4.5 键、值与命名

Redis中的键相当于数据的名字。键在当前逻辑数据库内必须唯一，值可以采用不同的数据类型。

项目中可使用冒号组织键名：

```text
service:nginx:status
service:mysql:status
inspection:last_time
website:visitors
```

这种写法不是目录结构，而是一种便于阅读、筛选和管理的命名约定。生产环境还常加入系统名、环境名或租户名，例如`techcorp:prod:website:visitors`。

查看键的数据类型：

```text
TYPE website:visitors
```

判断键是否存在：

```text
EXISTS website:visitors
```

删除指定键：

```text
DEL practice:temporary
```

不要为了清理一个练习键而执行`FLUSHDB`或`FLUSHALL`。前者清空当前逻辑数据库，后者清空全部逻辑数据库。

## 3.4.6 string：文本、状态与计数

string是最基础的数据类型，可保存文本、数字或二进制内容。

写入服务状态：

```text
SET service:nginx:status active
```

读取服务状态：

```text
GET service:nginx:status
```

创建访问计数：

```text
SET website:visitors 0
```

原子加一：

```text
INCR website:visitors
```

再次读取：

```text
GET website:visitors
```

`INCR`由Redis在服务端完成。多个客户端并发计数时，它比“先GET、在客户端加一、再SET”更不容易产生覆盖问题。

仅当键不存在时写入：

```text
SET service:owner ops NX
```

`NX`适合“只创建、不覆盖”的场景；如果键已存在，命令不会修改原值。

## 3.4.7 过期时间与缓存生命周期

缓存数据通常不应永久存在。Redis可以为键设置生存时间，即TTL（Time To Live）。

创建一个120秒后自动失效的键：

```text
SET verification:code 482916 EX 120
```

查看剩余秒数：

```text
TTL verification:code
```

常见结果：

| 返回值 | 含义 |
|---:|---|
| 正整数 | 剩余生存秒数 |
| `-1` | 键存在，但没有设置过期时间 |
| `-2` | 键不存在，可能已经过期 |

为已有键设置300秒过期时间：

```text
EXPIRE inspection:temporary 300
```

取消过期时间：

```text
PERSIST inspection:temporary
```

TTL不仅是一个命令知识点，还代表缓存设计中的生命周期管理。如果所有临时键都永久保留，内存会持续增长。

## 3.4.8 常见数据类型

### 1. hash：保存对象字段

hash适合保存一个对象的多个字段。

```text
HSET server:rocky-server ip 192.168.10.10 role database status active
```

读取一个字段：

```text
HGET server:rocky-server status
```

读取全部字段：

```text
HGETALL server:rocky-server
```

### 2. list：保存有顺序的元素

向列表左侧加入巡检事件：

```text
LPUSH inspection:events "nginx checked"
```

再加入一条事件：

```text
LPUSH inspection:events "mysql checked"
```

查看列表：

```text
LRANGE inspection:events 0 -1
```

### 3. set：保存不重复的成员

加入已巡检的节点：

```text
SADD inspection:nodes rocky-server rocky-web
```

再次加入`rocky-server`不会产生重复成员：

```text
SADD inspection:nodes rocky-server
```

查看集合：

```text
SMEMBERS inspection:nodes
```

### 4. sorted set：按分值排序

记录各服务的响应时间：

```text
ZADD service:latency 18 nginx 35 mysql 12 redis
```

按分值从小到大查看：

```text
ZRANGE service:latency 0 -1 WITHSCORES
```

本课程重点使用string、计数和TTL。其他类型用于理解Redis不是只能保存简单文本，不要求展开复杂编程。

## 3.4.9 安全边界：监听、认证与防火墙

Redis应只允许可信客户端访问。在本项目中，Redis与调用它的应用位于同一台`rocky-server`，因此没有开放远程连接的必要。

关键配置示例：

```text
bind 127.0.0.1 -::1
protected-mode yes
port 6379
requirepass <实验中设置的长密码>
```

四项配置的作用不同：

| 配置或控制 | 解决的问题 | 不能替代什么 |
|---|---|---|
| `bind` | 决定Redis在哪些本地地址监听 | 不能代替认证 |
| `protected-mode yes` | 在缺少安全配置时降低误暴露风险 | 不能代替正确监听和认证 |
| `requirepass` | 为默认用户设置共享密码 | 不能限制不同用户的不同权限 |
| firewalld | 控制哪些网络来源能访问端口 | 不能代替Redis内部认证 |

Redis 6及更高版本支持ACL，可以创建具名用户并限制命令和键。`requirepass`是兼容性较好的基础认证方式，本课程用它理解认证闭环；ACL的细粒度授权作为拓展内容。

连接后交互认证：

```text
AUTH <实验密码>
```

认证成功返回`OK`。查看当前ACL用户：

```text
ACL WHOAMI
```

使用`requirepass`时通常返回`default`。

不要把密码直接写在以下位置：

- 截图和实验报告；
- Git仓库；
- Shell历史中的`redis-cli -a 明文密码`；
- 可被其他用户读取的脚本或配置副本。

## 3.4.10 内存上限与淘汰策略

Redis主要使用内存。如果没有容量边界，持续写入可能耗尽系统内存。

查看内存信息：

```text
INFO memory
```

重点关注：

- `used_memory_human`：Redis当前已分配内存；
- `used_memory_peak_human`：历史峰值；
- `maxmemory_human`：配置的内存上限；
- `mem_fragmentation_ratio`：内存碎片相关指标之一。

常见配置项：

```text
maxmemory 0
maxmemory-policy noeviction
```

`maxmemory 0`在64位系统中通常表示没有由Redis配置的显式上限，并不代表机器拥有无限内存。达到上限后的行为由淘汰策略决定：

| 策略 | 基本行为 | 典型考虑 |
|---|---|---|
| `noeviction` | 不再接受会增加内存的写命令 | 数据不能被自动淘汰 |
| `allkeys-lru` | 从全部键中近似淘汰较久未使用的键 | 通用缓存场景 |
| `allkeys-lfu` | 从全部键中近似淘汰较少使用的键 | 关注访问频率的缓存 |
| `volatile-ttl` | 从设置了过期时间的键中优先淘汰TTL较短的键 | 只有部分键允许淘汰 |

不能只因为某个策略“常见”就直接套用。选择策略前需要判断哪些数据可以丢失、哪些键设置了TTL，以及业务在写入被拒绝时如何处理。

## 3.4.11 RDB与AOF持久化

Redis提供多种持久化选择：只使用RDB、只使用AOF、两者同时使用，或者完全不持久化。

| 机制 | 工作方式 | 优点 | 代价与风险 |
|---|---|---|---|
| RDB | 按条件生成某一时刻的数据快照 | 文件紧凑，适合备份，恢复通常较快 | 两次快照之间的新数据可能丢失 |
| AOF | 追加记录写操作，启动时重放 | 通常可获得更细的恢复点 | 文件通常更大，并带来写入与重写开销 |

常见RDB配置：

```text
save 3600 1
dbfilename dump.rdb
dir /var/lib/redis
```

`save 3600 1`表示在3600秒内至少发生1次修改时触发快照。不同版本和软件包的默认值可能不同，应以实际配置和运行信息为准。

常见AOF配置：

```text
appendonly no
appendfilename "appendonly.aof"
appendfsync everysec
```

Redis 7开始使用多部分AOF文件，因此不能再假定AOF永远只有一个普通文件。确认实际文件结构时应结合版本、`INFO persistence`和数据目录。

## 3.4.12 受控验证RDB

进入`redis-cli`并认证后，创建验证键：

```text
SET persistence:check course-data
```

发起后台快照：

```text
BGSAVE
```

`BGSAVE`由子进程在后台保存，服务端仍可处理请求。课程环境也能执行`SAVE`，但`SAVE`是同步操作，数据量大时会阻塞服务，不应养成在生产环境随意执行的习惯。

查看最近一次成功保存时间：

```text
LASTSAVE
```

查看持久化状态：

```text
INFO persistence
```

重点观察：

- `rdb_bgsave_in_progress`是否回到`0`；
- `rdb_last_bgsave_status`是否为`ok`；
- `rdb_last_save_time`是否更新；
- `aof_enabled`是否与配置一致。

重启服务后重新认证，再读取`persistence:check`。只有键仍然存在，才能证明“写入—生成持久化文件—服务重启—重新加载”这条最小链路已经通过。

## 3.4.13 持久化不等于备份

RDB或AOF与Redis服务通常位于同一台机器。如果磁盘损坏、虚拟机被还原或文件被误删，本机持久化文件也可能一起丢失。

一个基本备份闭环包括：

1. 确认后台保存已经成功；
2. 确认实际数据目录和文件名；
3. 将持久化文件复制到独立备份目录或其他主机；
4. 记录备份时间、Redis版本和配置；
5. 在隔离环境执行恢复验证。

在本课程2学时实验中完成“RDB生成、文件检查和重启读取”，完整的隔离恢复作为拓展任务。实验20继续检查Redis是否具备恢复依据。

## 3.4.14 配置变更闭环

修改服务配置时应遵循固定顺序：

```text
确认当前状态
→ 定位配置文件
→ 只在备份不存在时创建备份
→ 使用vim修改少量配置
→ 检查目标行和重复项
→ 重启服务
→ 检查systemd与journal
→ 检查监听地址
→ 从客户端验证未认证与已认证行为
→ 验证业务键和持久化
```

定位RPM软件包中的配置文件：

```bash
rpm -ql redis | grep '/redis\.conf$'
```

查看关键配置时不要输出密码行：

```bash
sudo grep -nE '^(bind|protected-mode|port|save|appendonly|maxmemory|maxmemory-policy)' /etc/redis/redis.conf
```

如果`requirepass`出现多条有效配置，后出现的配置可能覆盖前面的配置，容易造成“明明修改过却认证失败”。修改后应搜索并确认只有预期配置生效，但提交证据时必须隐藏密码内容。

## 3.4.15 故障现象与分层判断

| 现象 | 已经证明什么 | 优先检查 |
|---|---|---|
| `Connection refused` | 已到达目标主机，但目标地址和端口没有接受连接 | 服务状态、监听地址、端口 |
| 连接超时 | 尚不能证明到达服务进程 | IP、路由、防火墙、监听范围 |
| `NOAUTH` | TCP连接与Redis响应正常，但尚未认证 | 执行AUTH、检查客户端配置 |
| `WRONGPASS` | 已到认证阶段，但凭据或用户名错误 | 密码、ACL用户、认证方式 |
| `PONG` | 当前会话可以执行PING | 继续验证业务键、TTL和持久化 |
| 重启后键丢失 | 写入曾成功，但持久化恢复链路未通过 | RDB/AOF配置、保存状态、数据目录、日志 |

服务失败时先查看状态：

```bash
systemctl status redis --no-pager
```

再查看本次启动日志：

```bash
sudo journalctl -u redis -b -n 80 --no-pager
```

查看端口：

```bash
sudo ss -lntp | grep ':6379'
```

最后使用客户端验证：

```bash
redis-cli
```

排障时从“进程—监听—连接—认证—命令—数据—持久化”逐层验证，比反复重装软件更容易定位根因。

## 3.4.16 本章练习：设计巡检缓存数据

### 练习目标

为TechCorp巡检平台设计并验证一组缓存数据。每输入一条命令，就观察一次返回结果，不要整段复制。

### 任务一：选择数据类型

为以下需求选择Redis数据类型并说明理由：

1. 网站累计访问次数；
2. 服务器的IP、角色和状态；
3. 按发生先后保存最近的巡检事件；
4. 保存不重复的已巡检节点；
5. 保存两分钟后失效的验证码。

### 任务二：逐条创建数据

进入客户端：

```bash
redis-cli
```

如果服务已启用认证，先执行：

```text
AUTH <实验密码>
```

创建访问计数：

```text
SET practice:visitors 0
```

将计数增加一次：

```text
INCR practice:visitors
```

创建服务器对象：

```text
HSET practice:server ip 192.168.10.10 role database status active
```

创建一个120秒临时键：

```text
SET practice:code 482916 EX 120
```

立即查看TTL：

```text
TTL practice:code
```

等待一段时间后再次查看TTL，说明为什么数值发生变化。

### 任务三：形成验证证据

查询计数：

```text
GET practice:visitors
```

查询服务器对象：

```text
HGETALL practice:server
```

确认临时键是否存在：

```text
EXISTS practice:code
```

退出客户端：

```text
EXIT
```

### 练习验收

- 能说明每个键为什么选择对应数据类型；
- 能解释`INCR`返回值；
- 能区分`TTL`的正整数、`-1`和`-2`；
- 每个被查询的键都由前序步骤明确创建；
- 没有使用`KEYS *`、`FLUSHDB`或`FLUSHALL`。

## 3.4.17 本章小结

1. Redis通过键和值组织数据，适合缓存、计数和临时状态等高频访问场景。
2. TTL决定缓存数据生命周期，容量上限和淘汰策略决定内存不足时的行为。
3. `bind`、保护模式、认证和防火墙分别位于不同安全层，不能互相替代。
4. RDB生成时间点快照，AOF记录写操作；两者的恢复点、文件大小和性能代价不同。
5. `active`和`PONG`都只是局部证据，完整验收还要检查认证、业务数据和持久化。
6. 故障排查应按照进程、监听、连接、认证、命令和数据逐层进行。
