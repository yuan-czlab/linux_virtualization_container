# 3.5 Git与运维版本管理

> 所属课程：《Linux操作系统》
> 所属模块：模块三 企业服务器部署与综合运维
> 对应整册教材：第29章
> 对应实验：实验18 Git项目获取与版本恢复
> 学习路径：认识版本问题 → 理解三区状态 → 建立仓库 → 审查并提交 → 模拟协作 → 恢复误改

本章在`rocky-server`上建立TechCorp运维资料仓库。仓库保存脱敏配置模板、巡检脚本和说明文档，不保存真实密码、私钥、数据库转储和运行日志。实验18形成的仓库会在实验19中继续保存巡检脚本，并在实验20中形成最终交付记录。

## 3.5.1 项目情境与学习目标

服务器配置不是“一次写完、永远不变”的文件。管理员会修改端口、反向代理、检查脚本和交接文档。如果只保存`配置-最终版`、`配置-最终版2`等副本，很快就会遇到以下问题：

- 不知道哪一个版本真正通过了验收；
- 不知道某行由谁、因为什么修改；
- 误改后无法准确恢复单个文件；
- 多人交换文件时容易互相覆盖；
- 密码、日志和数据库备份可能被混入资料目录。

Git通过提交记录管理文本变化，可以回答“改变了什么、为什么改变、哪个版本可恢复”。完成本章后，应能够：

1. 说明工作区、暂存区、本地仓库和远程仓库的关系；
2. 使用`status`、`diff`、`add`、`commit`、`log`和`show`形成可追溯版本；
3. 使用`.gitignore`排除运行文件和敏感文件，并说明它的边界；
4. 使用裸仓库模拟团队中心，完成`push`、`clone`和`pull --ff-only`；
5. 根据文件所处状态选择正确的恢复命令；
6. 说明Git与文件备份、数据库备份和密码管理的区别。

## 3.5.2 Git适合管理哪些运维资产

| 资产 | 是否适合进入Git | 原因 |
|---|---|---|
| 脱敏配置模板 | 适合 | 文本差异清晰，可审查和恢复 |
| Shell或Python脚本 | 适合 | 可追踪逻辑变化并关联测试 |
| 部署与故障记录 | 适合 | 便于交接和复盘 |
| 架构图源文件 | 通常适合 | 文件较小且需要版本记录 |
| 真实密码、令牌、私钥 | 不适合 | Git历史会长期保留内容 |
| MySQL逻辑备份 | 不适合本仓库 | 需要专门的备份、权限与保留策略 |
| MongoDB转储、RDB、AOF | 不适合本仓库 | 可能很大且不是普通文本版本 |
| 运行日志 | 不适合 | 变化频繁、体积持续增长 |

Git不是“什么文件都放进去”的通用网盘。是否纳入版本控制，要考虑可审查性、体积、变化频率和保密要求。

## 3.5.3 仓库与四个位置

一个基本Git工作流可以分为四个位置：

```text
工作区 ──git add──► 暂存区 ──git commit──► 本地仓库
  ▲                    │                      │
  │ git restore        │ git restore --staged│ git push
  │                    ▼                      ▼
  └────────────── 下一次修改             远程仓库
                                             │
                                  git clone / git pull
```

### 1. 工作区

工作区是能够直接看到和编辑的文件，例如`README.md`和`scripts/server-health.sh`。

### 2. 暂存区

暂存区也叫索引，保存“下一次提交准备包含哪些内容”。执行`git add`并没有形成永久版本，只是把选中的变化加入下一次提交。

### 3. 本地仓库

执行`git commit`后，暂存内容成为带有作者、时间和说明的提交对象。提交保存在当前仓库的`.git`目录中。

### 4. 远程仓库

远程仓库是其他工作副本可以访问的仓库。实验18使用同机裸仓库模拟团队中心，不依赖GitHub。它用于练习协作流程，但因为仍位于同一台虚拟机，不能替代异机备份。

## 3.5.4 安装、身份与配置范围

查看Git版本：

```bash
git --version
```

Git提交需要作者姓名和邮箱。配置有不同作用范围：

| 范围 | 常用选项 | 影响 |
|---|---|---|
| 系统 | `--system` | 当前系统的所有用户 |
| 用户 | `--global` | 当前用户的所有仓库 |
| 仓库 | `--local` | 只影响当前仓库 |

课程实验使用本地范围，避免改变其他课程仓库：

```bash
git config --local user.name "Student Ops"
```

```bash
git config --local user.email "student@example.test"
```

查看配置来源：

```bash
git config --list --show-origin
```

姓名和邮箱用于标识提交作者，不是网站登录凭据。本地实验邮箱可以使用保留域名`example.test`。

## 3.5.5 初始化仓库

进入准备好的项目目录后初始化，并明确使用`main`作为初始分支：

```bash
git init --initial-branch=main
```

初始化会创建`.git`目录。查看隐藏目录：

```bash
ls -la
```

查看当前分支：

```bash
git branch --show-current
```

在第一次提交前，分支还没有提交对象，但分支名称已经确定。不要手工编辑`.git`内部文件。

## 3.5.6 用status读取文件状态

`git status`是每次提交、拉取和恢复前的安全起点：

```bash
git status
```

紧凑显示：

```bash
git status --short
```

短状态常见标记：

| 标记 | 含义 |
|---|---|
| `??` | 未跟踪文件 |
| ` M` | 工作区修改，尚未暂存 |
| `M ` | 修改已经暂存 |
| `MM` | 已暂存后又在工作区继续修改 |
| ` D` | 工作区删除，尚未暂存 |
| `A ` | 新文件已经暂存 |

短状态有两列。左列主要表示暂存区相对于当前提交的状态，右列主要表示工作区相对于暂存区的状态。理解两列比死记一条恢复命令更重要。

## 3.5.7 diff：提交和恢复前先看变化

查看工作区中尚未暂存的变化：

```bash
git diff
```

只查看一个文件：

```bash
git diff -- docs/service-map.md
```

查看已经进入暂存区、下一次提交将包含的变化：

```bash
git diff --cached
```

`git diff`没有输出不一定代表仓库没有变化。变化可能已经暂存，此时应查看`git diff --cached`和`git status`。

差异标记的基本含义：

- 以`-`开头的内容来自旧版本；
- 以`+`开头的内容来自新版本；
- `@@`行标识变化所在的上下文范围；
- 红色和绿色只是终端显示，不能单独作为内容判断依据。

## 3.5.8 add与精确暂存

暂存一个已经检查过的文件：

```bash
git add docs/service-map.md
```

暂存多个明确文件：

```bash
git add README.md .gitignore
```

运维目录中不建议未经检查就执行`git add .`，因为目录里可能同时存在日志、转储、临时文件和凭据。即使已经编写`.gitignore`，仍应使用`git status`和`git diff --cached`复核。

如果文件被误加入暂存区但尚未提交，可以撤销暂存：

```bash
git restore --staged docs/service-map.md
```

这条命令默认只改变暂存区，工作区中的修改仍然存在，便于继续检查或编辑。

## 3.5.9 commit：形成有意义的版本

提交暂存区内容：

```bash
git commit -m "docs: record service exposure policy"
```

一次良好提交应满足：

- 只包含同一个目的的变化；
- 提交前已经查看`git diff --cached`；
- 提交信息能说明为什么改变；
- 提交后能够完成对应验证；
- 不包含密码、私钥和运行数据。

本课程采用简洁的提交信息形式：

```text
docs: add operations handover guide
feat: add server health check
fix: correct nginx upstream port
refactor: simplify service status check
```

前缀不是Git强制语法，但统一格式有助于浏览历史。

## 3.5.10 log、show与版本标识

查看简洁历史：

```bash
git log --oneline --decorate --graph --all
```

每个提交前方有一段十六进制字符，这是提交ID的缩写。提交ID标识特定版本，不要假设不同仓库中的提交ID相同。

查看最近一次提交的统计：

```bash
git show --stat HEAD
```

查看最近一次提交的完整差异：

```bash
git show HEAD
```

查看某个历史版本中的单个文件，而不改变工作区：

```bash
git show HEAD~1:README.md
```

`HEAD`表示当前检出的提交，`HEAD~1`表示它的第一个父提交。仓库只有一次提交时，`HEAD~1`不存在。

## 3.5.11 .gitignore与敏感信息边界

`.gitignore`用规则告诉Git哪些未跟踪文件通常不应加入版本控制。

运维仓库示例：

```gitignore
.env
*.key
*.pem
*.log
*.sql
*.bson
*.rdb
*.aof
secrets/
runtime/
backup/
evidence/
```

查看某个文件由哪条规则忽略：

```bash
git check-ignore -v .env
```

查看包含已忽略文件的状态：

```bash
git status --short --ignored
```

`.gitignore`有三个重要边界：

1. 只影响尚未跟踪的文件；
2. 不能加密文件，也不能阻止有权限的人读取工作区文件；
3. 不能从历史中删除已经提交的秘密。

如果密码已经提交，应立即把它视为泄露：先更换凭据、停止继续推送，再按组织流程处理历史。只增加`.gitignore`或删除最新文件都不够。

## 3.5.12 分支与标签的基础作用

分支是一个可移动的提交引用。查看分支：

```bash
git branch --verbose
```

本课程只有2学时Git实验，以单一`main`分支完成基本协作，不展开复杂合并和变基。

标签适合标记已经验收的节点：

```bash
git tag -a linux-lab18-v1 -m "Lab 18 verified baseline"
```

查看标签：

```bash
git tag
```

标签只是版本标识，不会自动执行测试，也不会自动证明系统可用。应把标签与验收记录、测试结果和部署说明关联起来。

## 3.5.13 裸仓库与远程仓库

普通仓库包含工作区和`.git`目录；裸仓库只保存Git仓库数据，没有普通工作区，适合作为交换提交的中心。

创建以`main`为初始分支的裸仓库：

```bash
git init --bare --initial-branch=main ~/m1-project/git-server/techcorp.git
```

为当前工作仓库添加名为`origin`的远程：

```bash
git remote add origin ~/m1-project/git-server/techcorp.git
```

查看远程地址：

```bash
git remote -v
```

首次推送并建立跟踪关系：

```bash
git push -u origin main
```

推送标签需要单独执行：

```bash
git push origin linux-lab18-v1
```

实验使用本地路径模拟远程仓库，因此不会遇到网络认证。但真实Git服务器还涉及SSH或HTTPS认证、访问权限和分支保护。

## 3.5.14 clone、fetch、pull与push

| 命令 | 数据方向 | 作用 |
|---|---|---|
| `clone` | 远程→新目录 | 创建新的完整工作副本并设置远程 |
| `fetch` | 远程→本地仓库 | 获取远程对象与引用，不直接合并工作区 |
| `pull` | 远程→当前分支 | 通常先fetch，再整合远程变化 |
| `push` | 本地仓库→远程 | 发布本地提交 |

克隆仓库：

```bash
git clone ~/m1-project/git-server/techcorp.git ~/m1-project/git-review
```

查看远程分支：

```bash
git branch --all
```

在原仓库获取并只允许快进：

```bash
git pull --ff-only
```

`--ff-only`表示只有当前分支能够直接快进时才更新。如果本地和远程各自产生了新提交，Git会停止，要求管理员先理解历史，而不是自动生成未经判断的合并提交。

推送失败时，不应直接使用`--force`。先查看状态、远程和历史：

```bash
git status
```

```bash
git remote -v
```

```bash
git log --oneline --decorate --graph --all -n 10
```

## 3.5.15 根据状态选择恢复方法

恢复操作可能丢弃未提交内容，因此必须先执行`git status`和`git diff`。

### 1. 恢复未暂存的误改

先查看差异：

```bash
git diff -- docs/service-map.md
```

确认不要这项修改后，从暂存区恢复工作区文件：

```bash
git restore docs/service-map.md
```

### 2. 撤销误暂存，保留工作区修改

查看已暂存差异：

```bash
git diff --cached -- docs/service-map.md
```

撤销暂存：

```bash
git restore --staged docs/service-map.md
```

此时修改仍在工作区。可以继续编辑，也可以再次确认后执行`git restore`丢弃修改。

### 3. 恢复误删的已跟踪文件

查看删除状态：

```bash
git status --short
```

恢复文件：

```bash
git restore templates/techcorp.conf.example
```

### 4. 从指定标签恢复单个文件

先只读取历史内容：

```bash
git show linux-lab18-v1:README.md
```

确认版本正确后恢复工作区文件：

```bash
git restore --source=linux-lab18-v1 -- README.md
```

恢复后仍应通过`git diff`检查，决定是否提交这个变化。

### 5. 撤销已经共享的错误提交

已经推送的提交通常不应通过重写历史强行消失。`git revert`会创建一个反向提交，保留原有历史：

```text
git revert <需要撤销的提交ID>
```

本课程只理解其用途，不在基础实验中对共享仓库随意执行。不要使用`git reset --hard`解决所有恢复问题，它可能同时丢失工作区和提交引用。

## 3.5.16 Git与备份的区别

| 需求 | Git | 文件或数据库备份 |
|---|---|---|
| 查看文本行级差异 | 擅长 | 通常较弱 |
| 记录修改原因和作者 | 擅长 | 通常不具备 |
| 恢复已提交脚本 | 可以 | 可以 |
| 保存数据库一致性数据 | 不适合 | 应使用数据库专用工具 |
| 保存大规模运行日志 | 不适合 | 使用日志平台或归档策略 |
| 防止整机磁盘损坏 | 同机仓库不能防止 | 异机备份可以降低风险 |
| 保存秘密 | 不应使用 | 需要加密、访问控制和密钥管理 |

实验中的工作仓库、裸仓库和克隆副本都在`rocky-server`上，只能演示协作与恢复。虚拟机被还原或磁盘损坏时，它们可能一起消失，因此仍需要课程快照和独立副本。

## 3.5.17 本章练习：跟踪一份服务说明

### 任务一：建立仓库

创建目录：

```bash
mkdir -p ~/course-practice/m3/ch29
```

进入目录：

```bash
cd ~/course-practice/m3/ch29
```

初始化仓库：

```bash
git init --initial-branch=main
```

配置当前仓库作者：

```bash
git config --local user.name "Course Student"
```


### 任务二：创建并提交文件

创建文件：

```bash
vim service.conf
```

输入：

```text
service=nginx
port=80
exposure=campus-lab
```

查看未跟踪状态：

```bash
git status --short
```

暂存明确文件：

```bash
git add service.conf
```

```bash
git diff --cached
```

提交：

```bash
git commit -m "docs: add nginx service record"
```

### 任务三：模拟误改并恢复

重新编辑文件：

```bash
vim service.conf
```

把`port=80`故意改为`port=8088`并保存。

查看差异：

```bash
git diff -- service.conf
```

确认这是误改后恢复：

```bash
git restore service.conf
```

验证端口已经恢复：

```bash
grep '^port=80$' service.conf
```

确认仓库干净：

```bash
git status --short
```

## 3.5.18 本章小结

1. Git适合管理需要审查和追溯的文本资产，不适合保存秘密、运行数据库和海量日志。
2. 工作区、暂存区和本地仓库分别代表编辑内容、下一次提交内容和已提交历史。
3. `git status`是安全起点，`git diff`与`git diff --cached`分别检查未暂存和已暂存变化。
4. `.gitignore`只影响未跟踪文件，不能清除已经提交的秘密。
5. 裸仓库可以模拟团队中心，但同机裸仓库不是灾难恢复备份。
6. 恢复命令必须根据文件状态选择，恢复前先看差异和目标版本。
