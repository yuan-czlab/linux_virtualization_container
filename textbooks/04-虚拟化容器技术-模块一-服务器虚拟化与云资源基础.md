# 模块一：服务器虚拟化与云资源基础

> 适用课程：《虚拟化容器技术》  
> 对应实验：实验1—实验5｜建议学时：24学时  
> 主线环境：Windows宿主机、VMware Workstation、`rocky-server`、KVM/libvirt、教师预建OpenStack平台

## 模块导读

本模块从学生已经使用过的VMware虚拟机出发，进一步回答三个问题：虚拟机为什么能够运行、Linux服务器如何成为虚拟化宿主机、云平台如何把虚拟化资源交付给用户。学习重点不是背诵产品名称，而是建立“物理资源—虚拟化层—虚拟机—云资源管理”的完整认识，并在Linux课程保留的`rocky-server`中真实安装KVM、创建虚拟机、管理镜像和网络。`rocky-web`与`ubuntu-client`在KVM阶段通常关机，以给嵌套虚拟机释放资源。

完成本模块后，应能够：

1. 说明虚拟化、模拟、容器化和云计算之间的区别与联系。
2. 判断CPU虚拟化能力与嵌套虚拟化条件，形成环境基线记录。
3. 说明KVM、QEMU、libvirt及管理工具之间的职责关系。
4. 使用命令行完成虚拟机创建、启动、关机、删除和状态检查。
5. 使用qcow2镜像、快照和克隆完成快速交付与故障恢复。
6. 理解NAT、桥接、虚拟交换和端口访问路径，完成多机服务验证。
7. 在教师预建OpenStack平台中创建并验证一台云主机。
8. 按“先检查、再变更、留回退、做验证、存证据”的方式交付虚拟化环境。

## 本册学习方式

本册按照第1—5章顺序学习，每章按“问题背景—对象关系—工作机制—操作入口—风险边界—排障方法—思考迁移”组织。章节练习验证单个对象或关系，实验1—5再完成嵌套虚拟化、KVM平台、qcow2恢复、虚拟网络和OpenStack实例操作。

# 第1章 虚拟化技术与嵌套实验环境

## 1.1 为什么需要虚拟化

传统方式下，一项业务独占一台物理服务器。业务负载较低时，大量CPU和内存闲置；更换硬件时还需要重新安装系统和迁移应用。虚拟化在物理资源与操作系统之间增加抽象层，使一台物理机能够运行多台相互隔离的虚拟机。

虚拟化常见价值包括：

- 提高物理资源利用率；
- 缩短新服务器交付时间；
- 通过模板、快照和克隆提高环境一致性；
- 隔离不同业务或实验环境；
- 为资源池化、自动调度和云计算奠定基础。

虚拟化并不自动等于高可用或安全。单台物理宿主机故障仍可能影响其上的全部虚拟机；快照也不能替代独立备份。

## 1.2 虚拟化的基本对象

| 对象 | 含义 | 本课程实例 |
|---|---|---|
| 宿主机 | 提供CPU、内存、磁盘和网络的系统 | Windows物理机或Rocky KVM主机 |
| 虚拟机 | 获得虚拟硬件并运行完整操作系统的实例 | course-vm01 |
| Hypervisor | 创建和调度虚拟机的虚拟化层 | VMware、KVM |
| 虚拟磁盘 | 以文件或逻辑卷表示的虚拟块设备 | qcow2文件 |
| 虚拟网卡 | 提供给虚拟机的网络接口 | virtio网卡 |
| 虚拟网络 | 连接虚拟机和外部网络的逻辑网络 | libvirt default网络 |

## 1.3 Type 1与Type 2虚拟化

教材常按Hypervisor与硬件的关系进行分类：

```text
Type 1（裸机型）                 Type 2（宿主型）
应用/虚拟机                     应用/虚拟机
Hypervisor                     虚拟化软件
物理硬件                        宿主操作系统
                                物理硬件
```

生产环境中的边界可能比这张图复杂。KVM把Linux内核转变为能够运行虚拟机的Hypervisor，管理工具仍运行在Linux用户空间；VMware Workstation则安装在Windows宿主操作系统上。本课程重点是理解职责，而不是只记分类答案。

## 1.4 全虚拟化、半虚拟化与硬件辅助

- 全虚拟化让客户机看到一套完整虚拟硬件，客户机通常不需要知道自己运行在虚拟机中。
- 半虚拟化通过客户机与Hypervisor协作降低某些模拟开销。
- Intel VT-x、AMD-V等CPU扩展帮助Hypervisor高效执行客户机的特权指令。
- virtio是一组面向虚拟化环境的高性能设备接口，常用于虚拟磁盘、网卡和内存设备。

实际KVM虚拟机通常同时使用硬件辅助虚拟化与virtio设备，因此这些概念不是互相排斥的产品选项。

## 1.5 虚拟化、模拟、容器与云计算

| 技术 | 主要抽象对象 | 是否运行独立内核 | 典型用途 |
|---|---|---:|---|
| 模拟 | 指令集或完整硬件 | 是 | 跨架构运行、硬件研究 |
| 虚拟机 | 一套虚拟硬件 | 是 | 多操作系统、强隔离、传统业务 |
| 容器 | 操作系统进程与资源视图 | 否，共享宿主机内核 | 应用快速交付、微服务 |
| 云计算 | 可服务化交付的资源池 | 取决于服务 | 按需、自助、计量、弹性管理 |

云计算会使用虚拟化，但虚拟化资源池只有配合身份、网络、配额、自动化和服务接口，才具备更完整的云平台特征。

## 1.6 嵌套虚拟化

本课程环境存在两层虚拟化：

```text
Windows物理机
└── VMware中的rocky-server（第一层客户机）
    └── KVM创建的Linux虚拟机（第二层客户机）
```

要让Rocky中的KVM使用硬件虚拟化，物理CPU、主板固件、Windows虚拟化占用情况和VMware设置都必须满足条件。常见检查包括：

```bash
lscpu | grep -E 'Virtualization|Hypervisor'
grep -Eoc '(vmx|svm)' /proc/cpuinfo
lsmod | grep -E '^kvm'
```

`vmx`代表Intel虚拟化扩展，`svm`代表AMD虚拟化扩展。计数大于0说明客户机能看到相关标志，但仍需用KVM宿主验证工具做完整检查。

## 1.7 环境基线与容量意识

嵌套实验同时占用物理机、第一层Rocky和第二层客户机的资源。资源分配应遵循“满足实验、保留宿主余量”的原则：

| 层次 | 建议 |
|---|---|
| Windows物理机 | 确保有足够内存和磁盘，不把全部逻辑处理器分给VMware |
| Rocky虚拟化宿主机 | 建议4 vCPU、6—8GB内存、80GB以上磁盘 |
| 单台KVM客户机 | 1 vCPU、1—2GB内存、10—20GB磁盘即可完成基础实验 |

常用基线命令：

```bash
hostnamectl
lscpu
free -h
df -hT
ip -brief address
ip route
```

## 1.8 CPU虚拟化如何发生

操作系统内核需要执行修改页表、处理中断、访问设备等敏感操作。没有硬件辅助时，Hypervisor必须通过复杂的软件转换识别这些操作；现代Intel VT-x和AMD-V增加了客户机运行模式，使客户机大部分普通指令可以直接在物理CPU上执行，遇到需要Hypervisor处理的事件时再退出客户机。

一次简化的执行过程如下：

```text
客户机普通应用指令
→ 直接使用物理CPU执行
→ 客户机执行敏感操作或发生外部事件
→ VM Exit退出到Hypervisor
→ Hypervisor检查并模拟、拒绝或完成操作
→ VM Entry返回客户机继续执行
```

VM Exit不是错误，但频繁退出会带来开销。虚拟设备类型、中断方式、定时器和工作负载都会影响退出次数。因此虚拟化性能不是简单由“给了几个vCPU”决定。

### vCPU与物理CPU

vCPU是Hypervisor交给客户机的可调度处理器。多个vCPU最终由宿主机Linux调度到物理逻辑处理器上：

```text
客户机进程
→ 客户机内核调度到vCPU
→ QEMU/KVM线程
→ 宿主机内核调度到物理CPU
```

为虚拟机分配8个vCPU，并不意味着它独占8个物理核心。vCPU数量超过宿主机可用能力时会发生等待和竞争。教学机同时运行Windows、VMware、Rocky和KVM客户机，更应避免过度分配。

## 1.9 内存虚拟化

客户机看到的是客户机物理地址，真正内存由宿主机管理。现代CPU通过EPT或NPT等二级地址转换协助完成“客户机虚拟地址—客户机物理地址—宿主机物理地址”的映射。

```text
客户机虚拟地址
→ 客户机页表
→ 客户机物理地址
→ EPT/NPT二级转换
→ 宿主机物理地址
```

虚拟机定义中的内存是可用上限或启动配置，实际宿主机还要承担QEMU进程、页表、缓存和设备模型开销。生产环境可能使用内存超分、气球设备、大页和NUMA优化；本课程只要求理解资源不能凭空产生，并能从宿主机与客户机两侧检查内存。

## 1.10 I/O虚拟化与virtio

客户机需要磁盘、网卡、控制台和随机数等设备。完全模拟真实硬件兼容性好，但每次设备访问都可能需要较多模拟。virtio让客户机使用面向虚拟化的驱动与Hypervisor交换数据，通常比模拟旧式硬件效率更高。

| 设备 | 常见virtio形式 | 作用 |
|---|---|---|
| 磁盘 | virtio-blk、virtio-scsi | 提供虚拟块设备 |
| 网卡 | virtio-net | 提供高效虚拟网络接口 |
| 内存 | virtio-balloon | 协助调整客户机可用内存 |
| 控制台 | virtio-console | 提供客户机控制通道 |
| 随机数 | virtio-rng | 向客户机提供熵来源 |

使用virtio通常要求客户机系统包含相应驱动。教师基础镜像必须提前验证驱动和启动方式，不能只确认镜像文件存在。

### 本章小结

虚拟化把物理资源抽象为可独立分配的虚拟硬件；嵌套虚拟化使学生能够在现有VMware实验环境中继续学习KVM。实验开始前必须验证硬件能力、软件设置与资源余量，不能把“命令执行过”误当成“环境可用”。

### 思考与练习

1. 为什么快照不能替代独立备份？
2. 为什么容器通常比虚拟机启动更快？
3. 如果Rocky虚拟机看不到`vmx`或`svm`，应从哪几个层次排查？

# 第2章 KVM、QEMU与libvirt虚拟机管理

## 2.1 KVM技术栈

KVM环境不是一个单独程序，而是多个组件协作：

```text
virsh / virt-install / 管理界面
              ↓
           libvirt
              ↓
        QEMU虚拟机进程
              ↓
       KVM内核模块与Linux内核
              ↓
 CPU / 内存 / 存储 / 网络
```

| 组件 | 主要职责 |
|---|---|
| KVM | 通过内核模块提供硬件辅助虚拟化能力 |
| QEMU | 提供虚拟机进程、设备模型和模拟能力 |
| libvirt | 用统一接口管理虚拟机、存储和网络 |
| virsh | libvirt命令行管理工具 |
| virt-install | 以命令方式创建和安装虚拟机 |
| qemu-img | 创建、转换和检查虚拟磁盘镜像 |

## 2.2 安装与能力验证

Rocky Linux中的典型安装对象包括KVM、libvirt和虚拟机创建工具。具体软件包及服务单元以实验手册和机房镜像为准。安装后需要从三个角度验证：

```bash
# CPU和宿主条件
virt-host-validate

# 内核模块
lsmod | grep kvm

# libvirt连接与对象
sudo virsh uri
sudo virsh list --all
```

如果`virt-host-validate`提示硬件虚拟化失败，不应直接反复安装软件包，应返回上一层检查VMware的嵌套虚拟化设置。

## 2.3 libvirt连接与权限

`virsh`可以连接不同libvirt URI。教学中常用系统级QEMU连接：

```bash
sudo virsh -c qemu:///system list --all
```

系统级连接的虚拟机、网络和存储池由系统服务管理，通常需要管理员权限。不要在不了解URI差异时混用普通用户的`qemu:///session`与系统的`qemu:///system`，否则容易出现“创建过但列表中看不到”的现象。

## 2.4 虚拟机定义与运行实例

libvirt使用XML保存虚拟机定义，定义中包含名称、内存、vCPU、磁盘、网卡和启动方式。定义存在不代表虚拟机正在运行：

```bash
sudo virsh list --all
sudo virsh dominfo course-vm01
sudo virsh dumpxml course-vm01
```

常见生命周期操作：

```bash
sudo virsh start course-vm01
sudo virsh reboot course-vm01
sudo virsh shutdown course-vm01
sudo virsh destroy course-vm01
sudo virsh autostart course-vm01
sudo virsh autostart --disable course-vm01
```

`shutdown`向客户机请求正常关机，需要客户机配合；`destroy`相当于强制断电，可能导致文件系统或业务数据损坏，只用于明确的故障处置。

## 2.5 创建虚拟机的两条路径

第一条路径是从ISO安装，适合学习完整安装过程；第二条路径是导入教师提供的基础镜像，适合课堂快速交付。导入已有磁盘时通常使用`virt-install --import`，但具体磁盘路径、网络和控制台参数应以实验手册为准。

创建前要先回答：

- 虚拟机名称是否唯一？
- 内存和vCPU是否超出宿主余量？
- 磁盘是复制得到还是直接引用共享基础镜像？
- 网卡连接到哪个网络？
- 是否能够通过控制台或SSH登录？
- 删除定义时是否会误删仍需保留的磁盘？

## 2.6 控制台、客户机代理与地址发现

当网络尚未配置时，串口或图形控制台是关键管理通道。网络正常后可使用SSH。常用观察命令：

```bash
sudo virsh console course-vm01
sudo virsh domiflist course-vm01
sudo virsh domifaddr course-vm01
sudo virsh domblklist course-vm01
```

`domifaddr`能否显示地址取决于地址来源、网络类型和客户机代理。查不到地址不等于虚拟机没有地址，可结合DHCP租约、客户机控制台和虚拟网卡MAC继续判断。

## 2.7 标准排障链

```text
虚拟机不工作
├── 定义是否存在：virsh list --all / dominfo
├── QEMU进程能否启动：virsh start
├── 日志说明什么：journalctl / libvirt日志
├── 磁盘是否存在且格式正确：domblklist / qemu-img info
├── 网络是否连接：domiflist / net-list
└── 客户机内部是否完成启动：console / SSH
```

不要先删除虚拟机。保留现场、记录报错、检查依赖，再做最小修改。

## 2.8 libvirt对象模型

libvirt不只管理虚拟机。理解对象关系后，才能判断一个报错属于计算、磁盘还是网络：

```text
libvirt连接URI
├── Domain：虚拟机定义和运行实例
├── Network：虚拟网络、DHCP与转发
├── Storage Pool：一组可管理存储位置
│   └── Volume：虚拟磁盘或存储对象
├── Interface：宿主机网络接口
├── Secret：受控保存的认证信息
└── Node Device：宿主机设备
```

课堂主要操作Domain、Network以及qcow2文件。即使暂时不使用存储池命令，也要理解`/var/lib/libvirt/images`中的文件和虚拟机定义不是同一个对象：删除定义未必删除磁盘，删除磁盘也不会自动清除定义。

## 2.9 Domain XML关键字段

一份虚拟机XML大致包含：

| 区域 | 关键信息 | 排障意义 |
|---|---|---|
| `name`、`uuid` | 身份 | 名称冲突、克隆唯一性 |
| `memory`、`vcpu` | 资源 | 启动失败、资源不足 |
| `os` | 固件和启动顺序 | BIOS/UEFI、磁盘无法启动 |
| `features`、`cpu` | CPU与平台特性 | 嵌套虚拟化、兼容性 |
| `disk` | 驱动、格式、源文件、目标总线 | 文件不存在、格式或权限错误 |
| `interface` | MAC、网络源、设备模型 | 无地址、网络接错 |
| `console` | 串口或控制台 | 网络故障时登录 |

修改XML前先导出备份：

```bash
sudo virsh dumpxml course-vm01 > course-vm01.xml.backup
```

`virsh edit`会在保存时检查基本XML，但不能证明磁盘、网络和客户机配置一定有效。修改后仍要启动并完成登录验证。

## 2.10 持久配置与实时配置

虚拟机可能同时拥有持久定义和当前运行状态。有些`virsh`操作只影响当前运行实例，有些影响下次启动，也有参数允许同时修改。看到“命令成功”后，应确认变化是在当前实例、持久定义还是两者中生效。

例如调整资源时应分别检查：

```bash
sudo virsh dominfo course-vm01
sudo virsh dumpxml course-vm01
```

本课程不要求在线热调整复杂资源，但必须建立“live与config并非同一层”的意识，避免重启后配置恢复原状。

## 2.11 模板、首次启动与cloud-init

手工克隆后逐台修改主机名、用户、密钥和网络，规模稍大就容易出错。云环境常把只读基础镜像与首次启动配置结合：

```text
通用基础镜像
+ 实例专属元数据/用户数据
→ 首次启动初始化
→ 唯一主机名、用户、公钥和网络
```

cloud-init是常见初始化工具，可读取云平台或配置盘提供的数据。示例能力包括创建用户、注入SSH公钥、设置主机名和执行一次性初始化命令。本课程不要求编写复杂cloud-init配置，但OpenStack实验中“密钥对为什么能进入新实例”与这一机制有关。

模板应满足：系统已更新到课程基线、无个人密码和私钥、machine-id等唯一数据可以重新生成、磁盘能够扩展、控制台和网络驱动可用、版本与校验值可追溯。

### 本章小结

KVM提供内核虚拟化能力，QEMU运行虚拟机并提供设备模型，libvirt统一管理对象。虚拟机交付必须同时验证定义、运行状态、控制台或网络登录以及关机回退能力。

# 第3章 qcow2镜像、快照、克隆与恢复

## 3.1 虚拟磁盘格式

KVM常见磁盘格式包括raw与qcow2：

| 对比项 | raw | qcow2 |
|---|---|---|
| 结构 | 接近原始块设备 | 带元数据的QEMU写时复制格式 |
| 空间 | 可预分配，也可稀疏 | 支持按需增长 |
| 快照 | 依赖外部方案 | 支持内部或外部快照能力 |
| 功能 | 简单、开销较低 | 后备文件、压缩等功能更丰富 |

查看镜像信息：

```bash
qemu-img info /var/lib/libvirt/images/course-vm01.qcow2
```

“虚拟大小”是客户机看到的容量，“磁盘实际占用”是当前在宿主机使用的空间，两者可能不同。

## 3.2 写时复制与后备链

qcow2可以让新镜像引用只读基础镜像，新增写入保存到覆盖层：

```text
course-base.qcow2（基础镜像，不修改）
├── vm01-overlay.qcow2（保存vm01差异）
└── vm02-overlay.qcow2（保存vm02差异）
```

优点是创建快、节省空间；风险是覆盖层依赖后备文件。移动、改名或损坏基础镜像会使多个客户机同时失效。因此必须记录后备链并保护基础镜像。

## 3.3 镜像复制与校验

教师下发的基础镜像应带固定文件名、版本和SHA-256校验值。学生先验证再复制：

```bash
sha256sum course-base.qcow2
qemu-img info course-base.qcow2
```

校验和用于发现传输损坏或文件版本不一致，不等同于恶意代码安全审计。不要直接让多台虚拟机以可写方式共用同一个基础磁盘。

## 3.4 快照的用途和边界

快照记录某一时刻的磁盘状态，适合教学实验前创建回退点。按实现可分为内部快照和外部快照；按一致性可讨论崩溃一致与应用一致。

- 崩溃一致快照类似突然断电后的磁盘状态，文件系统通常能恢复，但应用缓存中的数据可能丢失。
- 应用一致快照会协调数据库或应用完成刷盘、冻结或备份，恢复质量更高。

常用查看操作：

```bash
sudo virsh snapshot-list course-vm01
sudo virsh snapshot-info course-vm01 --snapshotname before-change
```

快照与原虚拟机通常位于同一宿主机或同一存储故障域。源磁盘损坏时，快照也可能不可用，因此快照不是备份。

## 3.5 克隆后的唯一性

克隆不仅是复制磁盘。新虚拟机至少需要检查：

- libvirt虚拟机名称和UUID；
- 虚拟网卡MAC地址；
- 客户机主机名；
- DHCP租约或静态IP；
- `/etc/machine-id`；
- SSH主机密钥；
- 应用实例标识与日志归属。

如果两个克隆拥有相同网络身份或系统标识，会造成地址冲突、安全告警和自动化系统误判。模板制作应清理或在首次启动时重新生成唯一信息。

## 3.6 备份与恢复闭环

可靠的镜像备份至少包含：

```text
虚拟机配置XML
+ 虚拟磁盘或可重建的镜像链
+ 文件校验值
+ 版本与时间记录
+ 恢复步骤
+ 恢复验证结果
```

只复制正在高速写入的虚拟磁盘，可能得到不一致副本。课堂中应在关机或明确协调后备份；生产环境则需选择存储快照、客户机代理或应用备份方案。

## 3.7 容量与链路排查

```bash
df -hT
du -sh /var/lib/libvirt/images/*
qemu-img info --backing-chain vm01-overlay.qcow2
sudo virsh domblklist course-vm01
```

排查顺序是：确认虚拟机实际引用哪个磁盘，再确认磁盘格式与后备链，最后检查宿主机空间和权限。不要仅凭文件名推断关系。

## 3.8 qcow2按需分配的含义

qcow2把虚拟磁盘划分为可管理的数据区域，并维护从客户机逻辑块到宿主文件位置的映射。新建一个20GB qcow2文件时，宿主机可能只占很小空间；客户机不断写入后，实际占用才增加。

删除客户机文件不一定立即缩小宿主qcow2文件，因为客户机文件系统释放空间与镜像回收空间是两个层次。判断容量时要同时看：

```text
宿主文件系统剩余空间
→ qcow2文件实际占用
→ qcow2虚拟容量
→ 客户机文件系统使用量
```

基础教学阶段不要在唯一镜像上尝试不熟悉的压缩、缩减或修复操作。先复制镜像，在副本上验证。

## 3.9 快照、克隆与备份决策

| 需求 | 更合适的手段 | 原因 |
|---|---|---|
| 配置实验前快速回退 | 快照 | 创建和回退快，但仍依赖原存储 |
| 从统一模板创建多台虚拟机 | 克隆或覆盖层 | 快速生成独立实例 |
| 宿主机损坏后恢复 | 独立备份 | 副本位于不同故障域 |
| 跨平台长期归档 | 磁盘、XML、校验和与恢复文档 | 同时保存数据和重建信息 |
| 数据库一致性恢复 | 应用级备份配合镜像备份 | 仅磁盘状态不能保证业务一致 |

同一个动作可能组合使用。例如在关机状态下导出XML、复制磁盘并计算校验和，这是面向恢复的归档；在改配置前创建内部快照，则是短期回退点。

## 3.10 镜像链的安全变更原则

1. 先用`domblklist`确认虚拟机实际磁盘。
2. 再用`qemu-img info --backing-chain`确认依赖。
3. 记录虚拟机是否运行以及数据一致性要求。
4. 对基础镜像和关键覆盖层建立独立副本。
5. 只对明确副本执行转换、合并或修复实验。
6. 完成后不仅检查镜像结构，还要启动客户机并验证网络、文件和服务。

`qemu-img check`等工具可以检查镜像结构，但修复参数可能改变数据。发现损坏时先保留原文件，不在唯一副本上直接尝试修复。

### 本章小结

qcow2为教学环境提供按需增长、快照和后备文件等能力，但同时引入镜像链依赖。模板、快照、克隆和备份是四个不同概念，交付时必须同时管理唯一性、完整性和可恢复性。

# 第4章 KVM虚拟网络与服务访问

## 4.1 虚拟网络的组成

一条从客户机到外部网络的访问路径可能经过：

```text
客户机应用
→ 客户机虚拟网卡
→ tap接口
→ Linux网桥
→ 宿主机转发/NAT或物理网卡
→ 目标网络
```

每一层都有地址、链路状态、路由和防火墙，因此“能ping通”或“网卡是UP”都只能证明链路的一部分。

## 4.2 libvirt NAT网络

libvirt的默认网络通常提供私有网段、DHCP、DNS转发和NAT。客户机能够主动访问外部网络，但外部主机通常不能直接访问客户机私有地址。

```bash
sudo virsh net-list --all
sudo virsh net-info default
sudo virsh net-dumpxml default
sudo virsh net-dhcp-leases default
```

网络对象与虚拟机对象独立：网络未启动时，即使虚拟机定义中的网卡仍引用它，客户机也无法正常接入。

## 4.3 桥接网络

桥接可让虚拟机通过宿主机桥接到上游二层网络，看起来像网络中的独立主机。桥接是否可用取决于机房交换网络、无线网卡限制、安全策略和地址分配方式。在教学机房不应为了展示概念擅自改动上联网络；本课程以libvirt NAT网络完成必做实验，桥接作为拓展理解。

## 4.4 地址、路由、DNS与端口

客户机内部的基本检查链：

```bash
ip -brief link
ip -brief address
ip route
cat /etc/resolv.conf
ping -c 3 网关地址
getent hosts 目标域名
ss -tlnp
```

宿主机侧还需检查虚拟机网卡与网络对象：

```bash
sudo virsh domiflist course-vm01
sudo virsh net-list --all
sudo virsh net-dhcp-leases default
```

## 4.5 服务验证必须跨层

以HTTP服务为例，完整证据链包括：

1. 服务进程已启动；
2. 服务器内部有端口监听；
3. 本机能够访问；
4. 同一虚拟网络中的另一台虚拟机能够访问；
5. 页面内容或API响应正确；
6. 服务日志记录了远端请求。

```bash
systemctl status 服务名
ss -tlnp
curl --fail http://127.0.0.1:端口/
curl --fail http://服务器地址:端口/
journalctl -u 服务名 -n 30
```

## 4.6 故障注入与恢复

教学中的网络故障注入必须满足三个条件：范围明确、能够回退、恢复后重新验证。可以暂时断开某台实验虚拟机的虚拟网卡，观察现象并恢复，而不应修改机房物理网络。

标准记录表：

| 阶段 | 应记录内容 |
|---|---|
| 正常基线 | 地址、路由、网卡、服务响应 |
| 故障操作 | 改了哪个对象、何时修改 |
| 故障现象 | 哪一层失败、原始错误信息 |
| 定位依据 | 使用的命令、日志或对照结果 |
| 恢复操作 | 如何恢复原状态 |
| 恢复验证 | 原验证链是否全部重新通过 |

## 4.7 tap、网桥与数据帧路径

QEMU为虚拟机网卡连接一个宿主机侧接口，常见形式是tap。tap像一根从虚拟机伸到宿主机网络栈的虚拟网线，Linux网桥则像软件交换机，把多个接口连接在同一二层网络中。

```text
客户机eth0
↕ virtio-net
QEMU/tap接口
↕
virbr0软件网桥
├── 另一台虚拟机tap
└── 宿主机IP、DHCP/DNS及NAT转发
```

虚拟机网卡在客户机中显示UP，只证明客户机侧接口启用；tap可能断开、网桥可能未启动、libvirt网络可能无DHCP，外部访问仍会失败。

## 4.8 NAT、桥接与路由模式对比

| 模式 | 客户机地址来源 | 外部主动访问 | 适用场景 | 主要风险或限制 |
|---|---|---|---|---|
| NAT | 私有网段DHCP或静态地址 | 通常需端口转发 | 教学、开发、普通出网 | 外部不能直接到达客户机 |
| 桥接 | 上游网络分配 | 可能直接访问 | 需要虚拟机成为局域网主机 | 受机房网络、无线和安全策略限制 |
| 路由 | 独立子网并配置路由 | 由路由策略决定 | 数据中心受控网段 | 需要上游路由和防火墙配合 |
| 隔离网络 | 私有地址 | 不允许 | 恶意样本、后端隔离、内部测试 | 无法直接访问外部依赖 |

模式选择不是越开放越好，而是由访问方向、地址规划、隔离需求和机房权限共同决定。

## 4.9 DHCP、MAC与地址稳定性

DHCP通常根据虚拟网卡MAC识别客户端。克隆时如果MAC重复，可能发生租约冲突；MAC改变后，客户机地址也可能改变。需要稳定管理地址时，可以在libvirt网络中配置DHCP保留，或在客户机内设置静态地址，但两者都必须避免落入DHCP动态分配范围造成冲突。

排障时建立对应表：

| 虚拟机 | libvirt名称 | 网卡MAC | 客户机接口 | IP地址 | 网络对象 |
|---|---|---|---|---|---|
| course-vm01 | course-vm01 | 实际值 | eth0或ens3 | 实际值 | default |

## 4.10 四层与七层验证

ICMP通只表示基本IP路径可用；TCP连接成功说明目标端口能够建立连接；HTTP状态和内容正确才说明应用层达到预期。常用验证层次：

```text
链路：ip link
→ 地址：ip address
→ 路由：ip route
→ 邻居：ip neigh
→ IP：ping
→ TCP：nc或curl连接
→ HTTP：状态码、响应体
→ 应用：业务数据
→ 日志：服务端记录
```

遵循此顺序可以缩小故障范围。直接从“网页打不开”跳到重装Nginx，会丢失大量定位信息。

### 本章小结

虚拟网络不是一个“联网开关”，而是一条由虚拟网卡、tap、网桥、转发、地址、路由和防火墙组成的路径。排障要由近到远、由链路到应用，最终以真实服务响应证明交付成功。

2. 两台客户机能够互相ping通，但HTTP访问失败，接下来应查什么？
3. 故障恢复后为什么必须重复原验收步骤？

# 第5章 OpenStack云主机与模块综合交付

## 5.1 从KVM到OpenStack

在单台KVM主机上，管理员直接操作虚拟机、镜像和网络。当规模扩大后，还需要解决多宿主机调度、租户隔离、配额、身份、网络服务、自助申请和统一接口。OpenStack把计算、网络、镜像、身份等能力组织为云平台服务。

本课程只要求使用教师预建平台完成用户侧资源操作，不部署OpenStack。部署与集群管理会在后续《云计算应用》课程继续学习。

## 5.2 用户视角的核心对象

| OpenStack对象 | 作用 | 与KVM实验的联系 |
|---|---|---|
| Project | 隔离用户资源和配额 | 一组课程实验资源 |
| Image | 创建实例的系统模板 | qcow2基础镜像 |
| Flavor | 规定vCPU、内存和磁盘规格 | 虚拟机资源参数 |
| Network/Subnet | 提供实例网络 | libvirt虚拟网络 |
| Security Group | 控制进入或离开实例的流量 | 分布式虚拟防火墙规则 |
| Key Pair | 注入登录公钥 | SSH密钥认证 |
| Instance | 用户获得的云主机 | KVM虚拟机实例 |

## 5.3 创建云主机的依赖关系

```text
身份与项目权限
├── 配额
├── 镜像
├── 规格
├── 网络/子网
├── 安全组规则
└── 密钥对
        ↓
      实例
        ↓
 地址 + SSH + 服务验证
```

实例创建失败时，应先看平台事件和状态，再检查配额、镜像、网络和调度条件。实例显示`ACTIVE`只代表云平台认为计算实例已运行，仍需验证地址、端口、登录和客户机内部服务。

## 5.4 安全组与最小开放

安全组规则应围绕业务需求配置。SSH实验只开放TCP 22，并优先限制来源地址；不应为了省事开放全部协议和全部来源。安全组、客户机防火墙和应用监听共同决定访问结果：

```text
客户端
→ 平台网络路径
→ 安全组
→ 客户机防火墙
→ 应用监听地址与端口
```

任意一层不满足条件都会导致访问失败。

## 5.5 密钥对与登录

平台保存公钥，用户妥善保管私钥。私钥文件应限制权限，不放入公开仓库，不在报告中粘贴完整内容。常见命令形式：

```bash
chmod 600 私钥文件
ssh -i 私钥文件 镜像默认用户@实例地址
```

不同镜像的默认用户可能不同，应以教师发布的镜像清单为准。

## 5.6 资源配额与回收

云资源是有限、可计量的。实验结束后按依赖关系回收临时实例、安全组和密钥记录，但应先保存报告证据。删除云主机通常不可恢复，必须确认名称、项目和提交要求。

## 5.9 OpenStack主要服务关系

OpenStack由可组合服务构成，不是单一进程。用户体验实验涉及的主要服务包括：

| 服务 | 常见项目名 | 核心职责 |
|---|---|---|
| 身份服务 | Keystone | 用户、项目、角色、令牌和服务目录 |
| 镜像服务 | Glance | 保存和提供云主机镜像 |
| 计算服务 | Nova | 实例生命周期、调度和计算节点协作 |
| 网络服务 | Neutron | 网络、子网、端口、地址与安全组 |
| 块存储 | Cinder | 向实例提供可挂载卷 |
| Web界面 | Horizon | 调用各服务API提供用户界面 |

底层计算节点可使用KVM运行实例，但用户通常不直接登录计算节点执行`virsh`。云平台通过服务API、数据库、消息和代理协作完成调度与配置。

## 5.10 创建实例背后的流程

从用户点击“创建实例”到能够SSH，大致经历：

```text
Keystone验证身份和项目权限
→ Nova检查请求与配额
→ 调度器选择满足资源条件的计算节点
→ Glance提供镜像
→ Neutron创建端口并配置网络与安全组
→ 计算节点通过Hypervisor创建实例
→ 注入元数据或SSH公钥
→ 实例启动并获得地址
→ 用户从允许的网络路径连接
```

不同部署会增加卷、浮动IP和高可用组件。这个流程帮助判断错误来源：配额不足、镜像不可用、无可用主机、网络端口异常和客户机启动失败不是同一类问题。

## 5.11 镜像、临时磁盘与云硬盘

镜像是创建实例的模板，实例系统盘可能是计算节点上的临时磁盘，也可能由块存储卷提供。删除实例时，临时系统盘通常随实例删除；独立云硬盘是否保留由创建方式和删除选项决定。

因此创建和删除前要回答：

- 数据写在实例临时磁盘还是独立卷？
- 删除实例是否同时删除启动卷？
- 备份是镜像快照、卷快照还是应用备份？
- 重新创建实例后如何恢复身份、网络和业务数据？

## 5.12 配额与调度不是同一个概念

配额规定项目最多能够申请多少资源；调度判断当前是否存在满足条件的实际位置。项目仍有vCPU配额，不代表某个计算节点一定有足够连续内存；规格合法，也不代表镜像、网络和可用域组合一定可调度。

用户侧排障应记录实例状态、Fault信息、操作事件和所选对象，再向平台管理员提供可复现请求。不要连续创建多个同名实例加剧资源占用。

## 5.13 云平台使用者的交付责任

平台负责提供资源能力，但使用者仍负责客户机内部操作系统、账号、公钥、服务配置、数据和补丁。安全组开放22端口后，SSH服务仍可能未启动；平台实例状态正常后，应用仍可能故障。这种责任边界是后续云计算和企业运维课程的重要基础。

### 本章小结

OpenStack不是“另一种虚拟机软件”，而是把计算、镜像、网络、身份和配额组织成云服务。学生通过预建平台完成一次真实云主机生命周期，重点理解对象依赖、自助交付、安全开放和资源回收。

### 模块综合问题

1. 将KVM虚拟机对象与OpenStack用户对象逐项对应，并说明不能完全等同的地方。
2. 一台OpenStack实例状态为`ACTIVE`但SSH超时，列出由外到内的排查顺序。
3. 为一套可重复使用的KVM教学环境设计“基础镜像—克隆—快照—备份”策略。
4. 解释为什么本课程在`rocky-server`中真实运行KVM，却不要求学生部署OpenStack。
