# 模块三：企业服务部署与综合运维

> 适用课程：《Linux操作系统》  
> 对应实验：实验14—实验20｜建议学时：24学时  
> 主线环境：Rocky Linux 9服务器｜Ubuntu Server 22.04客户端  
> 核心服务：Nginx、MySQL 8.4 LTS、MongoDB 8.0、Redis

开始本模块前，应已完成模块一、模块二，具备命令行、权限、软件包、systemd、日志、网络、SSH、firewalld、SELinux和备份基础，并保留Rocky服务器与Ubuntu客户端可回退的虚拟机快照。服务部署在Rocky中完成，Ubuntu作为正式外部客户端验证名称解析、端口、HTTP、SSH和按需开放的数据库连接；Windows宿主机只承担VMware控制台和可选图形展示。

## 模块导读

本模块把前两模块的系统管理能力放入真实服务场景。学生不只要“装上软件”，还要回答五个问题：

1. 服务是否由正确进程运行？
2. 端口监听在什么地址，谁能够连接？
3. 客户端能否完成认证和最小业务操作？
4. 数据和配置能否备份、恢复和追溯？
5. 出现故障时，能否用证据定位到正确层次？

完成本模块后，应能够：

1. 部署Nginx静态站点、健康检查和反向代理。
2. 部署MySQL，创建最小权限用户并完成逻辑备份恢复。
3. 部署MongoDB，理解文档模型、认证数据库和基于角色的访问控制。
4. 部署Redis，完成键值操作、认证、监听和持久化检查。
5. 使用Git保存脱敏运维资料，完成克隆、同步和误改恢复。
6. 使用Bash编写只读巡检脚本，以输出和退出码表达结果。
7. 综合使用systemd、journal、端口、防火墙、SELinux和应用验证排查故障。
8. 交付一台有安全边界、有备份、有版本、有验收证据的Linux服务器。

## 统一安全规则

- 官方仓库和课程镜像只能选择一种来源，避免同一软件混装不同仓库的软件包。
- 密码通过交互式提示输入，不写入Shell历史、截图、脚本和Git。
- 修改配置先备份，修改后先做语法检查，再reload或restart。
- 数据库默认仅本机监听；确需远程访问时同时限制监听、防火墙来源和账号授权范围。
- 不用关闭firewalld、关闭SELinux、`chmod 777`或取消认证解决问题。
- active只是进程状态，必须继续验证端口、认证和业务操作。
- 备份文件存在不代表可恢复，至少完成内容检查和受控恢复验证。

# 第25章 Nginx Web服务

## 25.1 Nginx在服务器中的位置

Nginx是事件驱动的Web服务器和反向代理。入门课程中最常见的三种用途是直接返回静态文件、提供健康检查、把特定路径转发给后端应用。

```text
浏览器 --HTTP--> Nginx
                  ├── /            → /srv/techcorp/www/index.html
                  ├── /health      → Nginx直接返回200
                  └── /api/...     → http://127.0.0.1:5000/...
```

反向代理隐藏了后端的直接地址。访问者只接触Nginx，后端可以只监听回环地址，从而缩小暴露面。

## 25.2 HTTP请求、响应与状态码

一个请求包含方法、路径、协议版本和请求头；响应包含状态码、响应头和响应体。HTTP返回错误页时，TCP连接可能已经成功，因此“端口通”不能证明页面正确。

| 状态码 | 含义 | 运维判断 |
|---:|---|---|
| 200 | 请求成功 | 仍需确认内容是否正确 |
| 301/302 | 重定向 | 检查Location和是否形成循环 |
| 403 | 拒绝访问 | 检查路径权限、SELinux、访问规则 |
| 404 | 资源不存在 | 检查URI与root/alias映射 |
| 502 | 上游响应失败 | 检查后端服务、端口、协议和SELinux |
| 504 | 上游超时 | 检查后端性能、网络和超时设置 |

## 25.3 配置层次与虚拟主机

Rocky/RHEL系常见路径如下，实际路径以安装包为准：

```text
/etc/nginx/nginx.conf
/etc/nginx/conf.d/*.conf
/usr/share/nginx/html/
/var/log/nginx/access.log
/var/log/nginx/error.log
```

简化配置：

```nginx
server {
    listen 80;
    server_name _;
    root /srv/techcorp/www;
    index index.html;

    location = /health {
        default_type text/plain;
        return 200 "ok\n";
    }
}
```

- `server`定义一个虚拟主机。
- `listen`指定监听端口和可选地址。
- `server_name`匹配Host请求头。
- `root`决定静态文件根目录。
- `location`按URI选择处理规则。

每条普通指令通常以分号结束。括号、分号和包含文件错误都可能导致reload失败。

## 25.4 URI、root与文件路径

若`location /images/`中的`root`为`/srv/techcorp/www`，访问`/images/logo.png`通常映射到`/srv/techcorp/www/images/logo.png`。排查404时应记录请求URI、匹配的location、root或alias以及最终文件路径。

## 25.5 反向代理

```nginx
location /api/ {
    proxy_pass http://127.0.0.1:5000/;
    proxy_set_header Host $host;
    proxy_set_header X-Real-IP $remote_addr;
}
```

`proxy_pass`末尾斜杠会影响URI拼接。上例中访问`/api/health.json`时，后端收到`/health.json`。代理头用于传递原始主机、地址和协议，但应用只能信任由可信代理写入的头。

## 25.6 安全变更流程

```text
检查当前状态 → 备份 → 小范围编辑 → nginx -t
→ reload → curl实际URL → 检查日志 → 保存证据或回退
```

```bash
sudo nginx -t
sudo nginx -T
systemctl status nginx
sudo ss -lntp | grep ':80'
curl -i http://127.0.0.1/health
sudo journalctl -u nginx -n 50 --no-pager
```

`reload`通常比`restart`对现有连接影响更小，但语法正确不等于业务正确，必须继续发起请求。

## 25.7 Unix权限与SELinux

Nginx读取非标准目录需要路径遍历权限、文件读取权限和正确SELinux类型：

```bash
sudo semanage fcontext -a -t httpd_sys_content_t '/srv/techcorp/www(/.*)?'
sudo restorecon -Rv /srv/techcorp/www
```

反向代理连接网络后端通常还涉及`httpd_can_network_connect`布尔值。遇到502时应检查AVC证据，不直接关闭SELinux。

## 25.8 分层排障

| 层次 | 主要证据 |
|---|---|
| 配置 | `nginx -t/-T` |
| 进程 | `systemctl`、journal |
| Socket | `ss`检查80与后端端口 |
| 本机HTTP | `curl 127.0.0.1` |
| 后端 | 直接curl后端地址 |
| 文件权限 | `namei -l`、`ls -l` |
| SELinux | `ls -Z`、`ausearch` |
| 网络边界 | `firewall-cmd`、客户端curl |

# 第26章 MySQL数据库服务

## 26.1 关系型数据模型

MySQL把数据组织为数据库、表、行和列。表结构约束字段类型，主键唯一标识一行，索引帮助查询。它适合结构相对稳定、需要关联查询和事务一致性的业务数据。本课程重点是部署、授权、备份和排障，不展开复杂SQL开发。

```text
MySQL实例
└── company_db
    └── employees
        ├── id 主键
        ├── name
        └── department
```

## 26.2 服务组件

| 对象 | 常见名称 | 作用 |
|---|---|---|
| 服务进程 | `mysqld` | 接收连接、执行SQL、管理数据 |
| 客户端 | `mysql` | 交互式连接与执行SQL |
| 备份工具 | `mysqldump` | 生成逻辑备份 |
| 主配置 | `/etc/my.cnf` | 加载全局配置和包含目录 |
| 数据目录 | `/var/lib/mysql` | 保存表和系统数据 |
| 默认端口 | TCP 3306 | 客户端连接入口 |

运行中的数据库文件不能简单复制后就宣称备份可恢复。本课程以逻辑备份为主。

## 26.3 首次启动

使用MySQL官方RPM包时，首次启动通常完成初始化，并在日志中生成root临时密码：

```bash
sudo systemctl enable --now mysqld
systemctl is-active mysqld
sudo ss -lntp | grep ':3306'
sudo grep 'temporary password' /var/log/mysqld.log
```

临时密码属于秘密，不复制到公开报告；首次登录后设置符合课程策略的新密码。

## 26.4 SQL最小验证

```sql
CREATE DATABASE company_db CHARACTER SET utf8mb4;
USE company_db;
CREATE TABLE employees (
    id INT PRIMARY KEY AUTO_INCREMENT,
    name VARCHAR(50) NOT NULL,
    department VARCHAR(50) NOT NULL
);
INSERT INTO employees(name, department)
VALUES ('Zhang San', 'IT'), ('Li Si', 'OPS');
SELECT * FROM employees;
```

验收至少包含认证、选择业务库、查询和一次受控写入。应用操作不应长期使用root。

## 26.5 账号与最小权限

MySQL账号由`'user'@'host'`共同确定：

```sql
CREATE USER 'app_user'@'localhost'
IDENTIFIED BY '交互设置的密码';
CREATE USER 'app_user'@'127.0.0.1'
IDENTIFIED BY '交互设置的密码';
GRANT SELECT, INSERT, UPDATE ON company_db.*
TO 'app_user'@'localhost';
GRANT SELECT, INSERT, UPDATE ON company_db.*
TO 'app_user'@'127.0.0.1';
SHOW GRANTS FOR 'app_user'@'localhost';
SHOW GRANTS FOR 'app_user'@'127.0.0.1';
```

`app_user@localhost`、`app_user@127.0.0.1`与`app_user@192.168.200.%`是不同账号。前两者分别覆盖本机Socket/名称解析和明确的回环TCP场景；具体匹配结果受连接方式和名称解析设置影响。应用只需业务库权限时，不授予`ALL ON *.*`。

## 26.6 Socket与TCP

```bash
mysql -u root -p
mysql -h 127.0.0.1 -P 3306 -u app_user -p
```

第一条可能使用Unix Socket，第二条明确使用TCP。Socket成功不能证明3306可用，TCP成功也不代表远程防火墙开放。

## 26.7 监听与三道边界

```ini
[mysqld]
bind-address=127.0.0.1
```

```text
客户端 → 服务监听地址 → firewalld来源规则
       → 匹配的'user'@'host' → 密码和数据库权限
```

为“方便”同时使用`0.0.0.0`、全网放行和`user@'%'`会放大三层风险。

## 26.8 逻辑备份与恢复

```bash
mysqldump -u root -p --single-transaction \
  --routines --triggers company_db > company_db.sql
test -s company_db.sql
grep -n 'CREATE TABLE' company_db.sql | head
```

恢复应优先进入独立测试库：

```sql
CREATE DATABASE company_restore CHARACTER SET utf8mb4;
```

```bash
mysql -u root -p company_restore < company_db.sql
```

恢复后比较表结构、行数和关键样本。Shell重定向可能在认证失败前就创建空文件，因此必须检查退出码和文件内容。

## 26.9 常见故障

| 现象 | 优先检查 |
|---|---|
| 无法连接Socket | mysqld状态、Socket路径、日志 |
| Connection refused | 服务状态、3306监听地址 |
| Access denied | 用户、来源host、密码、认证插件 |
| 本机成功远程超时 | 监听、防火墙、路由 |
| 能登录但无权访问表 | `SHOW GRANTS`、目标数据库 |
| mysqld启动失败 | 配置、目录权限、journal和错误日志 |
| 备份为0字节 | mysqldump实际失败但重定向创建了文件 |

# 第27章 MongoDB文档数据库

## 27.1 文档模型

| MongoDB | 近似关系型概念 | 特点 |
|---|---|---|
| database | 数据库 | 逻辑命名空间 |
| collection | 表 | 文档集合，结构可以不同 |
| document | 行 | 字段和值，可嵌套 |
| field | 列 | 文档属性 |
| `_id` | 主键 | 默认自动生成且唯一 |

```javascript
{
  host: "rocky-vm",
  status: "ok",
  checks: ["nginx", "mysql", "redis"]
}
```

文档结构灵活不等于不需要设计、校验和索引。

## 27.2 组件与端口

| 对象 | 常见名称 |
|---|---|
| 数据库服务 | `mongod` |
| Shell客户端 | `mongosh` |
| 配置文件 | `/etc/mongod.conf` |
| 默认端口 | TCP 27017 |
| 备份恢复 | `mongodump`、`mongorestore` |

## 27.3 基础数据操作

```javascript
use company_db
db.inspections.insertOne({
  host: "rocky-vm",
  service: "nginx",
  status: "ok"
})
db.inspections.find()
db.inspections.countDocuments()
```

数据库和集合通常在首次写入时实际创建。空数据库未显示在`show dbs`中属于正常现象。

## 27.4 认证与RBAC

典型安全顺序：

```text
仅本机访问 → 创建首个管理用户 → 创建业务用户
→ security.authorization: enabled → 重启
→ 验证未认证失败、管理认证成功、业务认证成功
```

```yaml
security:
  authorization: enabled
```

用户属于创建它的认证数据库。连接时`--authenticationDatabase`必须指向正确位置：

```bash
mongosh --host 127.0.0.1 --port 27017 \
  --authenticationDatabase company_db -u inspectionApp -p
```

`-p`后不写密码，让客户端交互提示。常见角色包括`read`、`readWrite`、`dbAdmin`和`userAdmin`；业务用户只获得业务库必要权限。

## 27.5 监听与YAML

```yaml
net:
  port: 27017
  bindIp: 127.0.0.1
```

YAML对缩进敏感，使用空格且同层键保持一致。远程访问必须同时考虑bindIp、firewalld来源、认证、最小角色和传输安全。

## 27.6 逻辑备份

```bash
mongodump --host 127.0.0.1 --port 27017 \
  --authenticationDatabase company_db \
  -u inspectionApp -p --db company_db --out ./mongodb-backup
```

恢复到测试命名空间时先确认目标，避免不经判断使用`--drop`覆盖现有集合。

## 27.7 故障诊断

| 现象 | 检查方向 |
|---|---|
| mongod无法启动 | YAML缩进、配置键、目录权限、CPU支持、日志 |
| connection refused | 服务或27017监听地址 |
| Authentication failed | 用户名、密码、认证数据库 |
| Unauthorized | 已认证，但角色不允许当前操作 |
| 本机可达远程不可达 | bindIp、firewalld、路由 |
| show dbs未显示 | 是否写入数据、当前用户能否查看 |

# 第28章 Redis缓存服务

## 28.1 Redis的定位

Redis以内存作为主要工作介质，常用于缓存、计数、会话和轻量队列。速度快不等于数据永不丢失；能否恢复取决于持久化、备份、复制和业务设计。

```text
客户端命令 → Redis认证 → 按key定位value
           → 内存读写 → 根据配置生成RDB或追加AOF
```

## 28.2 键值与数据类型

```text
PING
SET company TechCorp
GET company
SET visitors 0
INCR visitors
TYPE visitors
TTL company
```

| 类型 | 适合场景 |
|---|---|
| string | 文本、数字、计数 |
| hash | 对象字段 |
| list | 有序队列 |
| set | 去重集合 |
| sorted set | 带分值排序 |

本课程以string和计数为主，重点是服务运维而不是完整数据结构编程。

## 28.3 认证与保护模式

```text
bind 127.0.0.1 -::1
protected-mode yes
port 6379
requirepass <实验密码>
```

连接后通过`AUTH`交互认证。密码不以`redis-cli -a 密码`形式出现在共享终端记录中。`protected-mode`不能替代正确监听、认证和防火墙，也不能为了连接方便而关闭。

## 28.4 RDB与AOF

| 机制 | 工作方式 | 优势 | 代价与风险 |
|---|---|---|---|
| RDB | 在条件满足时生成时间点快照 | 紧凑、恢复通常较快 | 两次快照间的数据可能丢失 |
| AOF | 追加记录写命令 | 可提供更细恢复点 | 文件更大，写入和重写有开销 |

常见配置项：

```text
save 3600 1
dbfilename dump.rdb
appendonly no
appendfilename "appendonly.aof"
dir /var/lib/redis
```

配置取决于允许丢失多少数据、性能、磁盘空间和恢复时间。开启持久化不等于完成异机备份。

## 28.5 持久化验证与高风险命令

课程小数据可受控执行：

```text
SET persistent_key course-data
SAVE
LASTSAVE
```

重启后重新认证并读取该键，可验证最小持久化链路。生产环境中`SAVE`同步阻塞，需要评估`BGSAVE`及资源影响。

以下命令风险较高：

- `FLUSHDB`清空当前数据库。
- `FLUSHALL`清空所有数据库。
- `CONFIG SET`可能造成运行配置与文件不一致。
- 大数据集上执行`KEYS *`可能阻塞服务。

清理课程数据使用明确键名的`DEL`，先确认目标。

## 28.6 故障排查

```bash
systemctl status redis
sudo journalctl -u redis -n 50 --no-pager
sudo ss -lntp | grep ':6379'
redis-cli
```

| 客户端结果 | 判断 |
|---|---|
| Connection refused | 目标没有服务监听或被主动拒绝 |
| timeout | 路径、防火墙或目标不可达 |
| NOAUTH | 已连接但尚未认证 |
| WRONGPASS | 密码或用户不正确 |
| PONG | 命令链路成功，仍需验证业务键与持久化 |

# 第29章 Git与运维版本管理

## 29.1 为什么运维需要Git

传统备份回答“某时有哪些文件”，Git还能回答谁在何时改变了什么、变化前后差异、哪个提交已验证，以及单个已跟踪文件如何恢复。

Git适合配置模板、脚本、说明文档和基础设施文本，不适合运行数据库、海量日志、构建产物和秘密。

## 29.2 工作区、暂存区与仓库

```text
工作区 --add--> 暂存区 --commit--> 本地仓库 --push--> 远程仓库
   ↑                                               |
   └--restore          clone/pull <----------------┘
```

`git status`是安全起点。推荐小步流程：

```bash
git status
git diff
git add 明确文件
git diff --cached
git commit -m "feat: add server health check"
```

避免不经判断执行`git add .`，因为运维目录常混有日志、备份和凭据。

## 29.3 提交与标签

良好提交信息说明变更目的：

```text
docs: record service exposure policy
fix: correct nginx upstream port
feat: add disk usage health check
```

标签可标记已经验收的基线，但标签本身不会自动证明版本可用，仍需要关联验收记录。

## 29.4 .gitignore的边界

```gitignore
.env
*.key
*.pem
*.log
*.sql
secrets/
runtime/
```

`.gitignore`只影响尚未跟踪的文件。秘密若已经提交或推送，应立即更换凭据、停止传播并按组织流程清理历史；删除最新文件不能消除历史内容。

## 29.5 克隆、推送和拉取

```bash
git clone /path/to/team.git working-copy
git push -u origin main
git pull --ff-only
```

裸仓库没有普通工作区，适合作为课堂共享中心。`--ff-only`在本地与远端分叉时停止，让管理员先理解历史，而不是自动产生未经判断的合并。

## 29.6 恢复前先看差异

```bash
git status
git diff -- path/to/file
git restore path/to/file
git show stable-v1:path/to/file
git restore --source=stable-v1 -- path/to/file
```

`git restore`会丢弃未提交变化。先用`git diff`或`git show`确认要保留与丢弃的内容。

## 29.7 Git与备份的区别

| 需求 | Git | 文件/数据库备份 |
|---|---|---|
| 查看文本差异 | 强 | 弱 |
| 记录变更原因 | 强 | 通常不具备 |
| 保存运行数据 | 不适合 | 适合 |
| 保存秘密 | 不应使用 | 需加密和访问控制 |
| 数据库一致性恢复 | 不能保证 | 使用数据库专用工具 |

# 第30章 Shell服务器巡检

## 30.1 从命令集合到脚本

巡检脚本把人工检查固化为一致流程：

```text
输入：阈值、服务、端口、URL
处理：采集 → 判断 → 汇总
输出：人可读文本 + 标准错误 + 退出码
```

巡检回答“现在是否符合预期”；监控强调持续采集和告警；自动修复会改变系统状态。入门脚本默认只读，避免错误判断触发重启循环。

## 30.2 基本结构

```bash
#!/usr/bin/env bash
set -u

STATUS=0

check_service() {
    local service=$1
    if systemctl is-active --quiet "$service"; then
        printf '[OK] %s active\n' "$service"
    else
        printf '[CRIT] %s not active\n' "$service" >&2
        STATUS=2
    fi
}

check_service nginx
exit "$STATUS"
```

- Shebang指定解释器。
- 引号保护变量，避免空格和通配符造成参数拆分。
- `local`限制函数变量范围。
- 函数使每类检查可独立修改。
- 退出码让其他程序判断结果。

## 30.3 数组、循环与阈值

```bash
SERVICES=(nginx mysqld mongod redis sshd)
for service in "${SERVICES[@]}"; do
    systemctl is-active --quiet "$service" || printf '[CRIT] %s\n' "$service"
done
```

磁盘使用率可从稳定格式中采集：

```bash
used=$(df -P / | awk 'NR==2 {gsub(/%/, "", $5); print $5}')
if (( used >= 80 )); then
    printf '[WARN] root filesystem %s%%\n' "$used"
fi
```

阈值不是普遍真理。生产阈值要结合增长速度、扩容时间、业务突发和CPU核数。

## 30.4 标准输出、错误和退出码

| 编号 | 名称 | 用途 |
|---:|---|---|
| 0 | stdin | 输入 |
| 1 | stdout | 普通结果 |
| 2 | stderr | 错误和严重异常 |

```bash
./server-health.sh > normal.log 2> error.log
./server-health.sh > all.log 2>&1
```

课程约定0为OK、1为WARN、2为CRITICAL。多项检查应保留最高严重级别。退出码会被下一条命令覆盖，应立即保存：

```bash
./server-health.sh
result=$?
printf 'result=%s\n' "$result"
```

## 30.5 为什么不盲目使用set -e

巡检需要观察失败并继续收集其他项目。简单启用`set -e`可能在第一个非0命令处退出，且其行为受条件、管道和子Shell影响。课程脚本使用明确判断和状态累计，使用`set -u`发现未定义变量。

## 30.6 质量验证

```bash
bash -n server-health.sh
chmod 750 server-health.sh
./server-health.sh
echo $?
```

合格脚本应满足：

1. 正常环境输出可读且退出0。
2. 受控故障能被识别并返回非0。
3. 恢复后重新执行回到正常。
4. 不修改服务、不包含密码。
5. 服务名、端口和阈值集中配置。
6. 输出包含时间、主机和检查对象。

## 30.7 常见错误

| 错误 | 后果 | 改进 |
|---|---|---|
| 变量不加引号 | 参数被拆分 | 默认使用`"$var"` |
| 输出未验证就做算术 | 空值造成错误 | 先校验格式 |
| 只看服务active | 端口或应用仍可能异常 | 增加端口和URL验证 |
| 自动重启失败服务 | 掩盖根因 | 默认只报告 |
| 日志目录不可写 | 脚本自身失败 | 使用明确可写目录 |
| 密码写在脚本 | 泄露到Git | 交互输入或秘密管理 |

# 第31章 综合部署、验收与故障排查

## 31.1 系统成功不是组件相加

```text
Nginx依赖文件权限和SELinux标签
反向代理依赖后端systemd服务和端口
数据库依赖进程、监听、认证和授权
巡检依赖正确服务名、端口和健康URL
恢复依赖真正可读的备份
交付依赖脱敏文档和可复核证据
```

Nginx为active时API仍可能返回502；MySQL监听3306时应用用户仍可能无表权限。

## 31.2 五维验收

| 维度 | 核心问题 | 证据示例 |
|---|---|---|
| 可运行 | 进程能否稳定启动 | systemd、journal |
| 可访问 | 请求能否到达入口 | ss、firewalld、curl |
| 可使用 | 认证后能否完成业务 | SQL、文档查询、Redis读写 |
| 可保护 | 是否最小开放和权限 | 监听、规则、授权、SELinux |
| 可恢复 | 误改或数据损坏后能否恢复 | 备份、演练、Git历史 |

## 31.3 配置变更闭环

```text
记录基线 → 准备备份与回退 → 小范围修改
→ 语法检查 → 应用变更 → 分层功能验证
→ 观察日志 → 提交脱敏版本与证据
```

任一步失败，应停止扩展改动，回到最近已验证状态。

## 31.4 分层排障

1. 明确谁访问什么失败、何时开始和影响范围。
2. 检查客户端地址、端口、协议和用户名。
3. 检查IP、路由和DNS。
4. 检查systemd状态及失败日志。
5. 检查监听地址、端口和协议。
6. 检查firewalld、SELinux和Unix权限。
7. 检查认证、授权、映射和数据。
8. 修复后验证原功能和相邻功能。

## 31.5 现象、根因与证据

| 现象 | 可能根因 |
|---|---|
| 浏览器打不开 | 地址、服务、监听、防火墙、路由 |
| Nginx 403 | 文件权限、目录遍历、SELinux、规则 |
| Nginx 502 | 后端、端口、协议、SELinux |
| 数据库Access denied | 用户、密码、认证库、来源或授权 |
| 服务重启失败 | 语法、权限、端口冲突、资源 |
| 备份存在但恢复失败 | 空文件、版本、权限、不一致 |

证据分为状态证据、配置证据、日志证据和功能证据。截图只是承载方式；有效证据还需要命令、目标、结果与判断。

## 31.6 安全边界

综合服务器需要明确：

- 哪些端口必须让客户端访问？
- 哪些服务只由本机应用访问？
- 每个账号需要和不需要哪些权限？
- 配置、日志、备份和Git是否泄露秘密？
- SELinux是否保持Enforcing？
- firewalld活动zone是否匹配实际网卡？

课程默认只开放SSH和HTTP，数据库与本地后端监听回环地址。

## 31.7 备份恢复矩阵

| 对象 | 合适方法 | 最小验证 |
|---|---|---|
| 静态站点 | rsync或归档 | 文件清单、哈希或diff |
| Nginx配置 | 副本 + Git脱敏模板 | `nginx -t`和请求 |
| MySQL | `mysqldump` | 非空、含表、测试库恢复 |
| MongoDB | `mongodump` | 文件、测试命名空间恢复 |
| Redis | RDB/AOF及受控副本 | 重启读取或隔离恢复 |
| Shell脚本 | Git | 语法、正常和异常测试 |

## 31.8 交付文档

另一名管理员应能从文档获得：系统和网络基线、服务清单、端口边界、关键配置路径、启停与语法检查、健康验证、备份恢复方法、已知限制和故障记录。文档应写“如何验证”，不只写“已完成”。

## 31.9 与容器课程的连接

| Linux课程能力 | 容器课程对应问题 |
|---|---|
| 进程与systemd | 容器主进程、生命周期、重启策略 |
| 端口与监听 | 端口发布、容器网络、服务发现 |
| 权限与SELinux | 挂载权限、标签、宿主机边界 |
| 软件包与仓库 | 基础镜像、镜像层、软件来源 |
| 日志排查 | 容器日志、运行时事件、应用日志 |
| Git版本 | Dockerfile、Compose、部署清单 |
| 备份恢复 | 数据卷、数据库备份、迁移 |

学生先理解服务在普通Linux中如何运行，再学习把它容器化，后续课程就不会退化为背Docker命令。

## 核心关系

