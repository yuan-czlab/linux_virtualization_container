## 模块导读

服务器只有接入网络、提供可验证的服务并具备基本防护，才具有实际使用价值。本模块以两台虚拟机为环境：Rocky Linux 9作为被管理服务器，Ubuntu Server 22.04作为管理客户端。学习过程从IP、路由和DNS开始，依次完成端口分析、HTTP验证、SSH远程管理、密钥认证、文件传输、增量备份、firewalld和SELinux基础防护，最后形成一套分层排障方法。

完成本模块后，应能够：

1. 使用`ip`和`nmcli`查看、配置并验证Linux网络。

3. 使用`ss`、`nc`、`dig`、`getent`和`curl`定位常见网络问题。
4. 安全配置SSH服务，验证主机指纹，并使用日志分析连接失败原因。
5. 使用Ed25519密钥、SSH客户端配置、SCP、SFTP和rsync管理远程主机。
6. 使用cron执行可验证的定时备份，并完成恢复演练。
7. 使用firewalld配置最小开放、永久规则和来源限制，并能安全回滚。
8. 解释DAC与SELinux MAC的分层关系，使用上下文和审计日志排错。
9. 按“客户端—网络—服务—监听—防火墙—SELinux—应用”的顺序完成综合排障。

## 操作安全规则

- 修改IP、SSH或防火墙前创建快照，并保留VMware控制台。
- 远程修改管理通道时，保留一个已登录会话，再用第二个会话验证。

- 防火墙规则先使用运行时配置验证，确认无误后再持久化。

- 备份必须执行恢复验证；复制完成必须检查内容或哈希。

# 第13章 IP、网卡、路由与DNS客户端

## 13.1 一次网络访问需要哪些条件

Linux主机访问另一个地址时，至少涉及以下对象：

```text
应用给出目标名称或IP
→ 名称需要DNS解析为IP
→ 路由表决定从哪个网卡、经哪个下一跳发送
→ 网卡必须处于UP状态并拥有适合的IP/前缀
→ 二层邻居解析得到下一跳MAC地址
→ 数据包离开主机
```

| 对象 | 解决的问题 | 常用检查命令 |
|---|---|---|
| 网卡 | 从哪个网络接口收发 | `ip link`、`nmcli device` |
| IP地址和前缀 | 本机身份及直连网段 | `ip address` |
| 路由 | 目标应从哪里发送 | `ip route`、`ip route get` |
| 默认网关 | 非直连目标的下一跳 | `ip route` |
| DNS客户端 | 名称如何转换为地址 | `getent hosts`、`dig` |
| 邻居表 | 下一跳IP对应哪个MAC | `ip neigh` |

“有IP”不等于“网络正常”。地址重复、前缀错误、默认路由缺失、DNS不可用或防火墙阻断都可能导致访问失败。

## 13.2 使用ip查看网络状态

```bash
ip -br link
ip -br address
ip route
ip route get 192.168.200.20
ip neigh
```

`ip route get`不会真正发送数据包，而是询问内核：访问这个目标时准备选择哪条路由、源地址和接口。示例结果：

```text
192.168.200.20 dev ens33 src 192.168.200.10
```

表示目标属于直连网段，经`ens33`发送，源地址选择`192.168.200.10`。

默认路由常见形式：

```text
default via 192.168.200.2 dev ens33 proto static metric 100
```

- `default`匹配没有更具体路由的目标。
- `via`后是下一跳网关。
- `dev`后是出口接口。
- metric较小的路由通常优先，但仍先遵循最长前缀匹配。

## 13.3 临时地址与永久连接配置

`ip`直接修改的是内核运行状态，通常在重启或重新激活连接后消失。以下命令只添加一个辅助地址，不替换当前管理地址：

```bash
IFACE=$(ip route show default | awk 'NR==1 {print $5}')
printf 'interface=%s\n' "$IFACE"
```

如果结果为空或不是实验网卡，停止操作并先检查`ip route`。确认无误后执行：

```bash
sudo ip address add 192.168.200.100/24 dev "$IFACE"
ip -br address show dev "$IFACE"
sudo ip address del 192.168.200.100/24 dev "$IFACE"
```

执行前确认：

1. `IFACE`输出的是预期实验网卡。
2. `192.168.200.100`属于实验网段。
3. 地址没有被其他主机使用。

不要在远程SSH会话中直接删除当前管理IP。

## 13.4 NetworkManager中的device与connection

NetworkManager区分物理或虚拟设备和连接配置：

```text
device：例如ens33这张网卡
connection：应用到网卡的一组配置，如static-net
```

```bash
nmcli device status
nmcli connection show
nmcli connection show --active
nmcli -f GENERAL,IP4 connection show static-net
```

连接名不一定等于网卡名。根据默认路由接口自动取得当前连接名：

```bash
IFACE=$(ip route show default | awk 'NR==1 {print $5}')
CON_NAME=$(nmcli -g GENERAL.CONNECTION device show "$IFACE")
printf 'interface=%s connection=%s\n' "$IFACE" "$CON_NAME"
nmcli connection show "$CON_NAME"
```

如果结果为空或为`--`，不要继续修改，应先用`nmcli connection show --active`确认设备是否由NetworkManager管理。

## 13.5 使用nmcli创建静态连接

本操作应在VMware控制台中完成。先保存现有配置文件：

```bash
backup_dir="/root/nm-backup-$(date +%F-%H%M%S)"
sudo mkdir -p "$backup_dir"
sudo cp -a /etc/NetworkManager/system-connections/. "$backup_dir/"
echo "backup=$backup_dir"
```

确认接口名和实验网段后创建新连接：

```bash
sudo nmcli connection add type ethernet \
  con-name m2-static ifname "$IFACE" \
  connection.autoconnect yes \
  connection.autoconnect-priority 100 \
  ipv4.method manual \
  ipv4.addresses 192.168.200.10/24 \
  ipv4.gateway 192.168.200.2 \
  ipv4.dns '223.5.5.5 119.29.29.29' \
  ipv6.method auto

sudo nmcli connection up m2-static
```

`connection.autoconnect-priority`数值较高的配置在同一设备存在多个可自动连接配置时更优先。记录原连接和新连接的设置：

```bash
nmcli -f connection.id,connection.autoconnect,connection.autoconnect-priority \
  connection show "$CON_NAME"
nmcli -f connection.id,connection.autoconnect,connection.autoconnect-priority \
  connection show m2-static
```

重启验证前，应决定最终保留哪个连接。若保留`m2-static`，可把原连接的自动连接关闭：

```bash
sudo nmcli connection modify "$CON_NAME" connection.autoconnect no
```

删除`m2-static`回退时，应重新启用原连接：

```bash
sudo nmcli connection modify "$CON_NAME" connection.autoconnect yes
```

立即验证：

```bash
ip -br addr
ip route
ip route get 192.168.200.20
ping -c 3 192.168.200.2
getent hosts mirrors.aliyun.com
```

如果地址或网关错误，在控制台回退：

```bash
sudo nmcli connection down m2-static
sudo nmcli connection delete m2-static
sudo nmcli connection up "$CON_NAME"
```

如果连接配置文件被误改，可在控制台把本章备份复制回原目录，再让NetworkManager重新读取：

```bash
sudo cp -a "$backup_dir"/. /etc/NetworkManager/system-connections/
sudo nmcli connection reload
```

恢复前先执行`sudo ls -la "$backup_dir"`确认目录正确。重新登录后变量会失效，需要从`/root/nm-backup-*`中人工确认对应备份，不能自动选择后直接覆盖。

不要同时激活多个面向同一网卡、带有不同默认路由的连接。

## 13.6 DNS设置与resolv.conf

Rocky Linux中`/etc/resolv.conf`通常由NetworkManager生成：

```bash
ls -l /etc/resolv.conf
cat /etc/resolv.conf
nmcli device show "$IFACE" | grep -E 'IP4.DNS|IP4.DOMAIN'
```

需要永久修改DNS时修改连接，而不是直接覆盖`/etc/resolv.conf`：

```bash
sudo nmcli connection modify m2-static \
  ipv4.ignore-auto-dns yes \
  ipv4.dns '223.5.5.5 119.29.29.29'
sudo nmcli connection up m2-static
```

若要恢复从DHCP获取DNS：

```bash
sudo nmcli connection modify m2-static ipv4.ignore-auto-dns no ipv4.dns ''
sudo nmcli connection up m2-static
```

## 13.7 Ubuntu Server网络对照

Ubuntu Server 22.04常通过Netplan生成systemd-networkd或NetworkManager配置：

```bash
ls /etc/netplan/
sudo netplan get
networkctl status 2>/dev/null || true
resolvectl status 2>/dev/null || true
```

Netplan是YAML格式，缩进错误会导致配置失败。远程修改时优先使用：

```bash
sudo netplan try
```

`netplan try`要求在限定时间内确认，否则自动回退，适合降低远程断连风险。正式应用前仍应保留控制台和原文件备份。

# 第14章 TCP、UDP、端口与服务监听

## 14.1 端口属于谁

端口不是某个软件的永久编号，而是传输层标识。运行中的进程通过Socket绑定本地地址、协议和端口：

```text
进程
└── Socket
    ├── 协议：TCP或UDP
    ├── 本地地址：127.0.0.1 / 0.0.0.0 / 具体网卡地址
    └── 本地端口：22 / 8080 / 其他
```

同一个端口号可以同时出现在不同协议或不同地址上。例如UDP 53和TCP 53可以由DNS服务同时使用。

## 14.2 TCP与UDP的运维差异

| 特性 | TCP | UDP |
|---|---|---|
| 建立连接 | 三次握手 | 无连接握手 |
| 可靠性 | 序号、确认、重传 | 协议自身不保证到达 |
| 边界 | 字节流 | 保留数据报边界 |
| 常见场景 | SSH、HTTP、数据库 | DNS查询、NTP、实时音视频 |
| 常见检查 | 监听、连接状态、握手 | 监听、收发包、应用响应 |

UDP端口没有TCP那样明确的“连接成功”语义。对UDP进行`nc -z`测试不能单独证明应用层服务正常，应结合实际协议查询和抓包结果。

## 14.3 使用ss查看Socket

```bash
ss -lnt
ss -lnu
sudo ss -lntup
ss -tan state established
ss -tan state time-wait
sudo lsof -nP -iTCP:8080 -sTCP:LISTEN
```

常用参数：

| 参数 | 含义 |
|---|---|
| `-l` | 只看监听Socket |
| `-n` | 不解析服务名和域名，直接显示数字 |
| `-t` | TCP |
| `-u` | UDP |
| `-p` | 显示进程，需要足够权限 |
| `-a` | 所有Socket |

监听地址：

| 地址 | 可接受的目标 |
|---|---|
| `127.0.0.1:8080` | 仅本机IPv4回环地址 |
| `192.168.200.10:8080` | 仅指定网卡地址 |
| `0.0.0.0:8080` | 所有IPv4本地接口 |
| `[::1]:8080` | 仅IPv6回环地址 |
| `[::]:8080` | 所有IPv6接口，是否同时接收IPv4取决于系统配置 |

## 14.4 监听地址对访问范围的影响

准备页面：

```bash
mkdir -p ~/m2-web
printf '<h1>M2 network test</h1>\n' > ~/m2-web/index.html
```

终端A只监听回环地址：

```bash
python3 -m http.server 8080 --bind 127.0.0.1 --directory ~/m2-web
```

终端B验证：

```bash
ss -lnt | grep ':8080'
curl http://127.0.0.1:8080/
curl --connect-timeout 3 http://192.168.200.10:8080/
```

第一个curl应成功，第二个即使在同一台主机也应失败，因为进程没有绑定网卡地址。按`Ctrl+C`结束终端A，再改为：

```bash
python3 -m http.server 8080 --bind 0.0.0.0 --directory ~/m2-web
```

此时两个地址都进入监听范围。外部客户端能否访问还取决于路由和防火墙。

## 14.5 使用nc测试TCP端口

Rocky与Ubuntu的软件包名称不同：

```bash
# Rocky Linux 9
sudo dnf install -y nmap-ncat

# Ubuntu Server 22.04
sudo apt install -y netcat-openbsd
```

从Ubuntu测试Rocky：

```bash
nc -vz -w 3 192.168.200.10 22
nc -vz -w 3 192.168.200.10 9999
```

常见结果：

| 现象 | 常见含义 | 下一步 |
|---|---|---|
| succeeded | TCP握手成功 | 继续验证应用协议和认证 |
| Connection refused | 目标可达但该地址/端口无监听，或防火墙主动拒绝 | 查`ss`和服务状态 |
| timed out | 报文丢弃、路由不通或中间防火墙静默丢弃 | 查路由、防火墙和抓包 |
| No route to host | 本机路由、网关、邻居或ICMP拒绝相关 | 查`ip route get`和网络层 |

不能仅凭一条报错直接确定唯一原因，应通过服务端`ss`和客户端测试交叉验证。

### 本章实践：端口证据链

1. 在Rocky分别绑定`127.0.0.1:8080`和`0.0.0.0:8080`。
2. 使用`ss`证明监听地址发生变化。
3. 使用curl测试回环地址和网卡地址。
4. 从Ubuntu使用`nc`测试Rocky的22、8080和9999端口。
5. 记录“进程状态、监听状态、客户端结果”三类证据。

完成本章后，在运行Python服务的终端按`Ctrl+C`，再确认8080监听已经消失：

```bash

```

# 第15章 DNS解析与hosts

## 15.1 名称解析链

大多数应用不会只查询DNS，而是通过系统名称服务接口按`/etc/nsswitch.conf`决定顺序：

```text
应用程序
→ glibc名称服务接口
→ /etc/nsswitch.conf中的hosts顺序
→ /etc/hosts、DNS或其他来源
→ 返回一个或多个地址
```

```bash
grep '^hosts:' /etc/nsswitch.conf
cat /etc/hosts
cat /etc/resolv.conf
```

常见配置含义是先查本地文件，再查DNS。实际字段可能包含`resolve`、`myhostname`等模块，应以当前系统为准。

## 15.2 DNS查询的基本过程

客户端通常把查询交给递归解析器。递归解析器可能从缓存返回，也可能继续询问根、顶级域和权威服务器。本模块重点是客户端配置与排障，不搭建企业DNS服务。

常见记录：

| 类型 | 用途 |
|---|---|
| A | 名称对应IPv4地址 |
| AAAA | 名称对应IPv6地址 |
| CNAME | 别名指向另一个名称 |
| MX | 邮件交换服务器 |
| NS | 域的权威DNS服务器 |
| PTR | 地址反向解析为名称 |
| TXT | 文本信息和域名验证等 |

## 15.3 getent、dig与nslookup

安装查询工具：

```bash
# Rocky Linux 9
sudo dnf install -y bind-utils

# Ubuntu Server 22.04
sudo apt install -y dnsutils
```

```bash
getent hosts mirrors.aliyun.com
getent ahosts mirrors.aliyun.com
dig mirrors.aliyun.com A
dig +short mirrors.aliyun.com A
dig mirrors.aliyun.com AAAA
nslookup mirrors.aliyun.com
```

- `getent`遵循系统NSS配置，行为更接近curl和SSH等应用。
- `dig`直接发起DNS查询，能查看状态、响应服务器、记录和耗时。
- `nslookup`适合快速交互查询，但排障信息通常不如dig完整。

如果`dig`成功而`getent`结果异常，应检查`/etc/hosts`和`/etc/nsswitch.conf`，而不是立即判断DNS服务器故障。

## 15.4 /etc/hosts控制实验

实验名称使用保留后缀`.test`。不要随意使用`.local`，因为`.local`在许多系统中具有mDNS特殊语义，可能产生与普通DNS/NSS不同的结果。

先备份：

```bash
sudo cp -a /etc/hosts /etc/hosts.m2-backup
```

在Rocky添加实验名称：

```bash
echo '192.168.200.10 m2-rocky.test m2-rocky' | sudo tee -a /etc/hosts
getent hosts m2-rocky.test
dig +short m2-rocky.test
```

预期：`getent`能够从`/etc/hosts`得到结果；`dig`只查询DNS，通常不知道这个本地名称。这证明“系统应用解析”和“直接DNS查询”不是完全相同的路径。

Ubuntu客户端也添加相同记录：

```bash
echo '192.168.200.10 m2-rocky.test m2-rocky' | sudo tee -a /etc/hosts
getent hosts m2-rocky.test
ping -c 2 m2-rocky.test
```

## 15.5 DNS故障分层判断

```text
第一步：目标IP是否可达
第二步：系统当前使用哪些DNS服务器
第三步：getent能否解析
第四步：dig向默认DNS查询是否成功
第五步：dig向指定DNS查询是否成功
第六步：检查hosts和nsswitch覆盖
第七步：检查UDP/TCP 53是否被网络策略阻断
```

```bash
ping -c 2 192.168.200.2
cat /etc/resolv.conf
getent hosts mirrors.aliyun.com
dig mirrors.aliyun.com
dig @223.5.5.5 mirrors.aliyun.com
```

`dig +trace`需要能够直接访问互联网多个DNS节点，受限机房不一定允许，因此不能作为基础验收的必要条件。

## 15.6 不直接修改resolv.conf制造故障

NetworkManager或systemd-resolved可能覆盖`/etc/resolv.conf`。为了观察DNS超时而直接写入错误nameserver，容易破坏后续软件安装。可以使用一次性查询安全模拟：

```bash
dig +time=2 +tries=1 @192.0.2.53 example.com
echo "exit_code=$?"
```

`192.0.2.0/24`是文档示例网段，不应在公网路由。该命令只影响本次dig，不修改系统配置。

### 本章实践：证明解析来源

提交以下对照结果：

```bash
grep '^hosts:' /etc/nsswitch.conf
getent hosts m2-rocky.test
dig +short m2-rocky.test
getent hosts mirrors.aliyun.com
dig +short mirrors.aliyun.com
```

说明每个结果来自`/etc/hosts`还是DNS，并写出清理命令：

```bash
sudo sed -i '/m2-rocky\.test/d' /etc/hosts
```

# 第16章 HTTP、HTTPS与curl

## 16.1 HTTP请求与响应

HTTP运行在传输通道之上：

```text
URL解析
→ DNS解析
→ TCP连接
→ HTTPS场景进行TLS握手和证书验证
→ 发送HTTP请求行、Header和可选Body
→ 接收状态行、Header和Body
```

HTTP本身是应用层协议。端口80和443是常见约定，不是强制要求，实验服务可以运行在8080和8443。

常见方法：

| 方法 | 一般用途 |
|---|---|
| GET | 获取资源 |
| HEAD | 只请求响应头 |
| POST | 提交数据或触发处理 |
| PUT | 创建或整体替换资源 |
| DELETE | 删除资源 |

## 16.2 状态码分类

| 分类 | 含义 | 常见示例 |
|---|---|---|
| 1xx | 临时信息 | 100 Continue |
| 2xx | 请求成功 | 200、201、204 |
| 3xx | 重定向或缓存 | 301、302、304 |
| 4xx | 客户端请求或权限问题 | 400、401、403、404 |
| 5xx | 服务端或上游处理失败 | 500、502、503、504 |

状态码只能指出协议层结果，不能单独确定根因。例如403可能来自文件权限、应用授权或SELinux；502通常表示代理无法从上游得到有效响应，但仍需结合代理和上游日志判断。

## 16.3 使用curl观察HTTP

终端A在Rocky启动测试服务：

```bash
python3 -m http.server 8080 --bind 0.0.0.0 --directory ~/m2-web
```

终端B执行：

```bash
curl http://127.0.0.1:8080/
curl -I http://127.0.0.1:8080/
curl -v http://127.0.0.1:8080/ -o /dev/null
curl -sS -o /dev/null -w 'code=%{http_code} total=%{time_total}\n' \
  http://127.0.0.1:8080/
curl -sS -o /dev/null -w 'code=%{http_code}\n' \
  http://127.0.0.1:8080/not-found
```

| 选项 | 作用 |
|---|---|
| `-I` | 发出HEAD请求 |
| `-v` | 显示连接、请求和响应细节 |
| `-o FILE` | 把响应Body写入文件 |
| `-sS` | 减少进度输出但保留错误 |
| `-L` | 跟随重定向 |
| `-w` | 输出状态码和耗时等变量 |
| `--connect-timeout` | 限制连接建立时间 |
| `--max-time` | 限制整个请求时间 |

curl默认在收到HTTP 404时仍可能退出0，因为HTTP事务本身成功完成。需要把4xx/5xx作为脚本失败时使用：

```bash
curl --fail-with-body http://127.0.0.1:8080/not-found
echo "exit_code=$?"
```

完成HTTP基础实验后，先在终端A按`Ctrl+C`结束8080服务，并确认端口已释放：

```bash
ss -lnt | grep ':8080' || echo '8080 listener stopped'
```

## 16.4 HTTPS原理与拓展实验

本节的证书实验用于加深TLS理解，不作为U16基础验收的必要条件。Nginx的正式HTTPS部署、证书文件组织和日志排障安排在模块三。

HTTPS提供传输加密、完整性保护和服务器身份验证。它不代表网站内容、账号权限或业务逻辑一定安全。

证书验证主要检查：

- 证书是否由客户端信任的CA签发。
- 当前时间是否处于有效期内。
- 访问名称是否包含在证书SAN中。
- 证书链和签名是否有效。

创建仅用于实验的自签名证书：

以下命令继续在Rocky执行。证书SAN中的IP必须替换为Rocky当前实际地址；如果只通过`m2-rocky.test`访问，名称SAN仍必须与该名称完全一致。

```bash
mkdir -p ~/m2-tls
cd ~/m2-tls
printf '<h1>M2 TLS test</h1>\n' > index.html

openssl req -x509 -newkey rsa:2048 -nodes -days 7 \
  -keyout server.key -out server.crt \
  -subj '/CN=m2-rocky.test' \
  -addext 'subjectAltName=DNS:m2-rocky.test,IP:192.168.200.10'

chmod 600 server.key
openssl x509 -in server.crt -noout -subject -issuer -dates -ext subjectAltName
```

证书私钥只能保存在Rocky实验机，不上传、不提交、不复制给其他人。

Rocky终端A在HTTP服务已停止后启动临时TLS服务：

```bash
cd ~/m2-tls
openssl s_server -accept 8443 -cert server.crt -key server.key -WWW
```

Rocky终端B对比。`server.crt`当前只存在于Rocky，若希望从Ubuntu验证，必须先只复制公开证书文件，绝不能复制`server.key`：

```bash
curl -v https://m2-rocky.test:8443/index.html
curl -vk https://m2-rocky.test:8443/index.html
curl --cacert ~/m2-tls/server.crt https://m2-rocky.test:8443/index.html
```

第一次通常因自签名证书不受信任而失败；`-k`跳过验证，只适用于受控诊断；`--cacert`显式信任本实验CA文件，仍会检查名称和有效期。生产脚本不应长期使用`-k`。

### 本章实践：HTTP证据表

记录以下项目：

| 项目 | 命令 | 结果 |
|---|---|---|
| 监听地址 | `ss -lnt` | |
| HTTP 200 | `curl -w` | |
| HTTP 404 | `curl -w` | |
| 404退出状态 | `curl --fail-with-body` | |
| TLS证书主题和SAN | `openssl x509` | |
| 不受信任证书 | `curl -v` | |
| 显式信任证书 | `curl --cacert` | |

# 第17章 SSH远程管理

## 17.1 SSH连接中的角色和密钥

SSH连接包含：

```text
客户端ssh
→ TCP连接服务器22端口
→ 协商算法并验证服务器主机密钥
→ 服务器验证用户密码或用户公钥
→ 建立加密会话
```

必须区分两类密钥：

| 密钥 | 证明对象 | 常见位置 |
|---|---|---|
| 服务器主机密钥 | “这是不是原来的服务器” | `/etc/ssh/ssh_host_*_key` |
| 用户认证密钥 | “这个客户端用户是否有登录资格” | 客户端`~/.ssh/`和服务端`authorized_keys` |

## 17.2 安装并检查sshd

Rocky：

```bash
sudo dnf install -y openssh-server
sudo systemctl enable --now sshd
systemctl status sshd --no-pager
sudo ss -lntp | grep ':22'
```

Ubuntu对照：

```bash
sudo apt install -y openssh-server
sudo systemctl enable --now ssh
systemctl status ssh --no-pager
```

Rocky的Unit通常叫`sshd.service`，Ubuntu通常叫`ssh.service`。实际进程仍是`sshd`。

如果Rocky上的firewalld已启用，首次远程连接前在VMware控制台只读检查SSH规则：

```bash
IFACE=$(ip route show default | awk 'NR==1 {print $5}')
ZONE=$(firewall-cmd --get-zone-of-interface="$IFACE" 2>/dev/null)
if [[ -z "$ZONE" || "$ZONE" == 'no zone' ]]; then
  ZONE=$(firewall-cmd --get-default-zone)
fi
firewall-cmd --zone="$ZONE" --query-service=ssh
```

若返回`no`，先在控制台添加运行时规则并从Ubuntu验证；成功后再写入永久配置：

```bash
sudo firewall-cmd --zone="$ZONE" --add-service=ssh
# 从Ubuntu验证新的SSH连接后再执行下一行
sudo firewall-cmd --permanent --zone="$ZONE" --add-service=ssh
```

## 17.3 首次连接与主机指纹

在Rocky控制台显示Ed25519主机公钥指纹：

```bash
sudo ssh-keygen -lf /etc/ssh/ssh_host_ed25519_key.pub
```

从Ubuntu首次连接：

```bash
ssh student@192.168.200.10
```

出现主机真实性提示时，先对照控制台指纹。相同后输入`yes`，记录保存在：

```bash
ssh-keygen -F 192.168.200.10
```

主机密钥警告可能表示服务器重装、地址被复用或中间人攻击。不能看到警告就直接删除`known_hosts`。应先通过控制台或可信渠道确认新指纹；确认是合法变更后才执行：

```bash
ssh-keygen -R 192.168.200.10
```

## 17.4 使用-v观察连接阶段

```bash
ssh -v student@192.168.200.10
ssh -vv student@192.168.200.10
```

重点观察：

1. 读取了哪些客户端配置。
2. 连接哪个地址和端口。
3. 选择了哪条主机密钥。
4. 客户端尝试了哪些用户密钥。
5. 服务端允许哪些认证方法。

调试输出可能包含用户名、主机名和路径，提交前应移除真实生产信息，但不得伪造关键证据。

## 17.5 查看有效服务端配置

配置文件中的注释和重复项不能代表最终值。使用：

```bash
sudo sshd -T | grep -E \
  '^(port|permitrootlogin|passwordauthentication|pubkeyauthentication|maxauthtries) '
```

`sshd -T`输出解析后的有效配置。Rocky和Ubuntu通常支持`/etc/ssh/sshd_config.d/*.conf`配置片段，但仍应检查主配置是否包含相应`Include`。

## 17.6 安全修改SSH配置

本章只设置不影响普通密码登录的基础项。先备份并创建片段：

```bash
sudo cp -a /etc/ssh/sshd_config /etc/ssh/sshd_config.m2-backup

sudo tee /etc/ssh/sshd_config.d/20-m2-baseline.conf >/dev/null <<'EOF'
PermitRootLogin no
MaxAuthTries 3
PubkeyAuthentication yes
EOF
```

语法检查和应用：

```bash
sudo sshd -t
sudo systemctl reload sshd
sudo sshd -T | grep -E \
  '^(permitrootlogin|maxauthtries|pubkeyauthentication) '
```

不要在密钥尚未验证时关闭密码认证。不要把“修改默认端口”当作核心安全措施；它只能减少部分自动扫描，不能替代密钥、最小权限、防火墙和日志审计。

## 17.7 SSH日志与排障

```bash
sudo journalctl -u sshd -n 50 --no-pager
sudo journalctl -u sshd --since '10 minutes ago'
```

`journalctl`是必做检查。Rocky最小化环境若安装并启用了rsyslog，还可以对照：

```bash
if [[ -f /var/log/secure ]]; then
  sudo tail -n 50 /var/log/secure
fi
```

Ubuntu对照：

```bash
sudo journalctl -u ssh -n 50 --no-pager
sudo tail -n 50 /var/log/auth.log
```

```text

→ ip route get是否选对路径
→ nc能否建立TCP连接
→ 服务端sshd是否active
→ ss是否监听预期地址和端口
→ firewalld是否允许
→ ssh -v显示在哪个认证阶段失败
→ 服务端journal记录什么
```

# 第18章 SSH密钥认证

## 18.1 公钥认证不是传送私钥

密钥认证的基本逻辑：

```text
客户端持有私钥并完成签名
→ 服务端从authorized_keys找到对应公钥
→ 服务端验证签名
→ 私钥始终留在客户端
```

`authorized_keys`泄露会暴露允许登录的公钥和注释，但私钥泄露会使攻击者可能冒充客户端。私钥必须设置权限并使用口令保护。

## 18.2 在Ubuntu生成独立实验密钥

先检查，避免覆盖已有密钥：

```bash
ls -la ~/.ssh 2>/dev/null || true
```

生成专用Ed25519密钥：

```bash
mkdir -p ~/.ssh
chmod 700 ~/.ssh
ssh-keygen -t ed25519 -a 64 \
  -f ~/.ssh/m2_ed25519 \
  -C "m2-$(whoami)@$(hostname)-$(date +%F)"
```

按提示设置私钥口令。生成后：

```bash
ls -l ~/.ssh/m2_ed25519*
ssh-keygen -lf ~/.ssh/m2_ed25519.pub
```

私钥通常应为600，公钥可以644。绝不能把`m2_ed25519`私钥内容复制到Rocky。

## 18.3 分发公钥

```bash
ssh-copy-id -i ~/.ssh/m2_ed25519.pub student@192.168.200.10
```

在Rocky检查：

```bash
ls -ld ~/.ssh
ls -l ~/.ssh/authorized_keys
tail -n 1 ~/.ssh/authorized_keys
```

建议权限：

```bash
chmod 700 ~/.ssh
chmod 600 ~/.ssh/authorized_keys
```

目录、文件和家目录不能允许其他用户写入，否则sshd可能拒绝使用该公钥。

## 18.4 强制只测试公钥认证

从Ubuntu执行：

```bash
ssh -i ~/.ssh/m2_ed25519 \
  -o IdentitiesOnly=yes \
  -o PasswordAuthentication=no \
  student@192.168.200.10
```

`IdentitiesOnly=yes`防止ssh-agent中其他密钥干扰测试；关闭本次连接的密码回退，可以证明成功确实来自指定密钥。

## 18.5 使用ssh-agent保护口令密钥

```bash
eval "$(ssh-agent -s)"
ssh-add ~/.ssh/m2_ed25519
ssh-add -l
ssh -i ~/.ssh/m2_ed25519 student@192.168.200.10
```

ssh-agent缓存的是解锁后的密钥使用能力，不应在不可信主机上转发Agent。课程基础实验不启用`ForwardAgent yes`。

## 18.6 密钥认证故障

| 现象 | 检查 |
|---|---|
| 客户端忽略私钥 | `ssh -v`、`IdentityFile`、`IdentitiesOnly` |
| 私钥权限过宽 | `chmod 600 ~/.ssh/m2_ed25519` |
| 服务端找不到公钥 | 用户是否正确、`authorized_keys`内容 |
| bad ownership or modes | 家目录、`.ssh`、`authorized_keys`所有者和权限 |
| Rocky权限正确仍失败 | `ls -Z`、`restorecon`、AVC日志 |
| 尝试了太多密钥 | `IdentitiesOnly yes` |

Rocky上恢复SSH目录默认SELinux上下文：

```bash
sudo restorecon -RFv ~/.ssh
ls -laZ ~/.ssh
```

## 18.7 安全关闭密码认证

只有满足以下条件才继续：

- VMware控制台可用。
- 已有会话保持登录。
- 第二个会话能使用指定私钥登录。
- 至少有一个具备sudo权限的密钥用户。

Rocky创建配置片段：

```bash
sudo tee /etc/ssh/sshd_config.d/30-m2-key-only.conf >/dev/null <<'EOF'
PasswordAuthentication no
KbdInteractiveAuthentication no
EOF

sudo sshd -t
sudo systemctl reload sshd
sudo sshd -T | grep -E \
  '^(passwordauthentication|kbdinteractiveauthentication|pubkeyauthentication) '
```

从第二个终端重新验证密钥登录。若失败，从控制台回退：

```bash
sudo rm -f /etc/ssh/sshd_config.d/30-m2-key-only.conf
sudo sshd -t
sudo systemctl reload sshd
```

### 本章验收

- 公钥和私钥用途解释正确。
- 私钥没有离开Ubuntu客户端。
- 使用`PasswordAuthentication=no`的客户端选项仍能登录。
- `ssh -v`明确显示使用`m2_ed25519`。
- 密码认证变更有第二会话验证和回退步骤。

# 第19章 SSH客户端配置与文件传输

## 19.1 使用ssh config管理主机

在Ubuntu编辑`~/.ssh/config`：

```sshconfig
Host rocky-m2
    HostName 192.168.200.10
    User student
    Port 22
    IdentityFile ~/.ssh/m2_ed25519
    IdentitiesOnly yes
    ServerAliveInterval 30
    ServerAliveCountMax 3
```

设置权限并检查展开结果：

```bash
chmod 600 ~/.ssh/config
ssh -G rocky-m2 | grep -E \
  '^(hostname|user|port|identityfile|identitiesonly) '
ssh rocky-m2
```

OpenSSH对大多数客户端参数采用“先取得的值生效”。具体`Host rocky-m2`应放在前面，通用`Host *`默认项放在后面，避免通用项提前覆盖主机专用值。`ssh -G`用于检查最终展开结果。

不要在共享账号的配置中保存明文密码。SSH config本身也不支持安全保存登录密码。

## 19.2 远程执行命令与引号

```bash
ssh rocky-m2 'hostnamectl --static'
ssh rocky-m2 'uptime && free -h'
ssh rocky-m2 'df -h /; systemctl is-active sshd'
```

单引号中的`$(hostname)`由远端Shell展开；双引号可能先被本地Shell展开：

```bash
ssh rocky-m2 'echo "remote=$(hostname) time=$(date -Iseconds)"'
```

批量远程执行命令前，应先在一台实验主机验证退出状态、权限和幂等性。后续Python自动化运维课程中的Paramiko、Fabric和Ansible会复用相同的主机名、用户和密钥规范。

## 19.3 SCP传输方向

准备文件：

```bash
printf 'm2 transfer %s\n' "$(date -Iseconds)" > ~/m2-transfer.txt
sha256sum ~/m2-transfer.txt
```

从Ubuntu上传到Rocky：

```bash
scp ~/m2-transfer.txt rocky-m2:/tmp/
```

从Rocky下载到Ubuntu：

```bash
scp rocky-m2:/etc/hostname ~/rocky-hostname.txt
```

递归目录：

```bash
mkdir -p ~/m2-transfer-dir
printf 'file-a\n' > ~/m2-transfer-dir/a.txt
printf 'file-b\n' > ~/m2-transfer-dir/b.txt
scp -r ~/m2-transfer-dir rocky-m2:/tmp/
```

不要把第16章的`m2-tls`目录整体传输，因为其中包含证书私钥`server.key`。选择传输目录前必须先检查内容。

传输方向由冒号所在位置决定：

```text
本地文件  主机:远程路径   → 上传
主机:远程文件  本地路径   → 下载
```

## 19.4 使用哈希验证完整性

```bash
sha256sum ~/m2-transfer.txt
ssh rocky-m2 'sha256sum /tmp/m2-transfer.txt'
```

两端SHA-256相同可以证明文件内容一致。仅检查文件名、大小或“命令没有报错”不足以证明内容完整。

## 19.5 SFTP交互传输

先在Rocky准备一个可下载文件：

```bash
ssh rocky-m2 'printf "remote sftp file\n" > ~/m2-sftp-remote.txt'
```

在Ubuntu家目录启动SFTP：

```bash
cd ~
sftp rocky-m2
```

进入后常用：

```text
pwd                 查看远端目录
lpwd                查看本地目录
ls                  列出远端文件
lls                 列出本地文件
put m2-transfer.txt /tmp/m2-sftp-upload.txt
get m2-sftp-remote.txt m2-sftp-download.txt
mkdir dirname       创建远端目录
exit                退出
```

SFTP基于SSH通道，不等同于传统FTP，也不需要开放FTP的20/21端口。

# 第20章 rsync增量备份与定时任务

## 20.1 rsync解决什么问题

SCP每次按指定对象传输；rsync会比较源和目标，只更新需要变化的内容，并能保留多种文件属性。远程rsync通常借助SSH，但源端和目标端都需要安装rsync。

本章的数据源、本地备份和cron任务均在Ubuntu客户端的`student`账号中执行；Rocky作为远程备份目标。以下两条安装命令分别在对应系统执行。

```bash
# Rocky
sudo dnf install -y rsync cronie

# Ubuntu
sudo apt install -y rsync cron
```

## 20.2 源目录末尾斜杠

创建实验数据：

```bash
mkdir -p ~/m2-source/{config,data}
printf 'version=1\n' > ~/m2-source/config/app.conf
printf 'record-1\n' > ~/m2-source/data/data.txt
mkdir -p ~/m2-rsync-test/a ~/m2-rsync-test/b
```

对比：

```bash
rsync -av ~/m2-source ~/m2-rsync-test/a/
rsync -av ~/m2-source/ ~/m2-rsync-test/b/
find ~/m2-rsync-test -maxdepth 3 -type f -print
```

- `m2-source`表示复制目录本身，目标中出现`m2-source/`层级。
- `m2-source/`表示复制目录内容，不额外创建该层级。

备份脚本必须明确目标目录结构，不能凭感觉添加或删除末尾斜杠。

## 20.3 观察增量同步

```bash
mkdir -p ~/m2-backup/current
rsync -aiv ~/m2-source/ ~/m2-backup/current/

printf 'version=2\n' > ~/m2-source/config/app.conf
printf 'record-2\n' >> ~/m2-source/data/data.txt
rsync -aiv --dry-run ~/m2-source/ ~/m2-backup/current/
rsync -aiv ~/m2-source/ ~/m2-backup/current/
```

| 选项 | 含义 |
|---|---|
| `-a` | 归档模式，递归并保留常用属性 |
| `-i` | 逐项说明发生了什么变化 |
| `-v` | 详细输出 |
| `-n`或`--dry-run` | 只预演，不写入目标 |
| `--checksum` | 用内容校验和判断变化，更可靠但更耗CPU和I/O |
| `--exclude` | 排除匹配对象 |
| `--partial` | 中断时保留部分文件，便于后续继续传输 |

rsync默认主要依据大小和修改时间快速判断。对于必须验证内容一致的结果，仍应生成哈希清单或执行恢复后的应用验证。

## 20.4 远程rsync

在Ubuntu确认Rocky也安装rsync后执行：

```bash
ssh rocky-m2 'mkdir -p ~/m2-remote-backup/current'
rsync -aiv --dry-run ~/m2-source/ rocky-m2:~/m2-remote-backup/current/
rsync -aiv ~/m2-source/ rocky-m2:~/m2-remote-backup/current/
ssh rocky-m2 'find ~/m2-remote-backup/current -type f -ls'
```

远程SSH命令会在目标端启动rsync进程，因此“客户端有rsync”不代表远程传输一定可用。

## 20.5 谨慎使用--delete

`--delete`会删除目标中源端不存在的对象，使目标成为镜像，而不是保留历史的备份。任何删除同步都必须先预演：

```bash
rsync -aiv --delete --dry-run ~/m2-source/ ~/m2-backup/current/
```

确认源、目标和预演列表之前，不删除`--dry-run`。备份历史更适合使用带时间戳的快照目录、硬链接快照或专用备份软件，不能仅靠一个被`--delete`持续覆盖的目录。

## 20.6 编写可由cron执行的本地备份脚本

定时任务不继承交互Shell的完整PATH、ssh-agent和当前目录。基础实验先使用本地备份，避免把交互密钥口令问题混入cron。

```bash
mkdir -p ~/bin ~/logs ~/m2-backup/current

cat > ~/bin/m2-backup.sh <<'SCRIPT'
#!/bin/bash
set -u

SOURCE="$HOME/m2-source/"
TARGET="$HOME/m2-backup/current/"
LOG="$HOME/logs/m2-backup.log"

mkdir -p "$TARGET" "$(dirname "$LOG")"
printf '[%s] backup start\n' "$(date -Iseconds)" >> "$LOG"

if /usr/bin/rsync -ai "$SOURCE" "$TARGET" >> "$LOG" 2>&1; then
  printf '[%s] backup success\n' "$(date -Iseconds)" >> "$LOG"
  exit 0
else
  code=$?
  printf '[%s] backup failed code=%s\n' "$(date -Iseconds)" "$code" >> "$LOG"
  exit "$code"
fi
SCRIPT

chmod 700 ~/bin/m2-backup.sh
~/bin/m2-backup.sh
tail -n 20 ~/logs/m2-backup.log
```

## 20.7 配置和验证crontab

```bash
command -v rsync
command -v flock
crontab -e
```

加入每10分钟执行一次的实验任务：

```cron
*/10 * * * * /usr/bin/flock -n /tmp/m2-backup-student.lock /home/student/bin/m2-backup.sh
```

这里使用绝对路径，并通过`flock -n`防止上一次任务尚未结束时重复运行。若实际用户名不是`student`，必须替换家目录路径。

检查：

```bash
crontab -l
systemctl status cron --no-pager
tail -f ~/logs/m2-backup.log
```

Ubuntu的服务名通常是`cron`，Rocky是`crond`。本章cron任务位于Ubuntu，因此应检查`cron.service`。

## 20.8 恢复验证

```bash
rm -rf ~/m2-restore-test
mkdir -p ~/m2-restore-test
rsync -a ~/m2-backup/current/ ~/m2-restore-test/
diff -ru ~/m2-source ~/m2-restore-test
echo "diff_exit=$?"
```

`diff`无输出且退出0表示当前内容一致。完成实验后删除定时任务，避免长期残留：

使用`crontab -e`删除包含`m2-backup.sh`的实验行，再执行`crontab -l`确认。不要用未经检查的过滤管道整体重写包含其他任务的crontab。

# 第21章 firewalld基础

## 21.1 防火墙解决什么问题

主机防火墙根据协议、地址、端口、连接状态和区域等条件决定数据包如何处理。它不能代替服务认证、文件权限和应用安全。

```text
客户端请求
→ 网络到达Rocky
→ firewalld/nftables规则判断
→ 内核把允许的数据交给监听Socket
→ 应用处理请求
```

因此“服务正在运行”和“端口正在监听”都不能证明外部一定可访问。

## 21.2 firewalld、nftables与iptables

Rocky Linux 9通常使用firewalld提供动态管理接口，底层使用nftables。`iptables`命令可能作为兼容工具存在。本模块使用firewalld；不要同时维护多套互相冲突的主机防火墙服务。

```bash
sudo dnf install -y firewalld
sudo systemctl enable --now firewalld
firewall-cmd --state
```

Ubuntu常用UFW作为前端，本模块只做对照认知，不要求在Ubuntu重复配置全部firewalld规则。

## 21.3 zone的含义

zone表示对进入流量来源的信任级别。接口或来源会进入某个zone，规则必须添加到实际生效的zone。

```bash
firewall-cmd --get-default-zone
firewall-cmd --get-active-zones
firewall-cmd --get-zones
nmcli -f NAME,DEVICE connection show --active
```

不要因为默认zone是public，就假设网卡一定在public。应以`--get-active-zones`结果为准。下文示例使用：

```bash
IFACE=$(ip route show default | awk 'NR==1 {print $5}')
ZONE=$(firewall-cmd --get-zone-of-interface="$IFACE" 2>/dev/null)
if [[ -z "$ZONE" || "$ZONE" == 'no zone' ]]; then
  ZONE=$(firewall-cmd --get-default-zone)
fi
printf 'interface=%s zone=%s\n' "$IFACE" "$ZONE"
firewall-cmd --zone="$ZONE" --list-all
```

如果结果与`--get-active-zones`不一致，先停止操作并查清接口绑定，不要把同一条规则盲目添加到多个zone。变量只在当前Shell会话中有效，重新登录后需要重新执行。

## 21.4 service与port

```bash
firewall-cmd --get-services | tr ' ' '\n' | grep -E '^(ssh|http|https)$'
firewall-cmd --info-service=ssh
firewall-cmd --info-service=http
```

- service是firewalld预定义的一组端口、协议和可选辅助信息。
- port是直接指定如`8080/tcp`。
- 放行service不会启动应用；启动应用也不会自动放行防火墙。

## 21.5 运行时与永久配置

| 配置 | 立即生效 | reload后保留 | 重启后保留 |
|---|---:|---:|---:|
| 运行时规则 | 是 | 否 | 否 |
| `--permanent`规则 | 否 | reload后生效 | 是 |

查看两套状态：

```bash
firewall-cmd --zone="$ZONE" --list-all
firewall-cmd --permanent --zone="$ZONE" --list-all
```

## 21.6 最小开放8080实验

终端A在Rocky启动：

```bash
python3 -m http.server 8080 --bind 0.0.0.0 --directory ~/m2-web
```

Rocky确认：

```bash
ss -lnt | grep ':8080'
curl http://127.0.0.1:8080/
```

Ubuntu尝试：

```bash
curl --connect-timeout 3 http://192.168.200.10:8080/
```

若被防火墙阻断，先添加运行时规则：

```bash
sudo firewall-cmd --zone="$ZONE" --add-port=8080/tcp
firewall-cmd --zone="$ZONE" --query-port=8080/tcp
```

Ubuntu再次验证。成功后先删除运行时规则：

```bash
sudo firewall-cmd --zone="$ZONE" --remove-port=8080/tcp
```

然后按永久流程完成：

```bash
sudo firewall-cmd --permanent --zone="$ZONE" --add-port=8080/tcp
sudo firewall-cmd --reload
firewall-cmd --zone="$ZONE" --query-port=8080/tcp
```

## 21.7 最小开放原则

- 只开放确有监听服务且业务需要的端口。
- 明确TCP还是UDP。
- 管理端口尽量限制来源。
- 数据库和Redis等内部服务默认不直接开放给所有来源。
- 规则变更后从真实客户端验证，不只看`success`。
- 删除服务前同步删除无用防火墙规则。

远程修改前确认SSH仍被允许：

```bash
firewall-cmd --zone="$ZONE" --query-service=ssh
sudo firewall-cmd --check-config
```

## 21.8 Ubuntu UFW对照

Ubuntu启用UFW前应先允许OpenSSH并保留控制台：

```bash
sudo ufw allow OpenSSH
sudo ufw status verbose
```

如果课程Ubuntu客户端没有对外提供服务，不要求启用UFW。不能为了对照实验在没有业务需求时开放8080或其他端口。

### 本章验收

提交运行时、永久状态和外部验证三类证据。仅提交`firewall-cmd`返回`success`不算完成功能验收。

验收完成后，在终端A按`Ctrl+C`结束Python服务，并确认端口已释放。服务停止后同步删除不再使用的永久规则：

```bash
ss -lnt | grep ':8080' || echo '8080 listener stopped'
sudo firewall-cmd --permanent --zone="$ZONE" --remove-port=8080/tcp
sudo firewall-cmd --reload
firewall-cmd --zone="$ZONE" --query-port=8080/tcp
```

# 第22章 firewalld规则、来源限制与回滚

## 22.1 为什么要限制来源

向所有来源开放SSH比只允许管理网段暴露更大。来源限制应建立在稳定的管理地址规划上；如果客户端使用经常变化的DHCP地址，规则可能导致合法管理者被拒绝。

本章不直接修改现有SSH规则，而是先用9090测试服务练习来源限制，避免锁死管理通道。

重新确认本会话的zone变量：

```bash
IFACE=$(ip route show default | awk 'NR==1 {print $5}')
ZONE=$(firewall-cmd --get-zone-of-interface="$IFACE" 2>/dev/null)
if [[ -z "$ZONE" || "$ZONE" == 'no zone' ]]; then
  ZONE=$(firewall-cmd --get-default-zone)
fi
```

在首次修改规则前保存真实基线：

```bash
mkdir -p ~/m2-evidence
firewall-cmd --zone="$ZONE" --list-all \
  > ~/m2-evidence/firewall-runtime-before.txt
firewall-cmd --permanent --zone="$ZONE" --list-all \
  > ~/m2-evidence/firewall-permanent-before.txt
```

## 22.2 rich rule结构

rich rule可以组合地址、端口、协议、日志和动作：

```text
rule
  family="ipv4"
  source address="192.168.200.20/32"
  port port="9090" protocol="tcp"
  accept
```

终端A在Rocky启动测试服务：

```bash
python3 -m http.server 9090 --bind 0.0.0.0 --directory ~/m2-web
```

确保没有一般性开放9090：

```bash
sudo firewall-cmd --zone="$ZONE" --remove-port=9090/tcp 2>/dev/null || true
sudo firewall-cmd --permanent --zone="$ZONE" --remove-port=9090/tcp 2>/dev/null || true
```

先添加一个故意不匹配Ubuntu地址的规则，证明“来源不匹配时拒绝”。文档示例地址`192.0.2.20`不会匹配实验客户端：

```bash
WRONG_RULE='rule family="ipv4" source address="192.0.2.20/32" port port="9090" protocol="tcp" accept'
sudo firewall-cmd --zone="$ZONE" --add-rich-rule="$WRONG_RULE"
```

从Ubuntu执行`curl --connect-timeout 3 http://192.168.200.10:9090/`，预期失败。随后删除错误来源规则：

```bash
sudo firewall-cmd --zone="$ZONE" --remove-rich-rule="$WRONG_RULE"
```

再只允许Ubuntu真实地址：

```bash
RULE='rule family="ipv4" source address="192.168.200.20/32" port port="9090" protocol="tcp" accept'
sudo firewall-cmd --zone="$ZONE" --add-rich-rule="$RULE"
firewall-cmd --zone="$ZONE" --list-rich-rules
```

从Ubuntu验证：

```bash
curl --connect-timeout 3 http://192.168.200.10:9090/
```

如果Ubuntu实际地址不是`.20`，必须改写`RULE`后再添加。测试完成后删除运行时规则：

```bash
sudo firewall-cmd --zone="$ZONE" --remove-rich-rule="$RULE"
```

## 22.3 持久化和重载

验证运行时规则正确后再添加永久规则：

```bash
sudo firewall-cmd --permanent --zone="$ZONE" --add-rich-rule="$RULE"
sudo firewall-cmd --reload
firewall-cmd --zone="$ZONE" --list-rich-rules
```

reload后必须再次从Ubuntu执行curl，证明永久规则在重载后仍能允许真实来源。

firewalld要求删除时提供完全一致的规则文本，因此变更记录应保存原始命令，而不是只截取部分输出。

## 22.4 zone与NetworkManager连接

查看当前连接绑定：

```bash
CON_NAME=$(nmcli -g GENERAL.CONNECTION device show "$IFACE")
nmcli -f NAME,DEVICE connection show --active
nmcli -g connection.zone connection show "$CON_NAME"
firewall-cmd --get-active-zones
```

本模块只读识别连接和zone关系，不切换活动接口。修改`connection.zone`会立即改变该接口接收流量所采用的策略，还会使之前记录的`ZONE`变量失效。只有具备第二管理通道、完整目标zone规则和明确回滚值时才能切换；不能为了“暂时能通”把接口或默认zone改为`trusted`。

## 22.5 安全变更闭环

```text
记录当前规则
→ 确认控制台和回退命令
→ 添加运行时规则
→ 从真实来源验证允许与拒绝
→ 添加永久规则
→ reload
→ 再次验证
→ 保存变更记录
```

保存变更后状态，与22.1的before文件对照：

```bash
mkdir -p ~/m2-evidence
firewall-cmd --zone="$ZONE" --list-all \
  > ~/m2-evidence/firewall-runtime-after.txt
firewall-cmd --permanent --zone="$ZONE" --list-all \
  > ~/m2-evidence/firewall-permanent-after.txt
```

## 22.6 回滚本章规则

```bash
sudo firewall-cmd --permanent --zone="$ZONE" --remove-rich-rule="$RULE"
sudo firewall-cmd --reload
firewall-cmd --zone="$ZONE" --list-rich-rules
```

按`Ctrl+C`结束9090测试服务，并确认9090监听已消失。

## 22.7 端口转发认知

firewalld支持端口转发和masquerade，但它会改变数据包目标或源地址，排障复杂度明显高于简单放行。本模块只要求理解：

```text
放行端口：允许访问本机监听服务
端口转发：把到达一个地址/端口的流量改送到另一个地址/端口
```

没有明确拓扑、回程路由和业务需求时，不执行端口转发实验。

- rich rule只允许指定Ubuntu地址访问9090。
- 删除规则后访问结果发生预期变化。
- 永久规则经过reload仍存在。
- 最终已清理9090规则，没有影响SSH服务。

# 第23章 SELinux与主机基础防护

## 23.1 DAC与MAC分层

Linux传统文件权限属于自主访问控制DAC，主要依据UID、GID、rwx和ACL。SELinux属于强制访问控制MAC，根据进程域、对象类型和策略规则进一步判断。

```text
访问请求
→ DAC：所有者、组、rwx、ACL是否允许
→ SELinux：进程域是否允许访问目标类型
→ 两层都允许，访问才成功
```

因此`chmod 777`不能保证绕过SELinux，也不是正确修复方式。

## 23.2 SELinux模式

```bash
getenforce
sestatus
```

| 模式 | 是否执行拒绝 | 是否记录AVC | 是否维护标签 |
|---|---:|---:|---:|
| Enforcing | 是 | 是 | 是 |
| Permissive | 否 | 是 | 是 |
| Disabled | 否 | 否 | 否或不完整 |

Permissive适合短时间验证问题是否与SELinux策略有关；Disabled会停止策略和正常标签维护，不应作为常规排错方法。

临时切换仅用于受控诊断：

```bash
sudo setenforce 0
getenforce
sudo setenforce 1
getenforce
```

任何诊断结束都必须恢复Enforcing。

## 23.3 安全上下文

```bash
ls -lZ ~/.ssh
ps -eZ | grep sshd
id -Z
```

常见格式：

```text
system_u:object_r:ssh_home_t:s0
```

字段通常包含SELinux用户、角色、类型和级别。本模块重点关注类型。sshd进程域和用户SSH文件类型之间的策略决定是否允许读取密钥。

## 23.4 chcon、restorecon与semanage fcontext

- `chcon`直接改变当前标签，可能被后续restorecon覆盖。
- `restorecon`根据策略数据库恢复默认标签。
- `semanage fcontext`增加持久路径规则，再用restorecon应用。

安装管理工具：

```bash
sudo dnf install -y policycoreutils-python-utils audit
sudo systemctl enable auditd
systemctl is-active --quiet auditd || sudo service auditd start
sudo systemctl status auditd --no-pager
```

在独立目录练习持久标签规则：

```bash
sudo mkdir -p /srv/m2-keys
sudo semanage fcontext -d '/srv/m2-keys(/.*)?' 2>/dev/null || true
sudo semanage fcontext -a -t ssh_home_t '/srv/m2-keys(/.*)?'
sudo restorecon -RFv /srv/m2-keys
ls -ldZ /srv/m2-keys
```

清理自定义规则：

```bash
sudo semanage fcontext -d '/srv/m2-keys(/.*)?'
sudo restorecon -RFv /srv/m2-keys
```

## 23.5 SSH密钥上下文故障实验

前提：Ubuntu使用`m2_ed25519`公钥认证Rocky已经成功，VMware控制台保持可用。

在Rocky记录并备份：

```bash
ls -lZ /home/student/.ssh/authorized_keys
sudo cp -a /home/student/.ssh/authorized_keys \
  /home/student/.ssh/authorized_keys.m2-backup
```

临时设置错误类型：

```bash
sudo chcon -t httpd_sys_content_t /home/student/.ssh/authorized_keys
ls -lZ /home/student/.ssh/authorized_keys
```

从Ubuntu强制只使用公钥测试：

```bash
ssh -i ~/.ssh/m2_ed25519 \
  -o IdentitiesOnly=yes \
  -o PasswordAuthentication=no \
  student@192.168.200.10
```

若认证失败，在Rocky收集证据：

```bash
sudo ausearch -m AVC,USER_AVC -ts recent
sudo journalctl -u sshd --since '5 minutes ago' --no-pager
```

修复标签：

```bash
sudo restorecon -v /home/student/.ssh/authorized_keys
ls -lZ /home/student/.ssh/authorized_keys
```

再次从Ubuntu测试。实验结果受当前SELinux策略版本影响；如果没有产生拒绝，也必须提交变更前后标签和日志，并说明“该策略未阻止此访问”，不能伪造403或AVC结果。

## 23.6 SELinux排障流程

```text
确认DAC权限和所有者
→ getenforce确认模式
→ ls -Z / ps -eZ检查类型
→ 查看应用日志
→ ausearch查看AVC
→ 判断正确修复是restorecon、semanage fcontext、布尔值还是配置
→ 恢复Enforcing
→ 重新验证功能
```

查看布尔值：

```bash
getsebool -a | head
```

不要看到AVC就直接生成并安装自定义策略模块。优先检查文件放错位置、标签错误、服务使用了非标准端口或已有布尔值尚未启用。

## 23.7 Ubuntu安全模块对照

Ubuntu默认更常见AppArmor：

```bash
sudo aa-status 2>/dev/null || true
```

AppArmor和SELinux实现方式不同，但运维方法相似：先确认传统权限，再确认强制访问控制状态、策略对象和拒绝日志。本课程以Rocky SELinux为主线，不要求在本模块编写AppArmor配置文件。

## 23.8 主机基础防护清单

- 使用受支持的软件源并及时评估安全更新。
- 普通账号登录，sudo执行必要管理操作。
- 禁止root远程密码登录。
- 优先使用独立、带口令的SSH密钥。
- 防火墙只开放必要服务并限制管理来源。
- 保持SELinux Enforcing，按证据修复策略问题。
- 停止并禁用无业务用途的服务。
- 保持时间同步，确保日志时间可信。
- 定期检查登录失败、异常监听端口和失败Unit。
- 配置和密钥变更必须备份、验证和可回退。

# 第24章 网络与安全综合排障

## 24.1 排障不是随机尝试命令

高效排障需要回答四个问题：

1. 范围：一个客户端、一个服务还是整台主机？
2. 层次：名称、路由、连接、监听、防护还是应用？
3. 证据：哪个命令、日志或抓包支持判断？
4. 变更：如何验证修复并安全回退？

推荐模型：

```text
目标名称和地址
→ 客户端IP与路由
→ 网关和目标可达性
→ 目标服务进程
→ 监听协议、地址和端口
→ firewalld规则
→ SELinux和文件权限
→ 应用配置与日志
```

## 24.2 建立可重复的测试服务

先确认前面章节的临时Python进程已经停止：

```bash
ss -lntp | grep ':8080' || echo '8080 is free'
```

如果仍有监听，回到启动该进程的终端按`Ctrl+C`，并根据`ss -lntp`显示的PID确认进程身份。不要使用宽泛的`pkill python3`，它可能终止无关任务。

在Rocky创建页面：

```bash
sudo mkdir -p /srv/m2-web
printf '<h1>M2 service baseline</h1>\n' | \
  sudo tee /srv/m2-web/index.html >/dev/null
sudo chmod 755 /srv/m2-web
sudo chmod 644 /srv/m2-web/index.html
```

创建systemd Unit：

```bash
sudo tee /etc/systemd/system/m2-web.service >/dev/null <<'UNIT'
[Unit]
Description=Module 2 troubleshooting web service
After=network.target

[Service]
Type=simple
User=nobody
WorkingDirectory=/srv/m2-web
ExecStart=/usr/bin/python3 -m http.server 8080 --bind 0.0.0.0
Restart=on-failure

[Install]
WantedBy=multi-user.target
UNIT

sudo systemctl daemon-reload
sudo systemctl enable --now m2-web
systemctl status m2-web --no-pager
ss -lnt | grep ':8080'
```

确保防火墙规则：

```bash
IFACE=$(ip route show default | awk 'NR==1 {print $5}')
ZONE=$(firewall-cmd --get-zone-of-interface="$IFACE" 2>/dev/null)
if [[ -z "$ZONE" || "$ZONE" == 'no zone' ]]; then
  ZONE=$(firewall-cmd --get-default-zone)
fi
sudo firewall-cmd --permanent --zone="$ZONE" --add-port=8080/tcp
sudo firewall-cmd --reload
```

在Ubuntu确保名称解析后验证：

```bash
sudo sed -i '/m2-rocky\.test/d' /etc/hosts
echo '192.168.200.10 m2-rocky.test m2-rocky' | sudo tee -a /etc/hosts
getent hosts m2-rocky.test
curl --fail-with-body http://m2-rocky.test:8080/
```

只有基线成功后才能开始故障实验。

## 24.4 故障一：服务停止

在Rocky注入：

```bash
sudo systemctl stop m2-web
```

预期证据：

- `systemctl is-active m2-web`不是active。
- `ss`没有8080监听。
- 本机和远端连接通常被拒绝。

修复：

```bash
sudo systemctl start m2-web
systemctl is-active m2-web
```

## 24.5 故障二：监听地址错误

创建覆盖配置，使服务只监听回环：

```bash
sudo systemctl edit m2-web
```

写入：

```ini
[Service]
ExecStart=
ExecStart=/usr/bin/python3 -m http.server 8080 --bind 127.0.0.1
```

应用：

```bash
sudo systemctl daemon-reload
sudo systemctl restart m2-web
ss -lnt | grep ':8080'
```

预期：Rocky的`curl 127.0.0.1:8080`成功，Ubuntu访问Rocky网卡地址失败。修复：

```bash
sudo rm -f /etc/systemd/system/m2-web.service.d/override.conf
sudo rmdir /etc/systemd/system/m2-web.service.d 2>/dev/null || true
sudo systemctl daemon-reload
sudo systemctl restart m2-web
```

## 24.6 故障三：防火墙规则缺失

```bash
sudo firewall-cmd --permanent --zone="$ZONE" --remove-port=8080/tcp
sudo firewall-cmd --reload
```

预期：

- 服务active。
- `ss`仍监听`0.0.0.0:8080`。
- Rocky本机curl成功。
- Ubuntu访问超时或被拒绝，取决于防火墙策略。

修复：

```bash
sudo firewall-cmd --permanent --zone="$ZONE" --add-port=8080/tcp
sudo firewall-cmd --reload
```

## 24.7 故障四：客户端名称指向错误

在Ubuntu先备份，再把实验名称指向文档示例地址：

```bash
sudo cp -a /etc/hosts /etc/hosts.before-m2-fault
sudo sed -i '/m2-rocky\.test/d' /etc/hosts
echo '192.0.2.10 m2-rocky.test' | sudo tee -a /etc/hosts
```

证据：

```bash
getent hosts m2-rocky.test
curl --connect-timeout 3 http://m2-rocky.test:8080/
curl http://192.168.200.10:8080/
```

如果IP访问成功而名称访问失败或到达错误地址，应先修复解析：

```bash
sudo cp -a /etc/hosts.before-m2-fault /etc/hosts
getent hosts m2-rocky.test
```

# 模块复习

## 核心关系

```text
名称 → DNS或hosts → IP
IP → 路由表 → 网卡和下一跳
端口 → Socket → 进程
远程管理 → SSH主机验证 + 用户认证 + 加密通道
外部访问 → 服务监听 + firewalld允许 + SELinux/DAC允许
备份可用 → 同步成功 + 日志成功 + 恢复验证成功
```

## 常用命令速查

| 任务 | 命令 |
|---|---|
| 地址和路由 | `ip -br addr`、`ip route`、`ip route get` |
| NetworkManager | `nmcli device`、`nmcli connection` |
| 监听和连接 | `ss -lntup`、`nc -vz` |
| 系统解析 | `getent hosts` |
| DNS查询 | `dig`、`nslookup` |
| HTTP验证 | `curl -v/-I/-L/--fail-with-body` |
| SSH调试 | `ssh -v`、`sshd -T`、`sshd -t` |
| 密钥 | `ssh-keygen`、`ssh-copy-id`、`ssh-add` |
| 传输 | `scp`、`sftp`、`rsync` |
| 定时任务 | `crontab -e/-l` |
| firewalld | `firewall-cmd --list-all/--add-port/--add-rich-rule` |
| SELinux | `getenforce`、`ls -Z`、`ausearch`、`restorecon` |

## 复习题

1. 有IP地址为什么仍然可能无法访问外部网络？
2. `ip route get`与`ping`分别证明什么？
3. `127.0.0.1:8080`和`0.0.0.0:8080`有什么区别？
4. Connection refused与timeout分别支持哪些排障方向？
5. 为什么`dig`结果和`getent hosts`可能不同？
6. curl收到404时为什么默认仍可能退出0？
7. 主机密钥和用户认证密钥分别证明谁的身份？
8. 为什么不能无条件执行`ssh-keygen -R`消除警告？
9. 为什么禁用SSH密码认证前必须保留两个会话和控制台？
10. rsync源目录末尾斜杠如何影响目标目录结构？
11. 为什么`--delete`不等于可靠备份？
